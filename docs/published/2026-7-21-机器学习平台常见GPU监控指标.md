# 机器学习平台常见 GPU 监控指标：一篇给新手的说明

训练或推理任务跑在 GPU 上时，监控面板通常会显示一组百分比、带宽、温度和功率数字。它们并不是同一件事的不同说法：有的表示 GPU 是否正在工作，有的表示显存是否快装满，有的表示数据是否在主机和 GPU 之间搬运，还有的反映硬件执行了哪类计算。

本文以 NVIDIA GPU 为例，介绍机器学习平台最常见的指标、它们的计算或获取方式，以及看到异常数值时应如何理解。不同型号、驱动、DCGM 版本和云平台的字段名可能略有差异，但基本含义相同。

## 先建立一个直观模型

可以把一次训练理解为一条流水线：CPU 读取和预处理数据，数据经 PCIe 送到 GPU；GPU 将模型参数、激活值和输入放到显存中；SM 和各类计算单元完成计算；最后可能把日志、预测结果或检查点数据送回主机。

因此：

- **GPU 利用率、SM Activity、Tensor/FP Engine Activity** 关注“算得有多忙”；
- **显存使用量、显存利用率** 关注“仓库占了多少”；
- **PCIe 流入/流出速率** 关注“路上搬了多少数据”；
- **温度、功率** 关注“运行状态和硬件压力”。

百分比通常是**监控采样窗口内的平均值**。例如 10 秒刷新一次，显示 70%，表示这 10 秒内相应硬件约有 70% 的时间处于指定的活跃状态；它不保证每一瞬间都是 70%。

## 1. GPU 利用率（%）

**它表示什么**

GPU 利用率是最常见的总览指标。对 NVIDIA 的 NVML/nvidia-smi 而言，它通常表示采样期间 GPU 上至少有一个内核（kernel）在执行的时间比例。可把它理解为“GPU 有没有在干活”。

例如，GPU 利用率为 90%，说明在最近一个采样周期内，大部分时间有 GPU 内核正在运行；10% 则常见于数据读取、CPU 预处理、同步、评估或等待下一个 batch 的阶段。

**如何计算或获取**

概念上可写为：

```text
GPU 利用率 = GPU 有内核在执行的时间 / 采样窗口总时间 x 100%
```

实际不应在应用层自行计时，而应从驱动获取。可以用：

```bash
nvidia-smi --query-gpu=utilization.gpu --format=csv,noheader,nounits
```

在机器学习平台中，通常由 NVIDIA DCGM、DCGM Exporter 或 NVML 采集；DCGM 对应的常见字段是 `DCGM_FI_DEV_GPU_UTIL`。

**怎样解读**

- 长时间接近 0%：任务可能未真正使用 GPU，或正在等待数据、通信、CPU、磁盘或其他资源。
- 训练期间较稳定地处于较高水平：通常是正常且积极的信号。
- 不必追求永远 100%：验证、保存 checkpoint、分布式同步和短小 batch 都会造成波动。
- 高 GPU 利用率不等于训练一定高效。若 SM Activity 或有效吞吐很低，或存在大量低效内核，仍可能浪费算力。

## 2. 显存利用率（%）

**先注意一个容易混淆的问题**

“显存利用率”在不同监控面板里可能有两种意思：

1. **显存容量占用率**：已经分配/使用的显存占总显存的比例。本文以下默认指它。
2. **显存控制器忙碌率**：显存控制器处理读写请求的时间比例，反映的是显存带宽活动，不是显存装了多少数据。`nvidia-smi` 的 `utilization.memory` 属于这一类。

查看面板字段说明很重要。前者回答“会不会 OOM”，后者回答“是否受显存带宽限制”。

**容量占用率的计算**

```text
显存利用率 = 显存使用量 / 显存总量 x 100%
```

例如，一张 80 GiB 的卡已使用 60 GiB 显存，则：

```text
60 / 80 x 100% = 75%
```

使用量可通过 `nvidia-smi` 或 NVML 获取：

```bash
nvidia-smi --query-gpu=memory.used,memory.total --format=csv,noheader,nounits
```

有些平台直接报告百分比，有些只报告 `memory.used` 和 `memory.total`，由平台按上式计算即可。注意，框架的显存缓存（例如 PyTorch caching allocator）也可能计入已使用显存，即使其中一部分稍后可以被框架复用。

**怎样解读**

- 接近 100% 时，下一次分配可能触发 OOM（显存不足）。建议预留余量，尤其是 batch 大小会变化、存在峰值激活或需要保存检查点时。
- 使用率高、GPU 利用率低不一定有问题：模型和参数已放入显存，但此刻可能正在等数据。
- 使用率低也不一定代表浪费：小模型或推理服务本来就不需要大显存。

## 3. 显存使用量（GiB）

**它表示什么**

显存使用量是当前已被 GPU 上的进程占用或驱动报告为已使用的显存容量，常用于定位 OOM、估算还能启动多少任务，以及分析不同模型规模的资源消耗。

1 GiB = 1024 MiB = 1024 x 1024 x 1024 Bytes。GiB 是二进制单位，不要与十进制的 GB 混用。

**如何计算或获取**

驱动一般能直接返回 MiB，再换算为 GiB：

```text
显存使用量（GiB）= 显存使用量（MiB）/ 1024
```

例如 `nvidia-smi` 显示 24576 MiB，即 24 GiB。也可以按进程查看：

```bash
nvidia-smi
```

对训练任务，显存通常主要由模型参数、梯度、优化器状态、输入 batch、前向激活值和框架缓存构成。混合精度、梯度检查点、减小 batch size 都可能降低峰值使用量。

## 4. SM Activity（%）

**它表示什么**

SM（Streaming Multiprocessor，流式多处理器）是 NVIDIA GPU 的主要计算资源。SM Activity 表示 SM 在采样周期中处于活跃状态的周期比例，比“GPU 利用率”更接近核心计算资源是否被实际调度。

在 DCGM profiling 指标中，常见字段为 `DCGM_FI_PROF_SM_ACTIVE`。它通常来自硬件性能计数器，而不是简单的进程状态判断。

**概念计算方式**

```text
SM Activity = SM 活跃时钟周期数 / SM 总时钟周期数 x 100%
```

不同架构对“活跃”的精确定义略有不同，实际平台应直接读取 DCGM 或 Nsight Systems/Compute 公开的计数结果。

**怎样解读**

- GPU 利用率高但 SM Activity 明显低：GPU 可能在执行内存搬运、很短的内核、同步相关工作，或因访存等待而未充分利用 SM。
- SM Activity 高：说明计算核心较忙，但仍需结合 Tensor/FP 指标判断在进行什么精度的计算。
- SM Activity 不是“模型准确率”或“训练速度”。高值只说明硬件繁忙，不代表每个内核都高效。

## 5. PCIe 流入速率（GiB/s）

**它表示什么**

PCIe 流入速率表示通过 PCIe **进入 GPU** 的数据速度，即 GPU 接收的数据量。最常见的方向是 CPU/主机内存到 GPU 的训练输入、参数或通信数据。

**计算或获取方法**

监控系统常先读到每个采样窗口的接收字节数，按时间差计算：

```text
流入速率（Bytes/s）= (本次接收字节计数 - 上次接收字节计数) / 两次采样间隔（s）
流入速率（GiB/s）= 流入速率（Bytes/s）/ 1024 / 1024 / 1024
```

DCGM 中可使用 `DCGM_FI_PROF_PCIE_RX_BYTES` 一类字段。这里的 RX 是相对于 GPU 而言的“接收”，即流入 GPU；平台需确认自己对方向的命名约定。

**怎样解读**

- 训练阶段有持续流入是正常的，因为每个 batch 都要送到 GPU。
- GPU 利用率低且流入长期很低，常见原因是数据加载、CPU 预处理、网络存储或 DataLoader workers 成了瓶颈。
- 流入很高不一定是好事。频繁把本可留在 GPU 的数据来回搬运，会占用 PCIe 带宽并增加等待。
- 若数据通过 NVLink/NVSwitch 在 GPU 间传输，PCIe 指标不会完整反映这部分流量，应额外查看 NVLink 指标。

## 6. PCIe 流出速率（MiB/s）

**它表示什么**

PCIe 流出速率表示通过 PCIe **离开 GPU** 的数据速度，即 GPU 向主机发送的数据量。常见来源包括把预测结果或日志搬回 CPU、保存检查点前的数据复制，或者部分跨设备通信。

**计算或获取方法**

```text
流出速率（Bytes/s）= (本次发送字节计数 - 上次发送字节计数) / 两次采样间隔（s）
流出速率（MiB/s）= 流出速率（Bytes/s）/ 1024 / 1024
```

DCGM 常用相应的 `DCGM_FI_PROF_PCIE_TX_BYTES` 字段；TX 是相对于 GPU 的“发送”，即流出 GPU。

**怎样解读**

- 少量、稳定的流出通常正常，例如上报 loss、准确率或返回少量预测结果。
- 训练中持续出现很高的流出，要检查是否在每个 step 调用了 `.cpu()`、`.numpy()`、`item()` 或同步复制了大张量。这些操作可能让 CPU 等待 GPU，并降低整体吞吐。
- 注意本指标单位是 MiB/s，不能直接与 GiB/s 的流入数值按数字比较。`1 GiB/s = 1024 MiB/s`。

## 7. Tensor Activity（%）

**它表示什么**

Tensor Activity 表示 Tensor Core（张量核心）执行相关矩阵运算的活跃比例。Tensor Core 擅长矩阵乘法、卷积等深度学习中最核心的操作，在支持的 GPU 和精度模式下通常能带来很高吞吐。

DCGM 常见字段是 `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE`。

**概念计算方式**

```text
Tensor Activity = Tensor Core 管线活跃周期 / 总采样周期 x 100%
```

该指标依赖硬件和驱动暴露的性能计数器。并非所有旧卡、虚拟化环境或 DCGM 配置都支持；没有数据不应直接判定为 0%。

**怎样解读**

- 对大模型训练、卷积和矩阵乘法密集任务，较高的 Tensor Activity 往往是正常现象。
- 指标低可能因为模型规模小、操作不适合 Tensor Core、矩阵尺寸没有对齐，或没有启用合适的 BF16/FP16/TF32 等计算路径。
- 它不是总算力利用率。Tensor Activity 低而 SM Activity 高，可能是在执行数据处理、归约、逐元素操作，或使用其他计算管线。

## 8. FP64 Engine Activity（%）

**它表示什么**

FP64 是双精度浮点计算，数值精度高，常用于科学计算、仿真和部分高精度数值任务。FP64 Engine Activity 表示执行 FP64 指令的计算管线活跃比例。

DCGM 常见字段是 `DCGM_FI_PROF_PIPE_FP64_ACTIVE`，概念上：

```text
FP64 Engine Activity = FP64 管线活跃周期 / 总采样周期 x 100%
```

深度学习训练通常不需要大量 FP64。若普通模型训练中它很高，应检查是否意外使用了 `float64`（PyTorch 中常显示为 `torch.float64`）。

## 9. FP32 Engine Activity（%）

**它表示什么**

FP32 是单精度浮点计算，是传统深度学习训练最常用的数据类型。FP32 Engine Activity 表示 FP32 计算管线的活跃比例。

DCGM 常见字段是 `DCGM_FI_PROF_PIPE_FP32_ACTIVE`，概念计算为：

```text
FP32 Engine Activity = FP32 管线活跃周期 / 总采样周期 x 100%
```

若模型主要按普通 FP32 路径运行，FP32 Activity 往往较高。不过在较新的 NVIDIA GPU 上，矩阵乘法可能被调度到 Tensor Core（包括 TF32 路径）执行，因此不能把“FP32 模型”简单等同于“FP32 Engine Activity 必然高”。

## 10. FP16 Engine Activity（%）

**它表示什么**

FP16 是半精度浮点计算，占用显存较少、计算吞吐通常更高，是混合精度训练和高性能推理的常用格式。FP16 Engine Activity 表示 FP16 标量或向量计算管线的活跃比例。

DCGM 常见字段是 `DCGM_FI_PROF_PIPE_FP16_ACTIVE`，概念计算为：

```text
FP16 Engine Activity = FP16 管线活跃周期 / 总采样周期 x 100%
```

启用 FP16/BF16 混合精度后，很多矩阵运算会走 Tensor Core，因此 FP16 Engine Activity 不一定会和预想一样高。判断混合精度是否生效时，应把它与 Tensor Activity、模型框架日志和实际吞吐一起看。

## 11. 温度（°C）

**它表示什么**

温度是 GPU 传感器报告的核心温度，单位为摄氏度（°C）。它反映芯片的热状态，不等同于机房环境温度，也不一定是显存颗粒的温度。

**如何获取**

```bash
nvidia-smi --query-gpu=temperature.gpu --format=csv,noheader,nounits
```

DCGM 常见字段是 `DCGM_FI_DEV_GPU_TEMP`。具体传感器类型与告警阈值以 GPU 型号和厂商规定为准。

**怎样解读**

- 负载升高后温度上升是正常现象。
- 长时间接近设备温度上限，可能触发降频（thermal throttling），使训练变慢。
- 温度异常高时，检查风扇、散热通道、机箱风道、环境温度和任务负载；不要只靠提高告警阈值掩盖问题。

## 12. 功率（W）

**它表示什么**

功率表示 GPU 当前的电功率消耗，单位为瓦特（W）。它是瞬时或短窗口平均读数，不是累计耗电量。累计耗电量需要对功率随时间积分，单位通常是 Wh 或 kWh。

**如何获取和估算耗电量**

```bash
nvidia-smi --query-gpu=power.draw,power.limit --format=csv,noheader
```

DCGM 常见字段是 `DCGM_FI_DEV_POWER_USAGE`。若以固定采样周期近似，耗电量可估算为：

```text
耗电量（Wh）约等于 每个采样点的功率（W）之和 x 采样间隔（h）
```

例如平均功率为 300 W，持续 2 小时，约消耗 600 Wh，即 0.6 kWh。实际服务器总耗电还应加上 CPU、内存、风扇、网络和电源损耗，不能只看 GPU 功率。

**怎样解读**

- 高负载时功率接近功率上限通常正常。
- GPU 利用率和 SM Activity 都高、功率却持续偏低，可能是频率/功率限制、温度限制或工作负载本身较轻；需要结合时钟频率和 throttling 原因进一步判断。
- 功率高不自动代表效率高，但在同一模型、同一配置下，吞吐没有提升而功率更高，值得检查配置变化。

## 指标之间应该怎样一起看

单一指标很容易产生误判。下面是几种常见组合：

| 现象 | 可能含义 | 优先排查方向 |
| --- | --- | --- |
| GPU 利用率低，PCIe 流入低 | GPU 经常在等输入 | DataLoader、CPU 预处理、磁盘/网络读取、batch 是否过小 |
| GPU 利用率高，SM Activity 低 | 有内核在运行，但核心计算未充分忙碌 | 内核粒度、访存等待、同步、分析 Nsight 时间线 |
| SM Activity 高，Tensor Activity 高 | 深度学习矩阵运算较活跃 | 继续观察吞吐、显存和温度即可 |
| 显存利用率接近 100% | OOM 风险高 | 减小 batch、启用混合精度/梯度检查点、预留峰值空间 |
| PCIe 流出持续很高 | 可能频繁把大张量传回 CPU | 检查 `.cpu()`、`.numpy()`、`item()` 和同步操作 |
| 温度高且性能下降 | 可能热降频 | 检查散热、风道、风扇、环境温度和 throttling |
| FP64 Activity 异常高 | 普通深度学习中可能误用了双精度 | 检查数据、模型参数和默认 dtype |

## 一个实用的采集起点

`nvidia-smi` 很适合人工快速核对基础指标：

```bash
nvidia-smi --query-gpu=index,name,utilization.gpu,memory.used,memory.total,temperature.gpu,power.draw \\
  --format=csv,noheader
```

要持续采集并绘制仪表盘，常见组合是 DCGM 负责读取 GPU 指标，DCGM Exporter 将其暴露给 Prometheus，再由 Grafana 展示。SM、Tensor、FP64/FP32/FP16、PCIe 等 profiling 指标通常需要在 DCGM 的采集配置中显式启用，并可能受 GPU 型号、驱动权限、MIG/虚拟化模式及多用户性能计数器限制影响。

## 最后记住这三句话

1. **GPU 利用率高，只能说明 GPU 没闲着；SM 和各类 Engine Activity 才能进一步说明它在忙什么。**
2. **显存“占用率”和显存“控制器忙碌率”不是同一个指标；前者判断 OOM 风险，后者判断带宽压力。**
3. **先看趋势和指标组合，再下结论。** 单个采样点的抖动很常见，持续数分钟或一个完整训练阶段的模式才更有诊断价值。


## 下一篇：这些指标是怎样出现在监控面板上的

理解指标含义之后，下一个自然的问题是：GPU 上的原始数据是谁读取的，为什么 Prometheus 能保存它们，Grafana 又是怎样画出曲线的？

这条链路通常由四个组件完成：**DCGM 读取和管理 GPU 遥测数据，DCGM Exporter 将数据转换成 Prometheus 能理解的格式，Prometheus 定期采集并保存时间序列，Grafana 查询 Prometheus 并制作仪表盘。**

下一篇将从零介绍这四个组件的分工、数据流、基本部署方式和常见误区。
