# 看懂 MFU / HFU / GPU 利用率：训练小白必须分清的三个指标

你第一次跑大模型训练时，大概率会遇到这样一个场景：

> 打开 `nvidia-smi`，看到 GPU 利用率 99%，心里一喜——"满载了，钱没白花"。可老板问你"算力用得怎么样"，隔壁做性能优化的同事却淡淡说一句："你那个 MFU 才 20%，还有大把空间。"

这时候你会一脸懵：不是已经 99% 了吗，怎么又只有 20%？

问题就出在：**GPU 利用率、MFU、HFU 根本不是一回事**。它们回答的是三个完全不同的问题。这篇文章就用大白话把这三个指标讲清楚，让你以后看到数字能立刻知道它在说什么。

## 一、先建立一个直觉：忙 ≠ 高效

想象你雇了一个顶级大厨（GPU），他每小时能炒 100 道菜（这是他的"理论峰值能力"）。

现在你去厨房看了一眼，大厨正在不停地干活，手一刻没停——这叫"**忙**"。

但你仔细一看：他大部分时间在洗菜、切菜、找调料、等食材上桌，真正"炒菜"的时间其实没多少。一小时下来只炒出了 20 道菜——这叫"**高效（或不高效）**"。

- "大厨有没有在干活" → 对应 **GPU 利用率**
- "大厨真正炒出了多少菜 / 他满血能炒多少菜" → 对应 **MFU**

一句话记住：**GPU 利用率衡量"忙不忙"，MFU 衡量"值不值"。** 忙不代表值。

## 二、GPU 利用率（GPU Utilization）：最容易被误解的指标

这是你在 `nvidia-smi` 里看到的那个百分比（`GPU-Util` 那一列）。

它的真实含义，很多人都搞错了。它**不是**"算力用了百分之多少"，而是：

> 在过去的一小段采样时间里，GPU 上**有没有至少一个 kernel（计算任务）在跑**的时间占比。

换句话说，只要 GPU 这一瞬间"手里有活"，哪怕只用了 1% 的计算单元，这个采样点也算"忙"。

所以会出现一个很坑的现象：

- 你的程序可能只是在做一些零碎的小操作、搬数据、等 CPU 喂数据；
- GPU 虽然没干多少"真正的大计算"，但它一直有零碎活儿；
- 于是 `nvidia-smi` 显示 **99%**，看起来很美好，实际算力浪费严重。

**结论：GPU 利用率高是"必要条件"，不是"充分条件"。** 它低了（比如只有 30%）肯定有问题（多半是数据加载、CPU 预处理拖了后腿）；但它高了，并不能证明你跑得快。它只能当"报警灯"，不能当"成绩单"。

## 三、MFU（Model FLOPs Utilization）：真正的"成绩单"

MFU 的全称是 **Model FLOPs Utilization**，中文可以叫"模型算力利用率"。它才是业界评价训练效率的"黄金指标"。

它的定义其实很直白：

> MFU = 模型训练真正"必须做"的计算量 ÷ 这段时间 GPU 理论上最多能做的计算量

拆开看两部分：

**分子：模型真正需要的计算量。**
这里的关键词是"模型本身需要的"。比如训练一个 Transformer，一次前向 + 反向传播，按公式算下来理论上需要多少次浮点运算（FLOPs），这是一个**和你代码写得好不好无关**的"标准答案"。常用的粗略估算公式是：

> 每个 token 的训练计算量 ≈ 6 × 模型参数量
>（6 = 前向 2 次 + 反向 4 次，这是一个方便记忆的经验值）
>
> **小白科普**
> 
> 模型参数量就是模型中**所有参数张量的元素总数**。例如，一个形状为 `[4096, 4096]` 的权重矩阵，包含 `4096 × 4096 ≈ 1680 万`个参数。
> 
> 通常有两种获取方式：
> 
> **1. 查模型介绍**
> 
> 模型名称中的 `7B`、`32B` 等通常表示近似参数量，`B` 表示十亿：
> 
> - 7B ≈ 70 亿参数
> - 32B ≈ 320 亿参数
> 
> 准确值可以查模型的官方说明或 Hugging Face 模型卡。
> 
> **2. 用代码统计**
> 
> 已经用 PyTorch 加载模型时：
> 
> ```python
> # 总参数量
> total_params = sum(p.numel() for p in model.parameters())
> print(f"总参数量：{total_params:,}")
> print(f"约 {total_params / 1e9:.2f}B")
> 
> # 参与训练的参数量
> trainable_params = sum(
>     p.numel() for p in model.parameters() if p.requires_grad
> )
> print(f"可训练参数量：{trainable_params:,}")
> ```
> 
> 对于文中的 **“每个 token 的训练计算量 ≈ 6 × 模型参数量”**，通常使用**稠密模型全> 参数训练的总参数量**。例如，7B 模型每个 token 约需 `6 × 7×10⁹ = 42×10⁹ > FLOPs`，也就是约 **420 亿次浮点运算**。
> 
> 注意：**MoE 模型需要考虑每个 token 激活的参数量；LoRA 微调也不能直接把可训练参> 数量代入 `6N`**，因为冻结的模型权重仍参与计算。

**分母：GPU 的理论峰值算力 × 时间。**
比如一张 H100 的 BF16 峰值大约是 ~990 TFLOPS，这是厂商标称的"满血速度"，实际基本摸不到。

举个例子你就懂了：

- 你算出模型每秒"必须做" 200 TFLOPs 的有效计算；
- 你用的 GPU 理论峰值是 1000 TFLOPS；
- 那 MFU = 200 / 1000 = **20%**。

意思是：这块卡的能力，你只真正用上了两成。

> **小白科普**
> T 是 Tera（万亿），表示 \(10^{12}\)。
> - 1 TFLOPs = \(10^{12}\) 次浮点运算，即 1 万亿次。
> - 1 TFLOPS = 每秒 \(10^{12}\) 次浮点运算，即 每秒 1 万亿次。
> 
> 前者表示计算量，后者表示计算速度。不过实际资料中大小写经常混用，需要结合上下文判断。

**这就解释了开头的矛盾**：GPU 利用率 99%（大厨一直在忙），但 MFU 只有 20%（真正炒出来的菜只有满血的两成）。中间那 79% 哪去了？被通信、等待、显存搬运、小算子、流水线空泡等各种"杂事"吃掉了。

一个经验参考（会随硬件和模型变化，仅供感受量级）：

- 大模型预训练能做到 **MFU 40%~50%** 就算相当不错的工程水平；
- 能上到 50%~60% 属于优化得很好；
- 如果你只有 10%~20%，说明优化空间巨大，别急着加卡，先优化。

## 四、HFU（Hardware FLOPs Utilization）：加上"重复劳动"的那一版

HFU 全称 **Hardware FLOPs Utilization**，"硬件算力利用率"。它和 MFU 长得几乎一样，只有分子不同：

> - MFU 分子 = 模型**理论上必须**的计算量
> - HFU 分子 = GPU **实际真正执行**的计算量（包含那些"额外多算的"）

为什么会有"额外多算的"？最典型的就是 **激活重计算（activation recomputation / gradient checkpointing）**。

这是一种省显存的常用技巧：反向传播时，为了不把中间结果全存下来（省显存），干脆在需要时**再前向算一遍**。这就等于让 GPU 多干了一遍活。

于是：

- 这部分"重算"的计算量，**算进 HFU 的分子，不算进 MFU 的分子**。
- 所以通常 **HFU ≥ MFU**。

用大厨比喻：

- MFU 问的是"你最终端上桌了多少道菜"；
- HFU 问的是"你的锅铲实际翻炒了多少次"（包括因为失误重炒的那几次）。

**怎么用这两个指标判断问题？**

- 如果 **HFU 很高，但 MFU 偏低**：说明 GPU 其实在拼命算，只是算了很多"重复劳动"（比如开了重计算）。瓶颈不在硬件没吃饱，而在于你在用算力换显存。
- 如果 **HFU 和 MFU 都低**：说明 GPU 真没在好好算，瓶颈多半在通信、数据加载、同步等待这些"非计算"环节。

一句话：**MFU 看"产出效率"，HFU 看"硬件干活效率"，两者的差距告诉你有多少算力花在了重计算这类额外开销上。**

## 五、三者放一起对比

| 指标 | 回答的问题 | 怎么得到 | 高了说明什么 | 局限 |
|------|-----------|---------|------------|------|
| GPU 利用率 | GPU 忙不忙？ | `nvidia-smi` 直接读 | 有活在干（但可能是杂活） | 不能反映算力真实使用率 |
| MFU | 算力花得值不值？ | 模型理论 FLOPs ÷ 峰值算力 | 真正的训练效率高 | 要自己算，依赖理论 FLOPs 估算 |
| HFU | 硬件实际干活多不多？ | 实际执行 FLOPs ÷ 峰值算力 | 硬件在拼命算（含重复劳动） | 算得多不等于产出高 |

它们的大小关系通常是：

> GPU 利用率（看着最高、最虚）  >  HFU  ≥  MFU（最实在）

## 六、给小白的实操建议

1. **别只看 `nvidia-smi` 的利用率就下结论**。它只是报警灯：低了一定有问题，高了不代表没问题。
2. **优化排错的第一步，先看利用率**。如果利用率都上不去（比如长期低于 70%、还一卡一卡的），八成是数据加载（DataLoader）或 CPU 预处理成了瓶颈，先解决喂数据的问题，再谈算力。
3. **评价训练效率，认准 MFU**。想横向比较"我这套配置好不好"、"换了并行策略有没有提升"，用 MFU 说话最靠谱。主流训练框架（如 Megatron-LM）通常会直接帮你打印 MFU / HFU，不用自己手算。
4. **MFU 和 HFU 对比着看**。差距大，说明重计算等额外开销占比高，可以权衡"显存 vs 速度"。
5. **不要盲目追求 100%**。MFU 受通信、流水线空泡等物理限制，大规模训练能稳定做到 40%+ 已经很好，别为了刷数字钻牛角尖。

## 结语

把这三个词的关系记成一句话就够了：

> **GPU 利用率告诉你"GPU 在不在忙"，HFU 告诉你"它实际算了多少"，MFU 才告诉你"这些算力到底值不值"。**
