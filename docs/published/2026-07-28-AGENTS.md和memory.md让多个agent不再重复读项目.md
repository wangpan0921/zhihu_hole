# AGENTS.md 和 memory.md：让多个 Agent 不再重复读项目

> 本文首发于知乎「Agent 工坊」专栏，记录我在自己的自动化项目里用 `AGENT.md` + 记忆文件解决"每个 Agent 都要从头认识项目"这个问题的真实做法。

## 一、问题：Agent 换一次，认知就清零一次

我手上有个项目，专门做知乎和公众号的自动发文——写文案、配图、发布、定时任务，一整条流水线。这个项目不是我一个人从头写到尾的，中间换过好几个 Agent 接手：有的负责写脚本，有的负责排查线上发布失败，有的负责改文案生成的 prompt。

一开始最烦的事情是：**每换一个 Agent，它都得重新问一遍项目结构。**

- 想法草稿放在哪，文章草稿放在哪，两套目录是不是一回事；
- 发布状态是靠文件存在与否判断，还是靠里面的字段；
- 为什么同一篇文章要分别看知乎和公众号两个标记文件才算真正发完；
- 登录态、cookie、token 这些东西能不能删、能不能重建。

这些问题不是什么高深的技术难题，但每次都要靠翻代码、翻日志现场推理一遍，效率很低，而且**推理过程本身就可能出错**——比如我之前遇到过，一个 Agent 没搞清楚归档逻辑是"两个平台都发完才挪到 published"，误判了一篇文章"没有重新发布"，其实只是它还卡在等公众号那一步。

后来我意识到，这不是某个 Agent 能力不够，而是**项目缺一个"新人手册"**。人类团队招新人会给一份文档过一遍规矩，Agent 接手项目也需要同样的东西，只是这份文档要写成 Agent 能直接读的格式。

## 二、AGENTS.md：把"项目边界"写成 Agent 的第一份入职文档

`AGENTS.md`（也写作 `AGENT.md`）不是我自己发明的格式，它是 2025 年由 OpenAI 提出、后来 OpenAI、Google、Cursor、Factory、Sourcegraph 等联合推动形成的一个开放约定：**在仓库根目录放一个 Markdown 文件，任何 Agent 工具在接手任务前先读它。** 现在 Codex、Cursor、Copilot、Gemini CLI、Aider 等主流工具都已经原生支持读取这个文件，GitHub 上采用这个约定的仓库已经有两万多个。

它要解决的问题很直接：**原本需要在每一次对话里重复交代的规矩，只写一次，让所有 Agent 都读同一份。**

我给自己项目写的 `AGENT.md`，大致分这么几块：

**1. 项目边界——先说清楚"东西都在哪"**

```markdown
## 项目边界

- 项目根目录：`/path/to/project`
- 主要配置：`config.yaml`
- 想法草稿：`data/pending/`
- 想法归档：`data/published/`
- 文章待发布目录：`docs/pending/`
- 文章已发布目录：`docs/published/`
- 登录态、密钥、发布标记都可能影响线上发布，不要随意删除或重建。
```

这一段看起来简单，但价值很大：新接手的 Agent 不用再去猜"pending 和 published 是不是同一套逻辑"，也不会因为看到一个登录态文件就顺手把它删了重建——**它知道这类文件是有代价的，删错了要重新扫码登录**。

**2. 开发原则——划清"能改"和"不能碰"的边界**

```markdown
## 开发原则

- 优先沿用现有脚本、目录结构和命名方式，不要引入新的发布流程。
- 不要回滚用户或其他 agent 已经产生的改动，除非用户明确要求。
- 不要把 API key、cookie、storage state、token 等敏感信息写进文章、日志或提交说明。
- 需要执行真实发布、联网请求、登录态刷新、删除标记文件等动作时，先确认用户意图是否明确。
```

这段本质是把"高风险操作先确认"这条规矩固化下来。之前我们排查过一次公众号发布失败，原因是登录态过期，如果 Agent 没有"先问过用户"的意识，直接尝试自己重建登录态或者删掉旧文件，反而可能把可用的信息搞丢。写进文档里，就不用每次都靠临场判断。

**3. 常用命令——省掉"猜怎么跑"的过程**

```markdown
## 常用命令

./venv/bin/python scripts/generate_drafts.py
./venv/bin/python scripts/publish_articles.py
./venv/bin/python scripts/publish_wechat_articles.py --dry-run
```

Agent 不需要再去翻 `scripts/` 目录猜哪个脚本对应哪个功能，直接照抄命令就能跑通最常见的场景，还顺手把 dry-run 这种"先验证不发布"的习惯也传递下去了。

**4. 排查路径——把"踩过的坑"提前标好**

```markdown
## 发布状态排查

- 文章发布状态优先看：
  - `docs/pending/`
  - `docs/published/*.meta.json`
  - `docs/published/*.wechat.meta.json`
  - `debug/wechat_article_*`
- 如果用户说公众号或知乎看不到某篇文章，不要只看 Markdown 是否存在，
  要同时检查对应平台的 meta 标记和发布日志。
```

这条是我们真实踩过坑之后补进去的：一篇文章的 Markdown 文件还在 `pending` 目录，不代表它没发布成功，可能只是"知乎发了、公众号没发"，卡在归档条件上。这种系统特有的"反直觉"逻辑，正是最值得写进文档的内容——因为它没法靠常识猜出来，只能靠踩过一次坑之后记下来。

## 三、AGENTS.md 管不住的东西：变化的历史

`AGENTS.md` 解决的是"规矩"层面的问题——这些内容相对稳定，项目结构不大改就不用频繁更新。但项目跑起来之后，会不断产生**新的、动态的信息**：

- 上一次某个功能改坏了，后来怎么修的；
- 某个第三方登录态大概多久失效一次；
- 某次发布踩过的一个诡异 bug，最后定位到是网络瞬时抖动，不是代码问题；
- 当前书籍池读到哪一本、哪一章了。

这些东西不适合塞进 `AGENTS.md`，因为它们不是"规矩"，是"历史"，而且会一直变。这时候就需要第二份文件，通常叫 `memory.md`（或者 `CONTEXT.md`、`STATE.md`，叫法不完全统一，但作用一致）：**一份持续追加、记录项目运行状态和踩坑历史的滚动笔记**。

这个思路在做长周期任务的 Agent 系统里已经比较普遍：Agent 本身是无状态的，一次对话结束，这次积累的上下文就没了；如果不主动把关键信息写到文件里，下一个 Agent（甚至是同一个 Agent 的下一次会话）就得重新靠翻日志、翻代码去"重新发现"一遍。`memory.md` 就是把这次发现的结果固化下来，变成下一个 Agent 的起点。

拿我自己的项目举例，如果补一份 `memory.md`，大概会长这样：

```markdown
# memory.md（持续更新，最新的写在最上面）

## 2026-07-24
公众号发布偶发 `net::ERR_NETWORK_CHANGED`，
排查后确认不是登录态问题（登录态仍有效），
是脚本运行瞬间本机网络抖动导致，重跑一次即可恢复。
遇到这个报错不需要先怀疑登录态，先重跑。

## 2026-07-23
公众号定时任务连续两天在 08:00 报登录态失效
（RuntimeError: 微信公众号登录态失效）。
根因是 `data/auth/wechat_mp_state.json` 过期。
需要人工扫码刷新，Agent 无法代替完成这一步。

## 2026-07-14
themes 模式生成的想法偏抽象、脱离生活场景。
调整了 SYSTEM_PROMPT，要求必须从具体日常场景切入，
避免"觉醒""内在力量"这类空泛大词。
```

这份文件解决的问题和 `AGENTS.md`不一样：它不是告诉 Agent "项目规则是什么"，而是告诉 Agent "**上一次到底发生了什么，别再把同一个坑当成新问题去分析一遍**"。如果没有这份记录，下一次公众号又报登录态相关的错误，接手的 Agent 很可能要重新走一遍"看日志→查代码→定位到底是登录态还是网络"的排查过程，即使这个问题三天前已经有明确结论了。

## 四、两份文件怎么配合，而不是重复劳动

实践下来，我给自己的分工原则很简单：

- **`AGENTS.md` 回答"这个项目是怎么运作的"**——目录结构、开发原则、常用命令、风险操作。内容偏静态，改动不频繁，主要在项目结构发生实质变化时才更新。
- **`memory.md` 回答"最近发生了什么、踩过什么坑"**——按时间顺序追加，新记录写在最上面方便快速看到最新情况，旧记录不删，允许文件慢慢变长。

具体使用上，我会要求接手任务的 Agent 遵守这么几条：

1. **开始任务前，先读 `AGENTS.md` 确认边界，再读 `memory.md` 看最近的历史**，而不是直接去翻代码猜。
2. **排查问题、修复 bug、遇到反直觉的系统行为之后，主动往 `memory.md` 追加一条记录**，哪怕这次任务本身已经做完了。这一步很容易被跳过，但恰恰是这份文件真正有价值的地方——记录不是为了这次任务本身，是为了下一次。
3. **`AGENTS.md` 只有在项目结构、核心流程发生变化时才更新**，不要把一次性的踩坑记录也写进去，否则这份文件会越写越臃肿，失去"新人一次读完"的作用。

这套分工下来，效果是：新接手的 Agent 不用再靠现场推理去理解"为什么一篇文章的 Markdown 还在 pending 目录里但已经发布成功了"，也不用重新怀疑"登录态又失效了吗"——这些都已经在 `memory.md` 里写明白了。它们不再是需要重新排查的谜题，而是可以直接复用的已知结论。

## 五、几个经验

1. **`AGENTS.md` 写"不变的规矩"，`memory.md` 写"会变的历史"**，两者职责不要混在一起，否则前者会被踩坑记录淹没，后者又缺乏结构变成流水账。
2. **踩坑之后顺手记一笔，比事后专门抽时间补文档更可持续。** 排查完一个问题就在当次任务里把结论追加进 `memory.md`，成本很低；指望"回头统一补文档"，大概率不会发生。
3. **反直觉的系统行为最值得写进文档**，比如"文件还在 pending 不代表没发布成功"——这类内容没法靠常识或代码风格猜出来，只能靠明确记录下来。
4. **文档是写给下一个 Agent（也包括未来的自己）看的，不是写给这一次任务看的。** 判断一条信息是否该记下来，标准是"如果三天后另一个 Agent 遇到同样情况，这条记录能不能帮它跳过重新排查的过程"。
