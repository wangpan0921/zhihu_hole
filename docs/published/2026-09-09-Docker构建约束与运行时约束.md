# Docker 构建约束与运行时约束：如何禁止容器私下安装已有依赖

这次直接用我项目里的 Dockerfile 片段说明两个变量：

```dockerfile
ARG PIP_CONSTRAINT=/tmp/pip-constraints-default.txt
ENV PIP_CONSTRAINT=/etc/pip-constraints-runtime.txt
```

这两行看起来都在设置 `PIP_CONSTRAINT`，但作用域完全不同：前者服务于镜像构建过程，后者写入最终镜像，服务于容器运行过程。它们解决的是“pip 使用哪份约束文件”，不是“谁有权修改 Python 环境”。

于是会产生一个直觉：镜像运行起来以后，用户再执行 `pip install`，应该也会自动遵守构建阶段的约束，甚至不能重新安装镜像里已经存在的包。

这个直觉只对了一半。约束文件是 pip 解析依赖时的输入，不是写入镜像后的访问控制策略。要实现“构建时怎么装，运行时就必须保持什么状态”，需要把依赖约束和容器权限一起设计。

## 一、先分清三个时间点

### 1. 构建时：解析并写入镜像

在 `docker build` 阶段，`ARG PIP_CONSTRAINT=/tmp/pip-constraints-default.txt` 定义一个构建参数。只要 Dockerfile 后续的安装命令调用 pip，pip 就可以通过这个变量找到默认约束文件：

```dockerfile
ARG PIP_CONSTRAINT=/tmp/pip-constraints-default.txt
COPY pip-constraints-default.txt /tmp/pip-constraints-default.txt
RUN pip install project-package==1.8.0
```

等价的构建命令是：

```bash
docker build \
  --build-arg PIP_CONSTRAINT=/tmp/pip-constraints-default.txt \
  -t project-package:build-20260909 .
```

这里的 `ARG` 只存在于构建阶段。它不会自动出现在 `docker inspect` 的容器环境中，也不会因为写了默认值就把文件复制进镜像。文件仍然必须通过 `COPY`、构建脚本或基础镜像实际放到该路径；否则 pip 会因为约束文件不存在而失败。

`PIP_CONSTRAINT` 对当前 pip 进程及其子进程生效。它相当于让构建脚本隐式带上约束文件，避免每个安装命令重复声明约束文件。约束文件中的包不会单独触发安装，只有依赖解析需要某个包时，约束才会限制该包的版本。

构建完成后，真正写入镜像的是 `site-packages` 中的文件、脚本和元数据，而不是 pip 的那次命令。镜像里不会自动保存“以后所有 pip 命令都必须读取这份约束文件”这个规则。

### 2. 启动时：读取镜像中的文件

容器启动后，Python 直接使用镜像中已经存在的包。此时不会重新解析依赖，也不会重新读取 `/tmp/pip-constraints-default.txt`。

如果只是启动应用，构建阶段的约束已经体现在实际文件上；但如果用户在容器中执行：

```bash
pip install requests==2.28.0
```

pip 可能会把镜像中的 `requests` 替换成另一个版本。正在运行的容器有一个可写层，这次修改通常不会回写原始镜像，却会影响该容器后续的进程和请求。

### 3. 运行时再次安装：是新的变更操作

运行时安装不是“使用镜像”，而是在修改容器状态。它可能造成：

- 同一个包被升级或降级，覆盖镜像里的文件；
- 新旧包的依赖关系不再满足，`pip check` 报错；
- 只在当前容器生效，重建或替换容器后又消失；
- 通过 `--user`、虚拟环境或 `--target` 绕开系统 `site-packages`；
- 产生无法审计的线上差异，即“镜像测试通过、容器现场却不是这个环境”。

因此，“构建约束”和“运行时禁止变更”是两个不同问题。

## 二、`ARG` 与 `ENV` 的交接关系

运行时对应的是：

```dockerfile
COPY pip-constraints-runtime.txt /etc/pip-constraints-runtime.txt
ENV PIP_CONSTRAINT=/etc/pip-constraints-runtime.txt
```

`ENV` 会被写入镜像配置。容器启动时，应用进程、`docker exec` 启动的普通命令以及它们的子进程都能看到这个变量。因此运行时执行：

```bash
pip install new-plugin==3.2.1
```

会默认使用 `/etc/pip-constraints-runtime.txt`，而不是构建阶段的 `/tmp/pip-constraints-default.txt`。

两份文件可以相同，也可以有意不同。常见设计是：构建约束文件包含编译工具和完整依赖树的版本边界；运行时约束文件只保留生产环境允许使用的版本边界，或者额外限制插件生态。关键是把运行时文件复制进最终镜像，并在发布前检查其内容和权限。

如果你的目标是“运行环境必须与构建结果一致”，不要让这两份文件各自独立维护。可以在构建阶段直接复制同一份文件：

```dockerfile
COPY pip-constraints-default.txt /tmp/pip-constraints-default.txt
RUN cp /tmp/pip-constraints-default.txt /etc/pip-constraints-runtime.txt
ENV PIP_CONSTRAINT=/etc/pip-constraints-runtime.txt
```

如果运行时约束文件必须由其他流程生成，则应在 CI 中对两份文件做规范化后的差异检查；只要同一个包在两份文件中的版本不同，镜像就不应发布。

如果在同一个 Dockerfile 阶段同时写了：

```dockerfile
ARG PIP_CONSTRAINT_BUILD=/tmp/pip-constraints-default.txt
ENV PIP_CONSTRAINT=/etc/pip-constraints-runtime.txt
RUN echo "$PIP_CONSTRAINT"
```

这条 `RUN` 看到的是 `ENV` 的值。也就是说，后出现的 `ENV` 会成为后续构建步骤和最终容器的环境值；`ARG` 的默认值不会自动覆盖它。需要在构建期明确使用默认文件时，应在命令中临时指定：

```dockerfile
RUN PIP_CONSTRAINT="$PIP_CONSTRAINT_BUILD" pip install project-package==1.8.0
```

更清晰的写法是分阶段命名，避免同名变量在阅读时产生歧义：

```dockerfile
ARG PIP_CONSTRAINT_BUILD=/tmp/pip-constraints-default.txt
ENV PIP_CONSTRAINT=/etc/pip-constraints-runtime.txt
```

### 构建参数不会自动成为运行时变量

不要把下面两件事混为一谈：

- `ARG`：构建时参数，可被 `docker build --build-arg` 覆盖，默认不保留在运行时环境；
- `ENV`：镜像和容器环境变量，默认会在运行时继续存在。

如果构建阶段只写了 `ARG PIP_CONSTRAINT=...`，而没有 `ENV PIP_CONSTRAINT=...`，容器启动后执行 pip 就不会继承这个约束。反过来，只有 `ENV` 也可以约束构建步骤，但它会把运行时路径一起写入镜像，必须确保该路径在构建时已经存在。

## 三、版本一致不等于禁止重复安装

在同一个 Python 环境、同一个 `site-packages` 路径中，pip 通常不会保留两个可独立选择的同名版本。再次执行安装时，常见结果是：满足要求则跳过，不满足要求则卸载旧版本文件并写入新版本文件。

真正容易被忽略的是另一条路径。例如用户执行 `pip install --target /tmp/extra requests`，或者在 `/tmp/venv` 创建虚拟环境，就能得到第二份包。只要调整 `PYTHONPATH` 或解释器，应用就可能优先导入这份包。因此“不能重复安装”不能只理解成禁止某一条 `pip install` 命令，而应理解成禁止未经批准的依赖目录和导入路径发生变化。

## 四、让运行时 pip 使用项目规定的约束文件

项目的运行时约束文件需要显式复制到最终镜像，并通过 `ENV` 暴露给容器内的 pip：

```dockerfile
COPY pip-constraints-runtime.txt /etc/pip-constraints-runtime.txt
ENV PIP_CONSTRAINT=/etc/pip-constraints-runtime.txt
```

之后，在没有额外参数的情况下，pip 会把 `PIP_CONSTRAINT` 当作约束文件：

```bash
pip install new-plugin==3.2.1
```

这可以减少遗漏运行时约束的情况，但它不是安全边界。用户可以执行 `env -u PIP_CONSTRAINT ...`，使用 pip 的 `--isolated` 模式，或者使用 `--no-deps`、`--target`、虚拟环境等方式改变安装行为。环境变量也不能阻止用户安装镜像中已经存在的包。

如果运行时安装是受控流程，建议同时使用哈希校验：

```text
# runtime-requirements.txt
new-plugin==3.2.1 \
    --hash=sha256:<approved-wheel-sha256>
```

安装时只允许读取这份审核过的文件：

```bash
pip install --require-hashes -r runtime-requirements.txt
```

哈希校验解决的是“下载到的文件是不是批准过的文件”，不解决“谁有权执行安装”。

## 五、真正禁止私下安装，需要分层控制

### 1. 以非 root 用户运行

Dockerfile 中创建专用用户，并让应用默认使用它：

```dockerfile
RUN groupadd --system app \
 && useradd --system --gid app --create-home app
USER app
```

同时确保 Python 环境目录归 root 所有且不可写：

```dockerfile
RUN chown -R root:root /opt/venv \
 && chmod -R a-w /opt/venv
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONDONTWRITEBYTECODE=1
```

这样，普通用户执行 `pip install` 时会因目标目录没有写权限而失败。`PYTHONDONTWRITEBYTECODE=1` 用于避免 Python 尝试在只读依赖目录中生成 `.pyc` 文件。

### 2. 运行时使用只读根文件系统

启动容器时再加一层文件系统保护：

```bash
docker run --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --cap-drop=ALL \
  --security-opt=no-new-privileges \
  --user 10001:10001 \
  my-app:1.0
```

`--read-only` 会让容器根文件系统不可写，`/tmp` 等确实需要写入的位置用临时文件系统单独提供。pip 即使找到下载源，也无法把文件写入镜像中的 Python 环境。

在 Kubernetes 中，对应的配置通常是：

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]
```

### 3. 运行镜像可以不带安装工具

推荐使用多阶段构建：在 builder 阶段安装依赖，在 runtime 阶段只复制虚拟环境和应用文件。生产镜像可以删除 `pip`、编译器、头文件和包管理器，减少“现场修包”的入口。

```dockerfile
FROM python:3.12-slim AS builder
RUN python -m venv /opt/venv
ARG PIP_CONSTRAINT_BUILD=/tmp/pip-constraints-default.txt
COPY pip-constraints-default.txt /tmp/pip-constraints-default.txt
RUN PIP_CONSTRAINT="$PIP_CONSTRAINT_BUILD" \
    /opt/venv/bin/pip install --no-cache-dir \
    project-package==1.8.0 \
 && /opt/venv/bin/pip check \
 && /opt/venv/bin/pip freeze --all > /tmp/installed.txt

FROM python:3.12-slim AS runtime
COPY --from=builder /opt/venv /opt/venv
COPY . /opt/app
COPY --from=builder /tmp/installed.txt /opt/app/installed.txt
COPY pip-constraints-runtime.txt /etc/pip-constraints-runtime.txt
ENV PATH="/opt/venv/bin:$PATH" \
    PIP_CONSTRAINT=/etc/pip-constraints-runtime.txt \
    PYTHONDONTWRITEBYTECODE=1
WORKDIR /opt/app
USER 10001:10001
ENTRYPOINT ["python", "-m", "app"]
```

是否删除 `pip` 要结合运维方式决定：如果生产环境明确禁止运行时安装，可以在 runtime 阶段移除它；如果保留它用于诊断，也必须依赖非 root、只读文件系统和执行权限控制，而不能把 `PIP_CONSTRAINT` 当作强制机制。

### 4. 控制进入容器的方式和网络出口

不给业务用户随意 `docker exec` 的权限，不在生产容器中提供交互式 shell，是比修改 shell 命令更可靠的控制。还可以限制容器访问 PyPI 或内部包源的网络出口，避免运行时下载新包。

但网络限制只是补充：用户仍可能从已挂载的目录、内网制品或自带 wheel 安装。因此核心仍然是“不可写的依赖目录 + 非特权身份”。

## 六、用启动审计发现漂移

权限控制解决“不能改”，审计解决“改过没有”。构建阶段可以保存已验证的版本清单：

```dockerfile
RUN /opt/venv/bin/pip freeze --all > /opt/app/installed.txt
```

入口脚本启动前执行：

```bash
python -m pip check
python -m app.verify_environment --manifest /opt/app/installed.txt
exec python -m app
```

`verify_environment` 可以通过 `importlib.metadata` 读取当前环境的发行包版本，与清单逐项比较；对更严格的场景，还可以校验每个发行包的 `RECORD` 文件或整个虚拟环境的镜像摘要。发现版本缺失、增加或不一致时直接退出，让问题在健康检查和日志中暴露，而不是等到业务请求才出现。

审计脚本不能替代权限控制，因为它发生在变更之后；它的价值是阻止“漂移后的容器继续承接流量”。

## 七、一个容易混淆的边界

如果用户拥有宿主机上的 Docker daemon 权限，或者能以 root 启动容器，那么他可以：

```bash
docker run --user root -it my-app:1.0 sh
docker commit <container> my-app:modified
```

这类用户本质上拥有修改容器和重新制作镜像的能力，不能靠镜像内的约束文件、`ENTRYPOINT` 或删除 `pip` 彻底阻止。此时应该在平台层回收 daemon、集群 exec、镜像推送等权限，并通过签名镜像、准入策略和 CI 重新构建来保证来源可信。

## 八、推荐的落地方案

对于“镜像已经包含一套依赖，运行时禁止用户私下重复安装”的场景，可以采用下面的基线：

1. 构建阶段使用锁定的直接依赖和完整约束，执行 `pip check`，生成版本清单。
2. 将 `/etc/pip-constraints-runtime.txt` 固化在镜像中，并设置 `ENV PIP_CONSTRAINT=/etc/pip-constraints-runtime.txt`，为受控的运行时安装提供一致边界。
3. 生产进程使用非 root 用户，依赖目录归 root 所有且不可写。
4. 以 `--read-only` 或 `readOnlyRootFilesystem` 运行，只给必要目录挂载可写临时空间。
5. 生产镜像移除 pip 和编译工具，禁止无审计的 `docker exec`，按需限制包源网络出口。
6. 启动时执行依赖清单审计；需要新包时修改源码依赖文件，重新构建、测试、签名并发布新镜像。

一句话总结：`ARG PIP_CONSTRAINT=/tmp/pip-constraints-default.txt` 让构建阶段使用默认约束，`ENV PIP_CONSTRAINT=/etc/pip-constraints-runtime.txt` 让运行阶段继承运行时约束；但两者都不能单独禁止安装，真正的阻断仍依赖不可写的依赖目录、非特权身份和平台权限控制。
