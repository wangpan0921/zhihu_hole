# 从 Notebook 调试到离线作业：数据工场基本使用实践

在数据工场中开发一个每天自动运行的数据任务，通常不会一开始就创建正式调度。更稳妥的流程是：先把已有代码放进 Notebook 中调试，确认运行环境、权限、参数和输出结果都没有问题，再将代码配置为离线作业，最后设置每天自动执行。

本文以“根据部门组织架构同步人员和组名到组内私有表”为背景，但不展开人员匹配、部门关联等业务逻辑，重点记录 Notebook 和离线作业的基本用法，以及从调试到上线时容易忽略的事项。

## 一、先理解两个核心概念

### 1. Notebook：交互式开发环境

Notebook 是数据工场提供的交互式开发环境。代码通常被拆成多个单元格，可以逐段执行并立即查看结果。它适合做以下事情：

- 查看源表结构和样例数据
- 验证已有 SQL 或脚本能否运行
- 分步骤观察中间结果
- 排查字段、权限、参数和资源问题
- 对一小段数据做临时分析

Notebook 更像开发阶段的工作台。它保存的是代码和分析过程，但不天然等同于生产任务。

### 2. 离线作业：批量和定时执行单元

离线作业用于运行已经验证过的数据处理逻辑。它通常具备以下能力：

- 按天、按小时或按其他周期调度
- 使用业务日期等运行参数
- 配置输入、输出和上下游依赖
- 设置计算资源、超时时间和失败重试
- 生成每次运行的实例和日志
- 配置失败、延迟或数据异常告警

离线作业的目标不是方便试错，而是让任务在无人值守的情况下稳定运行。

### 3. Notebook 和离线作业的关系

两者不是互相替代的工具，而是同一条开发链路中的两个阶段：

| 对比项 | Notebook | 离线作业 |
| --- | --- | --- |
| 主要用途 | 开发、调试、验证 | 生产运行、定时调度 |
| 执行方式 | 手动执行代码单元 | 按计划自动执行 |
| 结果查看 | 直接查看单元格输出 | 查看实例、日志和目标数据 |
| 参数方式 | 可临时修改 | 使用调度系统传入的参数 |
| 运行状态 | 依赖当前会话 | 每次运行生成独立实例 |
| 适用阶段 | 开发测试 | 发布上线 |

可以简单理解为：Notebook 解决“这段代码能不能正确运行”，离线作业解决“这段代码能不能每天稳定运行”。

## 二、使用 Notebook 调试已有代码

假设人员同步代码已经准备好，现在只需要在数据工场中验证它并准备上线。

### 1. 创建 Notebook

创建 Notebook 时，通常需要选择以下内容：

- 所属项目或工作空间
- 使用的语言，例如 SQL、Python 或 PySpark
- 计算引擎
- 运行资源，包括 CPU、内存和实例数量
- 数据源或数据库连接
- 执行身份和相关权限
- 依赖包、初始化脚本或资源文件

这些配置决定了代码在哪个环境中执行。尤其要确认 Notebook 连接的是测试环境还是生产环境，避免调试时误写正式表。

不同版本的数据工场在页面上可能使用不同名称，例如“内核”“集群”“实例规格”或“资源组”，但含义基本相同。

### 2. 将代码放入 Notebook

可以将已有代码复制到 Notebook，也可以从代码仓库或历史文件导入。建议不要把所有内容放在一个单元格中，而是按执行阶段拆分：

1. 初始化环境和参数
2. 读取源数据
3. 执行业务处理逻辑
4. 查看中间结果
5. 写入测试表或目标表
6. 执行结果检查

这样做的好处是，出错时可以迅速定位是读取、处理还是写入阶段出了问题，也方便只重新执行某一个阶段。

### 3. 逐步执行和查看结果

Notebook 的基本操作包括：

- 执行当前单元格
- 按顺序执行多个单元格
- 中断正在运行的单元格
- 重新执行某个单元格
- 重启运行环境
- 清理变量、缓存和临时结果

调试时建议先使用一个业务日期和少量数据验证代码是否能够运行，再逐步扩大范围。查看结果时，重点关注字段是否齐全、数据量是否合理、写入分区是否正确。

需要注意，单元格可以被单独执行，实际执行顺序不一定等于页面顺序。如果后面的代码依赖前面定义的变量，而前置单元格没有执行，就会出现“代码看起来正确但运行失败”的情况。重启运行环境后，之前的变量和会话状态也会全部消失。

### 4. 调试阶段重点检查什么

由于业务逻辑已经写好，调试重点应放在运行条件和结果验证上：

- 当前项目、数据库和表名是否正确
- Notebook 使用的身份是否有源表读取权限
- 是否有目标表写入权限
- 日期、环境等参数是否传入正确
- 代码依赖的包是否已经安装
- 目标表是否误用了生产表
- 计算资源是否足够
- 运行是否超时或扫描了过多数据
- 重复执行是否会产生重复结果

如果平台提供“预览”“校验”或“血缘”功能，也可以在运行前确认输入和输出对象。

### 5. 测试写入和正式写入要分开

调试阶段建议使用测试表、临时表或测试分区。先查看处理结果，确认无误后再验证写入动作。不要为了方便直接对生产表执行覆盖或删除操作。

如果必须连接正式数据源，至少要做到：

- 先限制业务日期或数据范围
- 先执行查询，不直接执行写入
- 明确当前使用的账号和环境
- 检查写入语句的覆盖、追加行为

### 6. 判断 Notebook 调试是否完成

准备迁移到离线作业前，建议确认以下事项：

- 代码可以完整执行并正常结束
- 输入和输出对象已经确认
- 关键结果符合预期
- 日期参数可以替换，不依赖硬编码日期
- 任务可以安全重跑
- 权限和资源配置满足要求
- 已清理不需要的临时表和调试代码

## 三、将 Notebook 代码配置为离线作业

### 1. 创建离线作业

在数据工场中创建离线作业时，通常需要设置：

- 作业名称和所属项目
- 作业类型，例如 SQL、Shell、Python 或 Spark
- 执行代码或脚本位置
- 运行环境和执行身份
- 计算资源和队列

离线作业是独立的运行实体。它不会自动继承 Notebook 当前会话里的变量、缓存或临时状态，因此代码需要具备独立运行的条件。

![离线作业](../新建作业.png)

### 2. 迁移代码时要做的调整

将 Notebook 中验证通过的代码复制到离线作业后，建议逐项检查：

- 删除仅用于调试的输出和临时代码
- 补齐 Notebook 中隐式依赖的初始化内容
- 将手工填写的日期改成调度参数
- 检查输入和输出表是否指向正确环境
- 确认依赖包在离线运行环境中可用
- 确认写入方式支持失败后重跑

Notebook 中能运行，不代表离线作业一定能运行。最常见的差异来自执行身份、数据源配置、依赖包和资源规格。

### 3. 使用调度参数

Notebook 调试时可能直接写入某个日期，例如使用固定的测试日期。生产任务应改为由调度系统传入业务日期、运行日期或分区值。

参数化的好处是：

- 每天自动处理当天数据
- 可以手工指定历史日期补数
- 不需要每天修改代码
- 运行实例中的参数更容易追溯

不同平台的参数占位符语法可能不同，应以当前数据工场的实际配置为准。上线前应在实例详情或日志中确认参数确实被替换成了预期值。


### 4. 配置输入、输出和幂等行为

离线作业需要明确：

- 从哪些表或路径读取数据
- 向哪个表或路径写入数据
- 使用哪个业务日期或分区
- 采用覆盖还是追加方式
- 是否需要临时表

每天任务都可能因为资源、上游延迟或网络问题失败，因此必须考虑重跑。常见做法是按分区覆盖、使用唯一键去重，或先写临时结果再替换正式结果。核心目标是：同一个业务日期重复运行，不会产生重复数据或半成品数据。

### 5. 配置资源和超时

根据任务数据量设置 CPU、内存、实例数量和并发数，并配置合理的超时时间和重试次数。首次从 Notebook 迁移到离线作业时，不要只看“是否成功”，还要观察实际耗时和资源使用情况。

## 四、设置每天自动运行

![作业配置](../作业配置.png)

### 1. 配置调度周期

常见配置包括：

- 每天执行一次
- 指定执行时间
- 设置生效日期和时区
- 设置最大并发数
- 是否允许手工补数

执行时间应避开源数据尚未准备完成的时间。如果源表由其他任务生成，优先配置任务依赖，而不是简单地把当前任务延后几十分钟。

### 2. 配置上下游依赖

人员同步任务通常需要等待组织架构或人员数据同步完成。可以将依赖关系配置为：

```text
组织架构数据准备
        ↓
人员组关系同步
        ↓
下游查询或权限消费
```

只有上游成功，当前任务才开始；当前任务失败时，也不应让依赖其结果的下游继续运行。

### 3. 配置重试和告警

建议配置：

- 失败自动重试 1～3 次
- 执行超时告警
- 上游延迟告警
- 任务失败通知负责人或群组
- 必要时增加结果数量异常告警

重试可以处理临时性故障，但不能替代错误排查。对于权限错误、字段错误等确定性错误，重复重试通常没有意义。

### 4. 提交、审核和发布

数据工场通常会区分保存、提交、审核、发布和启用调度等操作。一个常见流程是：

```text
Notebook 调试
    ↓
创建离线作业
    ↓
手工试运行
    ↓
检查实例和结果
    ↓
提交审核
    ↓
发布到生产
    ↓
启用每天调度
```

“保存代码”不一定代表线上任务已经更新。上线后应确认作业版本、运行环境和调度状态都已经切换到生产配置。

## 五、运行监控和问题排查

### 1. 查看任务实例

每天运行后，主要查看：

- 实例状态
- 业务日期
- 开始和结束时间
- 执行耗时
- 重试次数
- 上下游依赖状态

实例是一次具体运行的记录。同一个离线作业每天会产生不同实例，排查问题时要先定位到正确的业务日期。

![实例](../生产实例.png)

### 2. 查看日志

任务失败时，建议按以下顺序查看：

1. 任务状态和失败阶段
2. 错误日志中的第一条异常
3. 业务日期和分区参数
4. 源数据是否已经生成
5. 执行身份和表权限
6. 资源使用、数据量和超时信息

不要只看日志最后一行。有些平台会在最后显示任务失败，但真正原因出现在更早的位置。

![看日志](../看日志.png)

### 3. 常见问题

**Notebook 能运行，离线作业失败**

常见原因是执行身份不同、依赖包没有安装、参数没有替换，或者离线作业的资源配置较小。

**任务成功，但结果日期不对**

重点检查调度参数、输入分区和时区。任务的运行日期不一定等于要处理的业务日期。

**重跑后出现重复数据**

重点检查写入方式是否为追加，以及是否缺少分区覆盖或去重处理。

**任务运行很慢或超时**

重点检查是否扫描了不必要的数据、是否使用了分区条件、是否存在数据倾斜，以及资源规格是否合理。

### 4. 重跑和补数

当天失败时，可以先修复问题，再重跑当前实例。需要补历史数据时，指定业务日期范围运行，并确认：

- 上游历史数据仍然存在
- 补数不会和正常调度并发
- 重跑不会产生重复数据
- 补数完成后下游结果需要同步检查

## 六、推荐的使用规范

### Notebook 阶段

- 使用测试环境、临时表或测试分区
- 先小范围运行，再扩大数据范围
- 把代码拆成容易定位问题的多个单元格
- 记录参数、运行时间和调试结论
- 不依赖未执行的前置单元格
- 不在日志和输出中暴露不必要的人员信息

### 离线作业阶段

- 使用参数替代固定日期和路径
- 明确输入、输出和分区
- 配置显式的上下游依赖
- 保证同一日期可以安全重跑
- 设置超时、重试和告警
- 发布前先手工试跑
- 保留版本、审核和发布记录

### 涉及私有表时

- 只授予任务必要的读写权限
- Notebook 和离线作业分别确认执行身份
- 不把真实用户名数据复制到个人文件或公开日志
- 测试表和生产表分开管理
- 对离职人员、外包人员等特殊账号按组织规范处理

- [ ] 数据源连接正常

### 离线作业配置

- [ ] 作业代码已迁移
- [ ] 固定日期已改成调度参数
- [ ] 输入、输出和写入方式已配置

- [ ] 失败告警可以正常收到
- [ ] 下游任务运行正常

## 八、总结

数据工场中的 Notebook 和离线作业分别承担开发和生产两个阶段的职责。Notebook 适合打开已有代码、逐段执行、查看结果和定位问题；离线作业则负责把验证通过的代码参数化，配置资源、依赖、重试和告警，并按每天的计划自动运行。

对于人员组关系同步这类任务，推荐的落地流程是：先在 Notebook 中确认运行环境和结果，再创建离线作业进行手工试跑，最后发布并启用每日调度。后续维护时，重点关注实例日志、业务日期、数据分区、权限、幂等性和告警状态。
