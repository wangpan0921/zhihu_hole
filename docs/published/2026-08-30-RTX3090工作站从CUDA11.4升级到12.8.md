# RTX 3090 工作站从 CUDA 11.4 升级到 12.8：Ubuntu 完整实战教程

在 RTX 3090 工作站上执行 `nvidia-smi`，如果看到：

```text
CUDA Version: 11.4
```

很多人的第一反应是“卸载 CUDA 11.4，再安装一个新版本”。这一步很容易把显卡驱动、CUDA Toolkit 和 Python 环境混在一起，最后出现 `nvidia-smi` 失效、`nvcc` 仍指向旧版本，或者 PyTorch 突然找不到 GPU。

更稳妥的升级顺序是：

```text
记录现状
  -> 确认项目需要的 CUDA 版本
  -> 添加 NVIDIA 官方软件源
  -> 先升级驱动并重启验证
  -> 并行安装新 Toolkit
  -> 验证 CUDA 程序和深度学习框架
  -> 最后再决定是否删除旧 Toolkit
```

本文以 **Ubuntu 20.04、22.04 或 24.04 的 x86_64 工作站**为例，将目标版本定为 **CUDA Toolkit 12.8**。RTX 3090 属于 Ampere 架构，计算能力为 8.6，可以使用 CUDA 12.8。之所以不直接追逐最新大版本，是因为工作站的目标通常是兼容现有 PyTorch、TensorFlow、自定义算子和容器，而不是让版本号最大。

如果你的项目明确要求 CUDA 12.6、CUDA 13.x 或其他版本，应以项目兼容矩阵为准，并替换本文中的目标版本和驱动下限。

## 一、先分清四个容易混淆的版本

一台深度学习工作站至少涉及四层：

| 层次 | 作用 | 常用检查命令 |
| --- | --- | --- |
| NVIDIA 驱动 | 让操作系统访问 GPU，并提供 CUDA Driver API | `nvidia-smi` |
| CUDA Toolkit | 提供 `nvcc`、头文件、开发库和调试工具 | `nvcc --version` |
| 深度学习框架的 CUDA 构建 | PyTorch、TensorFlow 自带或依赖的用户态 CUDA 运行库 | `torch.version.cuda` |
| 容器内 CUDA 运行库 | 由容器镜像携带，通过宿主机驱动访问 GPU | 查看镜像标签和容器内环境 |

`nvidia-smi` 顶部的 `CUDA Version: 11.4` 主要表示：**当前 NVIDIA 驱动最高支持到 CUDA 11.4 兼容级别。**

它不等于以下任何一项：

- 不代表系统一定安装了 CUDA Toolkit 11.4；
- 不代表 `nvcc` 一定是 11.4；
- 不代表 PyTorch 一定基于 CUDA 11.4 构建；
- 不代表每个 Conda 环境和 Docker 容器都在使用 11.4。

所以，升级前不能只看这一行。

## 二、升级前完整记录现状

驱动升级需要重启。远程操作前应确认 SSH 可以在重启后恢复，最好还能通过物理终端、IPMI 或其他带外方式登录。先停止训练、推理和占用 GPU 的容器，不要在任务运行中替换驱动。

建立一份升级前记录：

```bash
mkdir -p ~/cuda-upgrade-backup

date | tee ~/cuda-upgrade-backup/date.txt
cat /etc/os-release | tee ~/cuda-upgrade-backup/os-release.txt
uname -a | tee ~/cuda-upgrade-backup/uname.txt

nvidia-smi | tee ~/cuda-upgrade-backup/nvidia-smi.txt
nvidia-smi --query-gpu=index,name,uuid,driver_version,memory.total \
  --format=csv | tee ~/cuda-upgrade-backup/gpu.csv

command -v nvcc || true
nvcc --version 2>&1 | tee ~/cuda-upgrade-backup/nvcc.txt
readlink -f /usr/local/cuda 2>&1 | tee ~/cuda-upgrade-backup/cuda-link.txt

gcc --version | head -n 1 | tee ~/cuda-upgrade-backup/gcc.txt
dkms status | tee ~/cuda-upgrade-backup/dkms.txt
dpkg -l | awk '/nvidia|cuda|cudnn|nccl/ {print}' \
  | tee ~/cuda-upgrade-backup/gpu-packages.txt
```

如果当前环境安装了 PyTorch，再记录框架实际看到的版本：

```bash
python3 - <<'PY'
import torch

print("PyTorch:", torch.__version__)
print("PyTorch CUDA build:", torch.version.cuda)
print("CUDA available:", torch.cuda.is_available())
if torch.cuda.is_available():
    print("GPU:", torch.cuda.get_device_name(0))
PY
```

还要检查 shell 中是否写死了旧目录：

```bash
grep -nE 'CUDA_HOME|CUDA_PATH|/usr/local/cuda|LD_LIBRARY_PATH' \
  ~/.bashrc ~/.profile /etc/environment 2>/dev/null
```

如果存在 `/usr/local/cuda-11.4/bin`，升级后需要一起修改，否则新 Toolkit 安装成功，终端仍可能调用旧 `nvcc`。

还要分别确认旧驱动和旧 Toolkit 的安装来源。这是两个独立问题，不能根据 `nvidia-smi` 的来源推断 Toolkit 的来源。

先检查 NVIDIA 驱动：

```bash
dpkg -S /usr/bin/nvidia-smi
command -v nvidia-uninstall || true
test -f /var/log/nvidia-installer.log && echo "发现 NVIDIA runfile 安装日志"
```

如果 `dpkg -S` 返回 `nvidia-utils-xxx: /usr/bin/nvidia-smi`，说明当前 `nvidia-smi` 属于 Deb 软件包，驱动通常由 APT 管理。如果 dpkg 查不到，但存在 `nvidia-uninstall` 和 runfile 安装日志，驱动通常来自 NVIDIA runfile。

再单独检查 CUDA Toolkit：

```bash
command -v nvcc || true
NVCC_PATH=$(command -v nvcc 2>/dev/null || true)
if [ -n "$NVCC_PATH" ]; then
  NVCC_REAL_PATH=$(readlink -f "$NVCC_PATH")
  echo "$NVCC_REAL_PATH"
  dpkg -S "$NVCC_REAL_PATH" 2>/dev/null || echo "nvcc 不属于已登记的 Deb 包"
fi
dpkg -l | grep -E "cuda-(toolkit|compiler|nvcc)"
```

`nvcc` 能被 `dpkg -S` 定位到 CUDA 软件包时，Toolkit 由 APT 管理；如果 `nvcc` 位于 `/usr/local/cuda-11.4/bin` 且 dpkg 查不到，同时存在 `/usr/local/cuda-11.4/bin/cuda-uninstaller`，Toolkit 11.4 通常来自 runfile。找不到 `nvcc` 则可能根本没有安装完整 Toolkit。

NVIDIA 的 CUDA 12.8 兼容表允许不同版本的 runfile Toolkit 与 Deb Toolkit 并存，因此 Toolkit 11.4 不必预先删除。但是，**不要直接用 APT 驱动覆盖 runfile 驱动**。当前驱动如果确定来自 runfile，应在维护窗口停止图形界面和 GPU 任务，使用 runfile 自带的 `nvidia-uninstall` 卸载旧驱动，再安装 `cuda-drivers`。这会让 GPU 暂时不可用，桌面工作站应准备本地 TTY 或带外登录。无法确认驱动来源时应先停下来查清楚，混用两种方式管理同一套驱动容易造成内核模块与用户态库不一致。

## 三、确认 CUDA 12.8 的兼容条件

NVIDIA 官方资料中，GeForce RTX 3090 的计算能力是 8.6，CUDA 12.8 可以为它编译 `sm_86` 代码。

驱动方面需要注意两个数字：

- CUDA 12.x 的小版本兼容机制以 Linux 驱动 525 系列为起点，但存在功能限制；
- CUDA 12.8 GA 在 Linux x86_64 上对应的完整驱动下限是 **570.26**。

工作站升级不建议依赖“勉强可运行”的小版本兼容，本文按 **驱动版本不低于 570.26** 处理。更高版本的驱动通常可以向后运行 CUDA 12.8 程序。

在动手前还应确认：

1. 当前 Ubuntu 版本仍在维护期内；

如果是 Ubuntu 22.04 或 24.04，通常可以继续使用。Ubuntu 20.04 的标准支持已经结束，除非机器启用了 Ubuntu Pro/ESM，否则不建议继续作为新 CUDA 环境的长期基础。
还可以确认 CUDA 12.8 是否提供对应仓库：
```bash
apt-cache policy cuda-toolkit-12-8
```
如果没有 Candidate，说明当前 Ubuntu 版本或软件源不匹配。

2. 业务框架提供与目标 CUDA 兼容的安装包；
3. 自定义 CUDA 扩展支持 CUDA 12.8 和当前 GCC；
4. 旧项目是否必须保留 Toolkit 11.4；
5. 主板是否开启 Secure Boot，以及自己是否能完成 MOK 驱动模块签名确认。

执行：
```bash
mokutil --sb-state
```

如果命令不存在，可以安装：
```bash
sudo apt install mokutil
```

结果解释：
```text
SecureBoot enabled
```
表示开启了 Secure Boot。安装 APT 驱动时，Ubuntu 可能要求设置 MOK 密码；重启后需要在蓝色界面选择 Enroll MOK，输入密码完成注册。
```text
SecureBoot disabled
```
表示没有 Secure Boot 这一层的限制，通常不需要 MOK。
还可以检查 NVIDIA 模块信息：
```bash
modinfo nvidia | grep -Ei 'signer|sig_id'
```

以及内核日志：
```bash
dmesg -T | grep -iE 'secure boot|module verification|lockdown|nvidia'
```

如果只是运行 PyTorch 官方预编译 wheel，并不编译 CUDA 程序或自定义算子，宿主机可能根本不需要完整 Toolkit。此时通常只要驱动足够新，再安装匹配的 PyTorch wheel 即可。

## 四、添加 NVIDIA 官方 CUDA 软件源

下面先根据 Ubuntu 版本生成 NVIDIA 仓库目录名：

```bash
. /etc/os-release

case "$VERSION_ID" in
  20.04) CUDA_REPO_DISTRO=ubuntu2004 ;;
  22.04) CUDA_REPO_DISTRO=ubuntu2204 ;;
  24.04) CUDA_REPO_DISTRO=ubuntu2404 ;;
  *)
    echo "本文命令不支持 Ubuntu $VERSION_ID，请查看 NVIDIA 官方安装指南"
    return 1 2>/dev/null || exit 1
    ;;
esac

echo "$CUDA_REPO_DISTRO"
```

RTX 3090 工作站通常是 x86_64。再确认一次：

```bash
uname -m
```

输出应为 `x86_64`。然后安装 NVIDIA 官方仓库的 keyring：

```bash
cd /tmp
curl -fsSLO "https://developer.download.nvidia.com/compute/cuda/repos/${CUDA_REPO_DISTRO}/x86_64/cuda-keyring_1.1-1_all.deb"
sudo dpkg -i cuda-keyring_1.1-1_all.deb
sudo apt update
```

这里使用 `cuda-keyring` 管理仓库密钥，不要再照搬使用 `apt-key` 的旧教程。

确认目标包可以找到：

```bash
apt-cache policy cuda-toolkit-12-8 cuda-drivers
```

如果 `cuda-toolkit-12-8` 没有 Candidate，先检查：

- `/etc/os-release` 是否与仓库目录匹配；
- CPU 架构是否确实为 x86_64；
- `sudo apt update` 是否有签名、代理或网络错误；
- `/etc/apt/sources.list.d/cuda-*.list` 是否已生成。

## 五、先升级 NVIDIA 驱动

先安装当前内核对应的头文件：

```bash
sudo apt install linux-headers-$(uname -r)
```

查看 `cuda-drivers` 即将安装的版本：

```bash
apt-cache policy cuda-drivers
sudo apt -s install cuda-drivers
```

![升级nvidia驱动](./升级nvidia驱动.png)

模拟安装结果中的 NVIDIA 驱动版本应不低于 570.26。确认无误后执行：

```bash
sudo apt install cuda-drivers
```

![升级nvidia驱动2](./升级nvidia驱动2.png)

安装过程中，如果 Secure Boot 已启用，Ubuntu 可能要求设置一次性 MOK 密码。重启时需要在蓝色界面中选择 `Enroll MOK`，输入刚才的密码，允许 NVIDIA 内核模块加载。跳过这一步可能导致驱动已经安装，但 `nvidia-smi` 仍然报错。

确认没有仍在写盘的任务后重启：

```bash
sudo reboot
```

机器恢复后，先只验证驱动，不急着安装 Toolkit：

```bash
nvidia-smi
nvidia-smi --query-gpu=name,driver_version --format=csv,noheader
lsmod | grep '^nvidia'
dkms status
```

![升级nvidia驱动重启后](./升级nvidia驱动重启后.png)

此时应满足：

- 能识别 `NVIDIA GeForce RTX 3090`；
- Driver Version 不低于 570.26；
- `nvidia-smi` 中的 CUDA Version 已变成 12.x 或更高；
- 没有 `NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver`。

注意，`nvidia-smi` 显示比 12.8 更高的 CUDA Version 并不代表安装错了。它表示新驱动支持更高的 CUDA 兼容级别，不妨碍运行 CUDA 12.8 程序。

## 六、并行安装 CUDA Toolkit 12.8

驱动正常后再安装 Toolkit：

```bash
sudo apt install cuda-toolkit-12-8
```

这里故意使用固定版本包 `cuda-toolkit-12-8`：

- 它安装 CUDA 开发工具，不包含显卡驱动；
- 它不会因为普通软件更新自动跨到下一个 CUDA 小版本；
- NVIDIA 官方支持不同 Toolkit 并行安装。

![安装cuda-toolkit](./安装cuda-toolkit.png)

不建议在需要稳定版本的工作站上直接执行：

```bash
sudo apt install cuda
```

`cuda` 元包会同时引入 Toolkit 和驱动，并跟随新版本升级，变更范围比本教程需要的大。

安装完成后查看目录和 alternatives：

```bash
ls -ld /usr/local/cuda*
update-alternatives --display cuda
```

如果系统同时保留 11.4 和 12.8，可选择默认 Toolkit：

```bash
sudo update-alternatives --config cuda
```

选择指向 `/usr/local/cuda-12.8` 的项目。

![安装cuda-toolkit](./安装cuda-toolkit确认.png)

然后在 `~/.bashrc` 中使用稳定的版本路径：

```bash
export CUDA_HOME=/usr/local/cuda-12.8
export PATH="$CUDA_HOME/bin:$PATH"
```

加载新配置并验证：

```bash
source ~/.bashrc
hash -r

command -v nvcc
readlink -f "$(command -v nvcc)"
nvcc --version
```

期望看到 `release 12.8`。通过 APT 安装时，系统动态链接器通常已经知道 CUDA 库的位置，不要一开始就在全局 `LD_LIBRARY_PATH` 中叠加多个 CUDA 版本。只有某个明确的软件要求时，再为该软件单独配置库路径。

## 七、编译一个真正运行在 3090 上的 CUDA 程序

只看 `nvcc --version` 只能证明编译器存在。下面编译并运行一个最小向量加法，同时验证编译器、CUDA Runtime、驱动和 GPU：

```bash
cat >/tmp/cuda_smoke.cu <<'CU'
#include <cuda_runtime.h>
#include <iostream>

__global__ void add_one(int *data) {
    int index = blockIdx.x * blockDim.x + threadIdx.x;
    if (index < 256) {
        data[index] += 1;
    }
}

int main() {
    cudaDeviceProp prop{};
    cudaError_t status = cudaGetDeviceProperties(&prop, 0);
    if (status != cudaSuccess) {
        std::cerr << cudaGetErrorString(status) << '\n';
        return 1;
    }

    int *data = nullptr;
    status = cudaMallocManaged(&data, 256 * sizeof(int));
    if (status != cudaSuccess) {
        std::cerr << cudaGetErrorString(status) << '\n';
        return 1;
    }

    for (int i = 0; i < 256; ++i) data[i] = i;
    add_one<<<1, 256>>>(data);
    status = cudaDeviceSynchronize();

    bool correct = status == cudaSuccess;
    for (int i = 0; i < 256 && correct; ++i) {
        correct = data[i] == i + 1;
    }

    std::cout << "GPU: " << prop.name << '\n';
    std::cout << "Compute capability: " << prop.major << '.' << prop.minor << '\n';
    std::cout << "Result: " << (correct ? "PASS" : "FAIL") << '\n';
    cudaFree(data);
    return correct ? 0 : 1;
}
CU

nvcc -arch=sm_86 /tmp/cuda_smoke.cu -o /tmp/cuda_smoke
/tmp/cuda_smoke
```

RTX 3090 上的输出应类似：

```text
GPU: NVIDIA GeForce RTX 3090
Compute capability: 8.6
Result: PASS
```

如果 `nvcc` 成功但程序运行时报 `CUDA driver version is insufficient for CUDA runtime version`，说明当前实际加载的驱动仍然太旧，应回到驱动层排查，而不是继续修改 Toolkit 环境变量。

## 八、验证 PyTorch，而不是强求三个版本号相同

回到原来的 Python 虚拟环境或 Conda 环境，执行：

```bash
python3 - <<'PY'
import torch

print("PyTorch:", torch.__version__)
print("PyTorch CUDA build:", torch.version.cuda)
print("CUDA available:", torch.cuda.is_available())

assert torch.cuda.is_available(), "PyTorch cannot use CUDA"
print("GPU:", torch.cuda.get_device_name(0))

x = torch.arange(1024, device="cuda", dtype=torch.float32)
y = (x * 2).sum()
print("Result:", y.item())
PY
```

这里很可能出现：

```text
nvidia-smi CUDA Version: 12.x 或更高
nvcc release: 12.8
torch.version.cuda: 12.6、12.8 或其他版本
```

这不一定是问题。PyTorch 官方 wheel 通常携带自己所需的 CUDA 用户态依赖，运行预编译 wheel 时不要求 `torch.version.cuda` 与系统 `nvcc` 完全相同。

需要重点匹配系统 Toolkit 的场景包括：

- 使用 `torch.utils.cpp_extension` 编译 CUDA 扩展；
- 编译 FlashAttention、xFormers 或其他本地 CUDA 算子；
- 从源码编译 PyTorch、TensorFlow 或 CUDA 项目；
- 第三方程序直接链接 `/usr/local/cuda` 下的开发库。

如果需要升级 PyTorch，应在新的虚拟环境中按 PyTorch 官方 **Start Locally** 页面生成安装命令，先验证模型、显存占用和自定义算子，再替换原环境。不要直接在唯一可用的训练环境中覆盖安装。

注意：这一步要到原来的**Python 虚拟环境**里。如果报错，你可能需要升级PyTorch CUDA 构建版本：

```bash
source .venv/bin/activate # 这一步要按照你的实际环境来
python -m pip install --upgrade pip
python -m pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu128
```

![升级cuda构建版本](./升级cuda构建版本.png)

升级 PyTorch CUDA 构建版本完成后，重新执行测试程序：

![升级cuda构建版本后](./升级cuda构建版本后.png)

## 九、Docker 用户还要检查容器这一层

GPU 容器使用宿主机的 NVIDIA 驱动，但 CUDA Runtime 通常来自容器镜像。宿主机安装 CUDA Toolkit 12.8，不会自动把已有镜像中的 CUDA 11.x 改成 12.8。

先验证容器能看到 GPU：

```bash
docker run --rm --gpus all nvidia/cuda:12.8.0-base-ubuntu22.04 nvidia-smi
```

如果宿主机 `nvidia-smi` 正常，而容器报 `could not select device driver`、`unknown runtime` 或找不到 GPU，应检查 NVIDIA Container Toolkit 和 Docker runtime 配置。这属于容器 GPU 映射问题，不是重新安装宿主机 CUDA Toolkit 能解决的。

生产镜像还应固定完整标签，例如 `12.8.0-base-ubuntu22.04`，不要只写 `latest`。

## 十、先保留 CUDA 11.4，稳定后再清理

新旧 Toolkit 可以并存。升级完成后先跑几天真实任务，确认以下项目全部正常：

- 原有模型能够加载并完成推理或训练；
- 自定义 CUDA 扩展可以重新编译；
- Docker 容器能访问 GPU；
- `nvidia-smi`、监控和温度功耗数据正常；
- 重启后驱动仍能自动加载；
- 没有程序仍依赖写死的 `/usr/local/cuda-11.4`。

查看旧包的准确名称：

```bash
dpkg -l | awk '/cuda.*11-4/ {print $2, $3}'
```

如果确认不再需要，可以先模拟删除：

```bash
sudo apt -s remove cuda-toolkit-11-4
```

认真检查模拟结果没有删除当前驱动、CUDA 12.8 或业务依赖，再执行：

```bash
sudo apt remove cuda-toolkit-11-4
```

不要为了“清理干净”直接执行来源不明的 `apt purge 'nvidia*' 'cuda*'`。它会扩大故障范围，而且对一次正常的并行升级没有必要。

如果新 Toolkit 引发兼容问题，可执行 `sudo update-alternatives --config cuda` 选择 `/usr/local/cuda-11.4`，并把当前项目环境中的 `CUDA_HOME` 和 PATH 改回 11.4。Toolkit 回退不等于驱动回退：新驱动通常可以向后运行旧 CUDA 程序，不应仅因为切换 Toolkit 就降级驱动。驱动确实需要回退时，应根据升级前保存的包清单、Ubuntu 版本和内核版本制定单独方案。

## 十一、常见故障与定位方法

### 1. `nvidia-smi` 已显示 12.x，但 `nvcc` 还是 11.4

这是 PATH 或 alternatives 仍指向旧 Toolkit：

```bash
type -a nvcc
readlink -f "$(command -v nvcc)"
update-alternatives --display cuda
grep -nE 'CUDA_HOME|/usr/local/cuda' ~/.bashrc ~/.profile
```

选择 `/usr/local/cuda-12.8`，修改旧环境变量，再执行 `hash -r`。

### 2. `nvcc` 是 12.8，但 `nvidia-smi` 仍显示 11.4

说明只升级了 Toolkit，没有升级实际加载的驱动。CUDA 程序可能因为驱动过旧而启动失败。先完成驱动安装和重启。

### 3. 重启后 `nvidia-smi` 无法连接驱动

按下面顺序检查：

```bash
uname -r
dkms status
lsmod | grep nvidia
sudo dmesg -T | grep -iE 'nvidia|nouveau|secure boot|module verification'
journalctl -k -b | grep -iE 'nvidia|nouveau|secure boot'
```

常见原因是缺少当前内核头文件、DKMS 编译失败、Secure Boot 未完成 MOK 注册，或 `nouveau` 与 NVIDIA 模块冲突。远程机器应先保留旧内核启动项和带外登录能力，再处理驱动问题。

### 4. PyTorch 仍显示 CUDA 11.x

`torch.version.cuda` 是这个 PyTorch 包的构建版本，不会因为安装系统 Toolkit 12.8 自动改变。只要新驱动能向后兼容，而且 CUDA 张量测试正常，预编译 wheel 可以继续使用。

### 5. 自定义算子编译时报 GCC 不支持

先查看 CUDA 12.8 安装指南支持的 GCC 范围，再让构建系统显式使用受支持版本：

```bash
gcc --version
g++ --version
nvcc --version
```

不要长期使用 `-allow-unsupported-compiler` 掩盖编译器不兼容，它可能把问题延后到编译结果或运行阶段。

### 6. 升级后出现 `Driver/library version mismatch`

通常是内核仍加载旧模块，而用户态库已经更新。先确认没有任务运行并正常重启。如果重启后仍存在，再对照 `dkms status`、当前内核和已安装驱动包排查，不要反复覆盖安装 Toolkit。

## 十二、最终验收清单

完成升级后，至少保存以下输出：

```bash
nvidia-smi
nvidia-smi --query-gpu=name,driver_version --format=csv,noheader
nvcc --version
readlink -f /usr/local/cuda
gcc --version | head -n 1
dkms status
```

验收标准是：

1. RTX 3090 能被驱动稳定识别；
2. 驱动版本不低于 570.26；
3. `nvcc --version` 显示 CUDA 12.8；
4. CUDA smoke test 输出 `Compute capability: 8.6` 和 `PASS`；
5. PyTorch 能创建 CUDA Tensor 并完成计算；
6. 使用容器时，容器内也能执行 `nvidia-smi`；
7. 重启后以上检查仍然通过。

CUDA 升级最重要的不是把所有地方的版本号改成同一个数字，而是清楚每个版本属于哪一层，并逐层验证。对于 RTX 3090 工作站，保留旧 Toolkit、先升级驱动、再并行安装 CUDA 12.8，是比“全部卸载重装”更容易验证和回退的路径。
