# 内存使用量、内存申请量、工作集使用量，到底有什么区别？

先问你一个场景题。

你盯着监控面板，看到同一个进程挂着三个"内存"数字：一个写着**申请了 8 GB**，一个写着**使用了 3 GB**，还有一个写着**工作集 1.5 GB**。老板走过来问："这玩意儿到底吃了多少内存？"

你一时语塞。到底哪个才是"真占用"？是不是哪里统计错了？

其实三个数字都没错，它们只是在回答三个不同的问题。搞混它们，轻则容量规划拍脑袋，重则在 Kubernetes 里把 limit 设歪，服务动不动就被 OOMKill。这篇就把这三个概念彻底讲清楚。

## 一、先建立一个直觉：图书馆借书

把内存想象成一座图书馆，你的程序是来借书看书的读者。

- 你跟管理员说"给我留 100 本的书架位"——这是**申请**。你还没真借，但位子先占上了。
- 你实际从书架上搬了 40 本书下来——这是**使用**。书真的到你手上了。
- 你此刻摊在桌子上正在翻的，其实只有 10 本——这是**工作集**。剩下 30 本虽然借了，但堆在角落暂时没碰。

一句话先记住：

> 申请量是"要了多少"，使用量是"真拿了多少"，工作集是"眼下真在用的那部分"。

三者通常是**申请量 ≥ 使用量 ≥ 工作集**。接下来逐个拆开。

## 二、内存申请量（Allocated / Reserved）

申请量，是程序向操作系统**要**的内存，也常被叫作"已分配"或"已保留"的虚拟内存。

关键在于：申请不等于真的占用物理内存。

现代操作系统有个很"鸡贼"的机制叫**惰性分配（lazy allocation）**。你 `malloc(1GB)` 或者 `new` 一大块，系统往往只是在虚拟地址空间里给你画了块地、记了个账，并没有立刻掏出真实的物理内存条。只有当你真正往某一页里写数据时，才会触发缺页中断，操作系统这时才给你贴上一页真实内存。

举个例子：

```cpp
// 申请 1GB 虚拟地址空间
char* buf = (char*)malloc(1024 * 1024 * 1024);
// 此刻物理内存几乎没动，只是账面上申请量 +1GB

// 只写了前面 10MB
memset(buf, 0, 10 * 1024 * 1024);
// 现在才真正占用约 10MB 物理内存
```

所以申请量往往是三个数字里**最大、也最虚**的那个。它反映的是"程序理论上可能用到多少"，而不是"现在真占了多少"。

> 申请量看的是程序的"胃口"，不是它真吃进肚子的量。

在 Linux 里，`top` / `ps` 看到的 **VSZ（Virtual Size）** 就属于这一类——它经常大得吓人（动不动几十 GB），但完全不代表机器被吃空了。很多新手看到 VSZ 几十 G 就吓一跳，其实大可不必。

## 三、内存使用量（RSS / 常驻内存）

内存使用量，通常指**真正占用了物理内存**的那部分，最经典的指标就是 **RSS（Resident Set Size，常驻集大小）**。

承接上面的例子：你申请了 1GB，但只写了 10MB，那么 RSS 就是约 10MB。RSS 统计的是"已经落到物理内存条上"的页面，包括：

- 你程序真正读写过的堆、栈数据；
- 加载进来的代码段、共享库中被实际用到的部分。

这才是大多数时候我们说"这进程吃了多少内存"的那个数字。`top` 里的 **RES** 列、`ps` 里的 **RSS** 列，看的都是它。

但 RSS 也有两个坑，顺带点一下：

1. **共享内存会被重复计算**。多个进程共用一个动态库，这块库的内存可能在每个进程的 RSS 里都算了一遍，加起来会虚高。
2. **RSS 里有"冷数据"**。有些页面你很久以前写过、现在根本不碰了，它们可能还赖在物理内存里没被换出，仍然计入 RSS。

第 2 点，正是引出"工作集"的关键。

> 使用量（RSS）是"真占了多少物理内存"，但里面掺着一些你早就不碰的冷数据。

## 四、内存工作集使用量（Working Set）

工作集，指的是进程在**最近一段时间内真正在活跃使用**的那部分内存。

还是图书馆那个比喻：你借了 40 本（RSS），但最近一小时真正翻过的只有 10 本（工作集）。剩下 30 本虽然还占着你的桌子，但如果图书馆位子紧张，管理员完全可以先把那 30 本收走（换出到磁盘），等你要用了再搬回来，基本不影响你当下看书。

所以工作集的核心含义是：**为了让程序流畅运行，当下真正"必须留在物理内存里"的量**。它比 RSS 更能反映程序的"真实活跃内存需求"。

这个概念在两个地方特别重要：

**1. Windows 的 Working Set**

Windows 任务管理器里的"工作集"就是这个意思——进程当前占用的物理内存中，正被活跃引用的部分。系统内存吃紧时，会把不活跃的页面从工作集里修剪（trim）出去。

**2. Kubernetes / cgroup 的 working_set_bytes**

这是如今最容易踩坑的地方。K8s 里 `kubectl top pod` 看到的内存，以及容器 OOM 判定用的，正是 **working set**，它的计算大致是：

```
working_set = 容器使用的内存 − 可以被回收的 inactive 文件缓存
```

也就是说，它把"随时能丢、丢了也不影响运行"的那部分文件页缓存扣掉了，剩下的才是"真正扛着、丢了会出事"的内存。当这个 working set 顶到 limit，Pod 就会被 **OOMKilled**。

> 工作集回答的是最关键的那个问题：现在到底有多少内存是"丢不得"的。

很多人把容器 limit 按 VSZ 或粗略的 RSS 来估，结果不是浪费配额，就是莫名其妙被 kill——根子就在于没搞清监控看的其实是 working set。

## 五、一张表看懂三者区别

| 指标 | 回答什么问题 | 典型来源 | 和物理内存的关系 | 一句话类比 |
| --- | --- | --- | --- | --- |
| 申请量 | 程序**要**了多少 | Linux VSZ、malloc 总量 | 多数是虚账，不占物理内存 | 预订了多少书架位 |
| 使用量 | 真正**占**了多少物理内存 | Linux RSS、top 的 RES | 实打实的物理占用，含冷数据 | 实际借下来多少本书 |
| 工作集 | 当下**丢不得**的有多少 | Windows Working Set、K8s working_set_bytes | 活跃的物理占用，扣掉可回收缓存 | 此刻摊在桌上正看的几本 |

关系链再强调一遍：

> **申请量 ≥ 使用量（RSS）≥ 工作集**

从左到右，水分越来越少，越来越贴近"程序真正离不开的内存"。

## 六、实战中该看哪个？

分场景记就行：

- **排查内存泄漏**：盯 **RSS** 的长期趋势。如果 RSS 只涨不降、一路爬坡，大概率是泄漏。单看申请量没用，因为申请了不写照样是虚账。
- **做容量规划 / 设 K8s limit**：以 **工作集** 为主要依据，再留一截安全余量。这才是容器真正会被 OOM 判定的量。
- **看虚拟地址空间是否异常**：才去看 **申请量 / VSZ**，比如怀疑地址空间耗尽、mmap 过多的时候。
- **普通人问"这进程占多少内存"**：报 **RSS** 最不容易被挑错，它最接近直觉里的"占用"。

一句话收口：**申请量看胃口，使用量看占用，工作集看命门**——盯错指标，省钱和稳定性就都保不住。
