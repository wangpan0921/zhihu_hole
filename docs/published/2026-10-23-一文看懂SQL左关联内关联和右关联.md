# 一文看懂 SQL 左关联、内关联和右关联：区别与使用场景

在写 SQL 查询时，只要数据分散在两张表里，就很可能需要使用 `JOIN`。

例如，员工表里保存了员工姓名和部门编号，部门表里保存了部门名称。要查询“每位员工所在的部门”，就需要按照部门编号把两张表连接起来。

最常见的连接方式有三种：

- 内关联：`INNER JOIN`
- 左关联：`LEFT JOIN`
- 右关联：`RIGHT JOIN`

它们的语法非常相似，真正的区别只有一个：**当关联条件匹配不上时，哪些数据仍然会被保留下来。**

本文用同一组示例数据，逐步讲清三种关联的结果、使用场景和常见误区。

## 一、先准备两张示例表

假设有一张员工表 `employees`：

| id | name | department_id |
| --- | --- | --- |
| 1 | 张三 | 10 |
| 2 | 李四 | 20 |
| 3 | 王五 | NULL |
| 4 | 赵六 | 99 |

还有一张部门表 `departments`：

| id | department_name |
| --- | --- |
| 10 | 研发部 |
| 20 | 销售部 |
| 30 | 财务部 |

两张表通过下面的条件建立关联：

```sql
employees.department_id = departments.id
```

这里有三种值得注意的数据：

- 张三、李四的部门编号能够正常匹配。
- 王五没有填写部门编号。
- 赵六填写了部门编号 `99`，但部门表里不存在这个部门。
- 财务部存在于部门表中，但暂时没有员工。

正是这些“匹配不上”的数据，决定了三种连接的结果差异。

## 二、内关联：只保留两边都能匹配的数据

内关联使用 `INNER JOIN`：

```sql
SELECT
    e.id,
    e.name,
    d.department_name
FROM employees AS e
INNER JOIN departments AS d
    ON e.department_id = d.id;
```

查询结果是：

| id | name | department_name |
| --- | --- | --- |
| 1 | 张三 | 研发部 |
| 2 | 李四 | 销售部 |

王五、赵六和财务部都没有出现在结果中，因为它们都无法在另一张表里找到匹配项。

可以把内关联理解为：

> 只要两张表的交集，关联成功才返回。

### 内关联适合什么场景

当业务只关心“关系完整、确实匹配成功”的数据时，使用内关联。

典型场景包括：

- 查询已经分配部门的员工。
- 查询确实产生过订单的用户。
- 查询同时存在商品信息和库存记录的商品。
- 查询已绑定角色的账号。

例如，只统计有有效部门的员工人数：

```sql
SELECT COUNT(*) AS employee_count
FROM employees AS e
INNER JOIN departments AS d
    ON e.department_id = d.id;
```

需要注意，内关联会直接过滤掉匹配失败的数据。如果你还想发现脏数据或缺失关系，内关联可能会让问题“看不见”。

## 三、左关联：左表全部保留，右表匹配不到就补 NULL

左关联使用 `LEFT JOIN`，完整写法是 `LEFT OUTER JOIN`，其中 `OUTER` 通常可以省略：

```sql
SELECT
    e.id,
    e.name,
    d.department_name
FROM employees AS e
LEFT JOIN departments AS d
    ON e.department_id = d.id;
```

查询结果是：

| id | name | department_name |
| --- | --- | --- |
| 1 | 张三 | 研发部 |
| 2 | 李四 | 销售部 |
| 3 | 王五 | NULL |
| 4 | 赵六 | NULL |

左表 `employees` 中的四名员工全部被保留。右表能匹配时，返回部门名称；匹配不到时，右表字段用 `NULL` 填充。

可以把左关联理解为：

> 以左表为主，左表的数据一条都不能少。

### 左关联适合什么场景

左关联是业务查询中最常用的一种连接，适合“主数据必须完整展示，附属数据有则显示、无则留空”的场景。

典型场景包括：

- 展示所有用户，以及每个用户最近一次登录时间。
- 展示所有商品，以及对应的库存数量。
- 展示所有员工，以及对应的部门名称。
- 展示所有日期，即使某些日期没有订单也要显示为 0。

例如，查询所有用户及其订单数，包括从未下过单的用户：

```sql
SELECT
    u.id,
    u.name,
    COUNT(o.id) AS order_count
FROM users AS u
LEFT JOIN orders AS o
    ON u.id = o.user_id
GROUP BY u.id, u.name;
```

这里要使用 `COUNT(o.id)`，而不是 `COUNT(*)`。对于没有订单的用户，左关联仍会产生一行结果，只是订单字段全为 `NULL`。`COUNT(*)` 会把这一行计为 1，而 `COUNT(o.id)` 不统计 `NULL`，结果才会是 0。

### 左关联还能查“没有关联记录”的数据

如果想找出没有有效部门的员工，可以判断右表主键是否为 `NULL`：

```sql
SELECT
    e.id,
    e.name,
    e.department_id
FROM employees AS e
LEFT JOIN departments AS d
    ON e.department_id = d.id
WHERE d.id IS NULL;
```

结果会包含王五和赵六。这种写法常被称为“反连接”，适合查找：

- 从未下过单的用户。
- 没有库存记录的商品。
- 没有分配权限的账号。
- 引用了不存在对象的异常数据。

## 四、右关联：右表全部保留，左表匹配不到就补 NULL

右关联使用 `RIGHT JOIN`：

```sql
SELECT
    e.id,
    e.name,
    d.department_name
FROM employees AS e
RIGHT JOIN departments AS d
    ON e.department_id = d.id;
```

查询结果是：

| id | name | department_name |
| --- | --- | --- |
| 1 | 张三 | 研发部 |
| 2 | 李四 | 销售部 |
| NULL | NULL | 财务部 |

这一次，右表 `departments` 的所有部门都被保留。财务部没有员工，因此员工字段显示为 `NULL`。王五和赵六不会出现，因为他们在左表中，而右关联不保证保留左表的未匹配数据。

可以把右关联理解为：

> 以右表为主，右表的数据一条都不能少。

### 右关联适合什么场景

只要业务要求完整保留右表，就可以使用右关联。例如：

- 查询所有部门及其员工，包括没有员工的部门。
- 查询所有标准分类，以及归属该分类的商品。
- 查询所有权限项，以及拥有该权限的角色。

不过在实际项目中，右关联通常比左关联少见。因为同一个查询交换两张表的位置后，可以用左关联表达：

```sql
SELECT
    e.id,
    e.name,
    d.department_name
FROM departments AS d
LEFT JOIN employees AS e
    ON e.department_id = d.id;
```

这段 SQL 与前面的 `RIGHT JOIN` 含义相同，但阅读顺序更自然：先写需要完整保留的主表，再用左关联补充其他数据。

团队如果统一使用左关联，复杂 SQL 往往更容易阅读和维护。另一个现实原因是，并非所有数据库或数据处理引擎都支持右关联。

## 五、三种关联放在一起比较

| 关联方式 | 保留左表未匹配数据 | 保留右表未匹配数据 | 主要用途 |
| --- | --- | --- | --- |
| `INNER JOIN` | 否 | 否 | 只查询两边都匹配的数据 |
| `LEFT JOIN` | 是 | 否 | 完整保留左表，补充右表信息 |
| `RIGHT JOIN` | 否 | 是 | 完整保留右表，补充左表信息 |

选择时可以只问两个问题：

1. 哪张表的数据必须全部保留？
2. 匹配不上的数据要显示，还是要过滤？

对应关系如下：

- 只要匹配成功的数据：`INNER JOIN`。
- 左边这张表必须全部保留：`LEFT JOIN`。
- 右边这张表必须全部保留：`RIGHT JOIN`。

如果左右两边未匹配的数据都要保留，需要的是 `FULL OUTER JOIN`。MySQL 不直接支持这种语法，通常需要通过 `LEFT JOIN`、`RIGHT JOIN` 和 `UNION` 组合实现；PostgreSQL、SQL Server 等数据库则原生支持。

## 六、最容易踩坑的地方

### 1. 把右表条件写进 WHERE，左关联可能变成内关联

假设只想关联“启用状态”的部门，下面的写法存在问题：

```sql
SELECT
    e.name,
    d.department_name
FROM employees AS e
LEFT JOIN departments AS d
    ON e.department_id = d.id
WHERE d.status = 'active';
```

没有匹配部门的员工，其 `d.status` 是 `NULL`，无法满足 `WHERE d.status = 'active'`，因此会被过滤掉。最终效果接近内关联。

如果需求是“保留所有员工，只关联启用的部门”，条件应该放在 `ON` 中：

```sql
SELECT
    e.name,
    d.department_name
FROM employees AS e
LEFT JOIN departments AS d
    ON e.department_id = d.id
   AND d.status = 'active';
```

可以记住：

- `ON` 决定两张表如何匹配。
- `WHERE` 对连接完成后的结果再次过滤。

条件放置的位置不同，查询含义可能完全不同。

### 2. 一对多关联会让结果行数增加

如果一个用户有 3 个订单，那么用户表和订单表关联后，这个用户会出现 3 行。这不是重复数据，而是一对多关系的正常结果。

```sql
SELECT
    u.id,
    u.name,
    o.id AS order_id
FROM users AS u
LEFT JOIN orders AS o
    ON u.id = o.user_id;
```

如果最终只需要每个用户一行，就应该聚合、筛选或先在子查询中处理订单，而不是直接用 `DISTINCT` 掩盖问题。

例如，查询每个用户的最后下单时间：

```sql
SELECT
    u.id,
    u.name,
    MAX(o.created_at) AS last_order_time
FROM users AS u
LEFT JOIN orders AS o
    ON u.id = o.user_id
GROUP BY u.id, u.name;
```

### 3. NULL 不会与 NULL 自动匹配

SQL 中，`NULL` 表示未知值。下面这个条件不能让两边的 `NULL` 匹配成功：

```sql
a.code = b.code
```

即使 `a.code` 和 `b.code` 都是 `NULL`，比较结果也不是 `TRUE`。如果业务上确实需要把两个空值视为相等，应根据数据库选择空值安全的写法。

MySQL 可以使用：

```sql
a.code <=> b.code
```

PostgreSQL 可以使用：

```sql
a.code IS NOT DISTINCT FROM b.code
```

但更重要的是先确认：业务上把两个“未知值”当作同一个值，是否真的合理。

### 4. 关联字段类型不一致会影响正确性和性能

例如，一张表的 `user_id` 是整数，另一张表的 `user_id` 是字符串。数据库可能进行隐式类型转换，不仅容易出现意外结果，还可能导致索引无法被有效使用。

关联字段最好满足以下条件：

- 数据类型一致。
- 字符串字段的字符集和排序规则兼容。
- 主表关联键通常有主键或唯一索引。
- 明细表中高频使用的关联字段建立合适索引。

### 5. 不要遗漏关联条件

如果没有写 `ON` 条件，或者条件写错，可能产生笛卡尔积：左表每一行都与右表每一行组合。

假设左表有 1 万行，右表有 5 万行，错误连接可能产生 5 亿行中间结果。多表查询中，应逐个检查每个 `JOIN` 是否都有明确且正确的关联条件。

## 七、多表关联时怎么选择

真实业务通常不止两张表。例如查询所有订单，并补充用户和支付信息：

```sql
SELECT
    o.id AS order_id,
    u.name AS user_name,
    p.paid_at
FROM orders AS o
INNER JOIN users AS u
    ON o.user_id = u.id
LEFT JOIN payments AS p
    ON o.id = p.order_id;
```

这里两种连接方式表达了不同的业务规则：

- 订单必须属于一个有效用户，所以订单与用户使用 `INNER JOIN`。
- 订单可能尚未支付，但仍然需要显示，所以支付记录使用 `LEFT JOIN`。

多表关联不应该机械地全部使用同一种 `JOIN`。每连接一张表，都要重新判断：这张表匹配失败时，当前结果是否还应该保留？

## 八、性能上该注意什么

`INNER JOIN`、`LEFT JOIN` 和 `RIGHT JOIN` 的性能不能脱离数据量、索引和执行计划简单比较。数据库优化器常常会调整实际的连接顺序，因此不能只根据 SQL 的书写顺序判断谁先执行。

更有价值的优化方法是：

- 给高频关联字段建立合适索引。
- 保证关联字段类型一致，避免隐式转换。
- 只查询需要的列，避免无意义的 `SELECT *`。
- 尽早过滤不需要的数据，但要注意外关联中条件的位置。
- 使用 `EXPLAIN` 查看执行计划，而不是凭感觉改写 SQL。
- 先确认一对一、一对多还是多对多，预估结果集会放大多少。

例如，在 MySQL 中可以这样检查执行计划：

```sql
EXPLAIN
SELECT
    e.name,
    d.department_name
FROM employees AS e
LEFT JOIN departments AS d
    ON e.department_id = d.id;
```

## 九、总结

三种关联的核心区别，可以压缩成三句话：

- `INNER JOIN`：只保留两边匹配成功的数据。
- `LEFT JOIN`：完整保留左表，右表匹配不到时补 `NULL`。
- `RIGHT JOIN`：完整保留右表，左表匹配不到时补 `NULL`。

实际选择时，不要先背语法，而要先确定谁是“必须完整保留的主数据”。

如果查询的是“所有员工及其部门”，员工是主数据，用 `LEFT JOIN`；如果查询的是“所有部门及其员工”，部门是主数据，可以把部门放在左边继续使用 `LEFT JOIN`；如果只关心确实匹配的员工和部门，就使用 `INNER JOIN`。

最后还要特别警惕三个问题：外关联条件写在 `WHERE` 中导致数据被过滤、一对多关联导致行数膨胀，以及关联字段类型不一致导致索引失效。把这三点处理好，大多数表关联问题就已经解决了一半。
