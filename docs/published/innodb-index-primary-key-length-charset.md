# InnoDB 索引：主键、长度与字符集

设计 MySQL 表时，经常会遇到这些问题：为什么查询需要索引？主键是不是必须用自增整数？多个字段能不能一起做主键？`VARCHAR(255)` 建索引会不会超长？只保存英文和数字时，应该使用 `utf8mb4` 还是 `ascii`？

这些问题看起来分散，实际上都围绕同一件事：**InnoDB 如何组织和查找数据**。理解索引、主键、字节长度和字符集之间的关系，才能避免查询慢、索引创建失败，或者表刚建好就给后续业务埋下限制。

## 1. 数据库索引是什么

索引可以理解为一本书的目录。

没有目录时，要找某个知识点，只能从第一页开始逐页翻。数据库没有可用索引时，也可能需要扫描整张表，这在执行计划中通常表现为全表扫描。

有了目录，可以先找到页码，再直接翻到目标页。数据库索引也会额外保存“索引列的值”和“对应数据的位置”，让数据库少检查很多行。

InnoDB 的普通索引通常使用 B+Tree。B+Tree 会让索引值保持有序，因此不仅能加速等值查询，还适合范围查询和排序。例如给订单表的 `created_at` 建索引后，下面的查询可能只扫描指定时间范围内的数据：

```sql
SELECT *
FROM orders
WHERE created_at >= '2026-07-01'
  AND created_at <  '2026-08-01';
```

索引常见的作用包括：

- 加速 `WHERE` 条件过滤。
- 加速表连接中的关联字段查找。
- 在顺序与索引一致时，减少 `ORDER BY` 和 `GROUP BY` 的额外排序。
- 通过唯一索引保证数据不重复。
- 在索引已经包含查询所需列时，形成覆盖索引，减少回表读取。

索引不是越多越好。每增加一个索引，插入、删除和更新数据时就要同步维护；索引还会占用磁盘和缓存。正确的做法是围绕真实查询设计索引，并通过 `EXPLAIN` 检查是否使用：

```sql
EXPLAIN SELECT * FROM orders WHERE tenant_id = 1001 AND order_no = 'A0001';
```

## 2. 主键和普通索引有什么不同

主键首先是一条数据的唯一身份标识。它有三个基本特点：

- 值不能重复。
- 值不能为 `NULL`。
- 一张表只有一个主键约束，但主键可以包含多个列。

在 InnoDB 中，主键还决定了数据的物理组织方式。InnoDB 的主键索引是**聚簇索引**，叶子节点保存完整的一行数据。因此，按主键查找通常可以直接拿到整行。

普通索引也叫二级索引。它的叶子节点通常保存“普通索引列 + 对应行的主键值”。通过普通索引查询完整记录时，InnoDB 先找到主键值，再去主键索引取整行，这一步常被称为“回表”。

可以把两者简化为：

```text
主键索引：主键值 -> 完整数据行
二级索引：索引列值 -> 主键值 -> 完整数据行
```

这也解释了为什么主键不宜太宽。主键越长，每个二级索引中附带的主键值通常也越大。表上二级索引越多，额外占用的空间和缓存越明显。

如果表没有显式主键，InnoDB 会尝试选择第一个所有列都为 `NOT NULL` 的唯一索引作为聚簇索引；如果仍然找不到，就生成内部隐藏的行 ID。隐藏 ID 不能方便地被业务查询和引用，因此业务表通常应该显式定义主键。

常见 OLTP 业务中，主键适合满足这些条件：

- 短小，减少主键索引和二级索引的体积。
- 稳定，插入后尽量不修改。
- 值大致递增，减少随机插入带来的页分裂和碎片。
- 与业务含义适度解耦，避免手机号、邮箱等可变信息成为主键。

因此，自增 `BIGINT` 是常见选择，但不是硬性规定。分布式系统也可以使用雪花 ID 等大致递增的数值 ID。随机 UUID 若直接保存为 36 字符字符串，会比较宽且写入位置随机；需要使用 UUID 时，可以考虑 `BINARY(16)`，并根据版本和生成方式改善写入顺序。

## 3. InnoDB 复合主键

由多个列共同组成的主键叫复合主键。例如，同一租户内订单号唯一，可以这样建表：

```sql
CREATE TABLE orders (
    tenant_id BIGINT UNSIGNED NOT NULL,
    order_no  VARCHAR(32) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    buyer_id  BIGINT UNSIGNED NOT NULL,
    status    TINYINT UNSIGNED NOT NULL,
    created_at DATETIME NOT NULL,
    PRIMARY KEY (tenant_id, order_no),
    KEY idx_buyer (buyer_id)
) ENGINE = InnoDB
  DEFAULT CHARACTER SET = utf8mb4;
```

这里不是有两个主键，而是只有一个主键，由 `tenant_id` 和 `order_no` 共同组成。不同租户可以出现相同的订单号，但同一租户内不能重复。

### 列顺序决定能支持哪些查询

复合索引遵循最左前缀原则。对于主键 `(tenant_id, order_no)`，数据先按 `tenant_id` 排序，在相同 `tenant_id` 内再按 `order_no` 排序。

它适合以下条件：

```sql
WHERE tenant_id = 1001

WHERE tenant_id = 1001 AND order_no = 'A0001'

WHERE tenant_id = 1001 AND order_no >= 'A0001'
```

但只按第二列查询时，通常不能高效利用这个 B+Tree 的最左侧定位能力：

```sql
WHERE order_no = 'A0001'
```

如果这种查询很频繁，需要根据业务情况增加以 `order_no` 开头的索引。

### 复合主键的优点和代价

复合主键能直接表达“多列组合唯一”，也经常适合租户隔离表、中间关系表。例如用户和角色的关联表，可以用 `(user_id, role_id)` 作为主键。

它的代价是主键可能变宽。上面的 `idx_buyer` 不只保存 `buyer_id`，其索引记录还需要携带复合主键，以便定位原始数据。因此可以把它近似理解为：

```text
idx_buyer 的记录：buyer_id + tenant_id + order_no
```

如果复合主键由多个长字符串组成，每个二级索引都会被放大。设计时要同时考虑唯一性、查询条件和二级索引成本，而不能只看“这几列组合起来很自然”。

还要注意，`PRIMARY KEY (a, b)` 已经可以保证 `(a, b)` 唯一，通常不需要再创建一个完全相同的唯一索引。

## 4. InnoDB 索引长度如何计算

索引长度限制按**字节**计算，不是按字符数计算。

对于字符列，可以先做一个保守估算：

```text
索引字节数 ≈ 索引字符数 × 字符集每个字符的最大字节数
```

常见字符集的最大字节数如下：

- `ascii`：每个字符最多 1 字节，只能保存 ASCII 范围内的英文、数字和符号。
- `utf8mb4`：每个字符最多 4 字节，可以保存完整 Unicode，包括中文和 Emoji。

例如：

```text
VARCHAR(255) CHARACTER SET ascii
最大索引长度约为 255 × 1 = 255 字节

VARCHAR(255) CHARACTER SET utf8mb4
最大索引长度约为 255 × 4 = 1020 字节
```

`VARCHAR(255)` 中的 255 表示最多 255 个字符，并不表示固定占用 255 字节。表中保存短字符串时，数据存储通常只使用实际内容所需的字节数，再加长度等开销；但是数据库检查能否创建索引时，需要按列定义允许的最大长度考虑。

复合索引要把各索引列的最大字节数相加。假设建立下面的索引：

```sql
KEY idx_name_code (display_name, external_code)
```

其中：

```text
display_name VARCHAR(200) utf8mb4：200 × 4 = 800 字节
external_code VARCHAR(100) ascii：100 × 1 = 100 字节
合计约 900 字节
```

数字和时间类型按其类型所需字节估算。例如 `BIGINT` 为 8 字节，`INT` 为 4 字节。实际索引记录还包含记录头、可空标记、变长字段信息以及二级索引携带的主键等内容，所以估算索引体积时不能只看上述键值之和；不过判断是否接近“最大索引键长度”时，这个计算很实用。

## 5. 常见的 InnoDB 索引限制

MySQL 版本、InnoDB 页大小和行格式都会影响限制，不能脱离环境只记一个数字。

在现代 MySQL 的常见配置中，InnoDB 页大小为 16 KiB，表使用 `DYNAMIC` 行格式，单个索引键的上限通常是 **3072 字节**。页大小为 8 KiB 或 4 KiB 时，上限通常分别是 1536 和 768 字节。

较老版本或使用 `COMPACT`、`REDUNDANT` 行格式的旧表，经常遇到 **767 字节**的索引键限制。这就是很多旧资料建议将 `utf8mb4 VARCHAR(255)` 的索引前缀写成 191 个字符的原因：

```text
191 × 4 = 764 字节
```

这个“191”主要是兼容历史限制，不是所有现代 MySQL 表都必须遵守的固定规则。

另外还有一些常见限制：

- 一个复合索引最多包含 16 个列或键部分。
- InnoDB 一张表最多支持 64 个二级索引。
- `TEXT`、`BLOB` 等大字段建立 B+Tree 索引时必须指定前缀长度。
- 前缀索引只能索引字段开头的一部分，可能降低区分度，也不能替代所有需要完整值的唯一性约束。

例如给文章标题建立前缀索引：

```sql
CREATE INDEX idx_title_prefix ON articles (title(100));
```

对于非二进制字符串，前缀长度通常表示字符数；对于二进制字符串，表示字节数。不要机械地选择 191 或 255，而应结合数据分布评估区分度：

```sql
SELECT
    COUNT(DISTINCT title) AS full_values,
    COUNT(DISTINCT LEFT(title, 20)) AS prefix_20,
    COUNT(DISTINCT LEFT(title, 50)) AS prefix_50
FROM articles;
```

如果短前缀已经能区分绝大多数数据，就没有必要把索引建得很长。

可以通过下面的命令确认实际环境和表定义：

```sql
SELECT VERSION();

SHOW VARIABLES LIKE 'innodb_page_size';

SHOW CREATE TABLE orders;

SHOW INDEX FROM orders;
```

遇到 `Specified key was too long` 一类错误时，优先确认 MySQL 版本、页大小、行格式、字符集，以及复合索引中每一列的声明长度，不要只改其中一个 `VARCHAR` 的数字碰运气。

## 6. utf8mb4 和 ascii 的区别

`utf8mb4` 是 MySQL 中能够完整表示 Unicode 的 UTF-8 字符集，每个字符最多使用 4 字节。中文、日文、各类符号和 Emoji 都可以保存。面向用户的姓名、标题、评论和地址等文本，一般应使用 `utf8mb4`。

`ascii` 只包含 128 个 ASCII 字符，每个字符占 1 字节。它适合业务上能够严格保证只出现英文、数字和少量 ASCII 符号的机器字段，例如：

- 固定格式的英文状态码。
- 只允许 ASCII 的租户编码、设备编码、订单号。
- 十六进制字符串或经过约束的令牌。
- 某些协议明确规定为 ASCII 的字段。

相比 `utf8mb4`，`ascii` 的直接好处是同样字符长度的索引所需字节更少，并且数据库会拒绝超出 ASCII 范围的字符。这既是限制，也是一种数据校验。

但不要为了节省几个字节，把可能出现中文或其他 Unicode 字符的用户输入列设成 `ascii`。电子邮箱、域名、URL 等看起来经常只有英文的字段，也可能涉及国际化格式，应该先依据业务协议明确字符范围，而不是凭样例判断。

如果字段保存的不是文本，而是哈希、UUID 原始值或任意字节，`BINARY`、`VARBINARY` 往往比字符类型更准确。例如 32 位十六进制字符串可以转换为 16 字节二进制保存，而不必使用 `CHAR(32)`。

### 字符集之外还要看排序规则

字符集决定“能保存哪些字符以及如何编码”，排序规则，也就是 collation，决定“字符串如何比较和排序”。

例如，业务编码通常希望逐字节、区分大小写，可以考虑二进制排序规则：

```sql
order_no VARCHAR(32)
    CHARACTER SET ascii
    COLLATE ascii_bin
```

而用户昵称可能更适合某个 `utf8mb4` 的语言排序规则。排序规则还会影响唯一索引：如果规则不区分大小写，`ABC` 和 `abc` 可能被视为相同值。

连接两个字符串列时，尽量让两边的字符集、排序规则和类型一致。否则数据库可能需要隐式转换，不仅容易出现比较结果不符合预期，还可能影响索引使用。外键关联的字符串列也应该保持兼容定义。

## 7. 一套实用的设计顺序

设计表和索引时，可以按下面的顺序思考：

1. 先确定每行数据如何被稳定、唯一地标识，再选择单列主键或复合主键。
2. 列出高频查询、关联、排序条件，按照最左前缀原则设计复合索引的列顺序。
3. 记住 InnoDB 二级索引会携带主键，评估主键宽度对所有二级索引的影响。
4. 根据字段真实语义选择字符集：用户文本优先 `utf8mb4`，严格的 ASCII 机器编码才使用 `ascii`。
5. 用“字符数 × 每字符最大字节数”估算每个字符索引列，再计算复合索引总长度。
6. 通过 `SHOW CREATE TABLE`、`SHOW INDEX` 和 `EXPLAIN` 验证实际定义与执行计划。
7. 最后结合慢查询和真实数据分布调整索引，而不是只凭字段名猜测。

## 总结

InnoDB 的主键不仅负责唯一标识数据，还是整张表的聚簇索引；普通索引则通常通过主键回到完整数据行。因此，主键越宽，二级索引的成本也越高。

复合主键和复合索引都要重视列顺序，能否命中索引取决于最左前缀。索引长度按字节而不是字符计算，所以 `utf8mb4` 和 `ascii` 会直接影响可索引长度与索引体积。现代常见配置通常允许 3072 字节的索引键，旧环境则可能受 767 字节限制，最终应以实际 MySQL 版本、页大小和行格式为准。

把主键、查询方式、字符集和索引长度放在一起设计，比遇到慢查询或建索引报错后再逐项修补更可靠。
