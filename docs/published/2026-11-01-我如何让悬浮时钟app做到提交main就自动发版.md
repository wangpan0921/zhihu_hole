# 我不再手动发 APK：改完版本号，提交 main 就自动上线

我做了一款安卓悬浮时钟 App，用户不多，但更新不少。最早每次发版都是手动三连：让 Agent 改代码编 APK → 把 APK 从本地拖出来 → 改一遍下载页的版本号、文件大小、更新日期，再 push 到下载站仓库。做一次没什么，连做十几次之后，我开始怀疑人生——为了几行改动，我要在键盘上重复完全一样的三步。

于是我把发版流程塞进了 GitHub Actions：**我让 Agent 负责在 `build.gradle.kts` 里改一个版本号，剩下的构建、签名、打 tag、发 Release、刷新下载页、推 Cloudflare Pages 全自动跑完**。这篇文章就把这条链路拆开讲一下。

> 一句话记住：把“版本号”做成单一事实源，让 CI 自己判断要不要发；下载站仓库连 Cloudflare Pages 直连 git，部署这件事就不用自己写一行代码了。

## 一、整体链路：两个仓库 + 一个 Workflow

先给一张文字版的架构图，后面所有章节都在填这张图里的空：

```

   push     │  icey-floating-clock (App 代码仓库)              │
 ────────▶  │  .github/workflows/release-on-main.yml          │
   main     │                                                 │
            │  job 1 release:                                 │
            │    读 app/build.gradle.kts 里的 versionName     │
            │    查 origin 是否已有同名 tag                    │

            │    打 tag v1.3.9 + 发 GitHub Release 挂 APK     │
            │    上传 APK 到 Actions artifact                 │

            │  job 2 deploy-to-money (needs: release):        │
            │    下载上一步的 APK artifact                     │
            │    checkout wangpan0921/money 下载站仓库         │

            └─────────────────────────────────────────────────┘
                                 │

            │  wangpan0921/money (下载站仓库)                 │
```

关键是两条：

- **发版的触发器是“push 到 main”**，不是手动在 GitHub 上点 Release，也不是打 tag 触发。我只需要正常合并 PR 或直接 push。
- **部署到 Cloudflare 不用我自己做**。Cloudflare Pages 和 money 仓库是 GitHub 直连的，我这边只负责把文件 push 到 money 的 main 分支，部署就水到渠成。

## 二、版本号这件事：别让 CI 猜，让 CI 读

网上很多“自动发版”教程喜欢让 CI 帮你 bump 版本号——每次 push 就自动 +1，或者按 commit message 规约（conventional commits）自动算 semver。我试过，不好用：

- 合并 PR 和 rebase 之后，diff 版本号那一行容易误判。
- 版本号到底是 1.3.8 还是 1.3.9，我希望改代码的时候自己心里有数，不想让机器替我决定。
- 回滚也很尴尬：revert 一个 commit，CI 又当成一次新的 bump。

所以我的做法反过来：**版本号由我决定，Agent 写进 `app/build.gradle.kts`，CI 读它，然后用“tag 是否存在”判断要不要发。**

```yaml
- name: Read versionName from app/build.gradle.kts
  id: ver
  run: |
    set -euo pipefail
    V=$(grep -E '^\s*versionName\s*=\s*"' app/build.gradle.kts \
        | head -1 \
        | sed -E 's/.*"([^"]+)".*/\1/')
    echo "versionName=${V}" >> "$GITHUB_OUTPUT"
    echo "tag=v${V}"        >> "$GITHUB_OUTPUT"

- name: Check if tag already exists on origin
  id: tagcheck
  run: |
    set -euo pipefail
    if git ls-remote --exit-code --tags origin "refs/tags/v${V}" >/dev/null 2>&1; then
      echo "exists=true"  >> "$GITHUB_OUTPUT"
    else
      echo "exists=false" >> "$GITHUB_OUTPUT"
    fi
```

后面所有真正干活的步骤（构建、签名、打 tag、发 Release）都加一个 `if: steps.tagcheck.outputs.exists == 'false'`。效果就是：

- 我改了版本号 push → tag 不存在 → 走完整发版流程 → push 完成的那一刻 tag 就建上了。
- 没改版本号 push（纯文档修改、CI 自己的调整）→ tag 已存在 → workflow 从中间整段跳过，几秒钟就结束。
- 发布失败重跑 → 幂等天然成立。

> 一句话记住：**“HEAD 的 versionName 对应的 tag 不存在”是单一事实源**。重跑、回滚、合并，这个判断都不会错。

## 三、CI 里做正式签名，而不是本机签完上传

安卓的签名文件（keystore / jks）是开发者最怕弄丢的东西：**一旦换签名，老用户就必须卸载重装**，所有本地数据和已购权益全部清空。所以这文件绝对不能进仓库，也不能把密码写死到 workflow 里。

但另一边，我又不想每次都在本机构建完上传——那自动化就断了。折中方案：**把签名文件 base64 后放进 GitHub Secrets，CI 跑的时候再还原成文件**。

```yaml
- name: Materialize release keystore
  env:
    KEYSTORE_BASE64:   ${{ secrets.KEYSTORE_BASE64 }}
    KEYSTORE_PASSWORD: ${{ secrets.KEYSTORE_PASSWORD }}
    KEY_ALIAS:         ${{ secrets.KEY_ALIAS }}
  run: |
    set -euo pipefail
    JKS_PATH="$GITHUB_WORKSPACE/app/release.jks"
    printf '%s' "$KEYSTORE_BASE64" | base64 -d > "$JKS_PATH"
    {
      printf 'storeFile=%s\n'     "$JKS_PATH"
      printf 'storePassword=%s\n' "$KEYSTORE_PASSWORD"
      printf 'keyAlias=%s\n'      "$KEY_ALIAS"
      printf 'keyPassword=%s\n'   "$KEYSTORE_PASSWORD"
    } > "$GITHUB_WORKSPACE/keystore.properties"
```

这里有两个很坑的小细节，我各踩了一次坑才摸清：

**1. Secret 不能直接插进 shell 字符串。**

很多教程写法是这样：

```yaml
run: |
  echo "storePassword=${{ secrets.KEYSTORE_PASSWORD }}" > keystore.properties
```

看着没问题，其实 `${{ secrets.X }}` 是在 **workflow 解析阶段**就展开进脚本内容的——它根本不是 shell 变量，是 YAML 的字符串替换。GitHub 对 secrets 的屏蔽（masking）是针对标准输出做模糊匹配，挡不住 workflow 自身被恶意改动时的泄露。

正确做法是像上面那样 **先 env 注入，再从环境变量读**，这样 secret 只以环境变量形态存在，不会出现在脚本文本里。

**2. PKCS12 格式下 keyPassword 其实等于 storePassword。**

用 keytool 生成的 .jks 文件，格式默认是 PKCS12（可以用 `xxd keystore.jks | head -1` 看，开头是 `30 82` 就是 PKCS12；真正的 JKS 开头是 `FE ED FE ED`）。PKCS12 规范下 keytool 的 `-keypass` 参数会被静默忽略，内部 key 的密码等于 store 密码。

意思是：**哪怕你当年用 keytool 给 keyPassword 设了另一个值，PKCS12 keystore 里也不会生效**。

## 四、同步到下载站：跨仓库自动化的小心机

我的下载页在另一个仓库 `xxx/money` 里。为什么分两个仓库？因为 money 这个仓库不只放悬浮时钟一个 App，还放了其他小工具的下载页，而且走的是 Cloudflare Pages 的“监视 main 分支自动部署”，不能被 App 代码仓库污染。

于是 release workflow 的第二个 job 就是跨仓库搬运工：

```yaml
deploy-to-money:
  needs: release
  if: needs.release.outputs.published == 'true'
  runs-on: ubuntu-latest
  steps:
    - name: Checkout icey-floating-clock (for deploy script)
      uses: actions/checkout@v4
      with:
        sparse-checkout: .github/scripts
        sparse-checkout-cone-mode: false

    - name: Download APK artifact
      uses: actions/download-artifact@v4
      with:
        name: ${{ needs.release.outputs.apkName }}
        path: artifact

    - name: Checkout xxx/money (main)
      uses: actions/checkout@v4
      with:
        repository: xxx/money
        token: ${{ secrets.MONEY_REPO_TOKEN }}
        ref: main
        path: money

    - name: Rewrite floating-clock downloads in money repo
      run: |
        python .github/scripts/deploy_to_money.py \
          --money-dir money \
          --apk "artifact/floating-clock-standard-v${{ needs.release.outputs.versionName }}-release.apk" \
          --version "${{ needs.release.outputs.versionName }}"

    - name: Commit and push to money main
      working-directory: money
      run: |
        git config user.name  'icey'
        git config user.email '20722054+wangpan0921@users.noreply.github.com'
        git add -A apps/floating-clock
        git commit -m "chore(floating-clock): v${{ needs.release.outputs.versionName }} 发版同步"
        git push origin main
```

有几个点值得单独拎出来说：

**1. 跨仓库 push 要用 Personal Access Token，不能用默认的 `GITHUB_TOKEN`。**

`GITHUB_TOKEN` 只对**当前运行 workflow 的那个仓库**有权限，想推别人仓库必须自己准备一个 Personal Access Token。我用的是 **Fine-grained tokens**（细粒度令牌）：

- Resource owner 选 `xxx`
- Repository access 选 **Only `xxx/money`**（只给这一个仓库）
- Repository permissions → **Contents = Read and Write**（只给 Contents，不给 Actions 和 Secrets）

这样这个 token 哪怕泄露，爆炸半径也就限于 money 一个仓库的内容。老式的 classic token 一开就是 `repo` 全权限，泄露了基本等于交出所有仓库，不推荐。

![alt text](image-1.png)

**2. 下载的两件套：`.apk` 和 `.apk.zip` 字节完全一样。**

money 下载页托管在 Cloudflare Pages 上，静态文件没问题。但下载链接我在 index.html 里**同时放了 `.apk` 和 `.apk.zip` 两个入口**，两个文件字节完全相同，只是扩展名不同。

为什么要这么做？因为我早期还在 InfinityFree 做备份下载，有些手机浏览器识别 `.apk` 直接拦截“存在风险”，但对 `.zip` 没意见；配套的 `.htaccess` 把 `.zip` 的 `Content-Disposition` 改成 `.apk`，浏览器下载完还是正常的安卓安装包。两个入口都挂上，兼容面最大。

**3. 替换版本号的脚本只改字段，不碰文案和 CSS。**

`deploy_to_money.py` 的核心是几条正则：

```python
html = re.sub(r"v\d+\.\d+\.\d+", f"v{args.version}", html)
html = re.sub(r"\d+ KB", f"{size_kb} KB", html)
html = re.sub(r"20\d\d 年 \d+ 月 \d+ 日", date_str, html)
```

绝不动 `<style>` 块、功能介绍、页脚，这几条都是经过 CI 一次次踩雷调出来的——有一次我用了更宽松的替换，把 CSS 里的某个尺寸给换掉了，页面布局当场塌。模板写死之后，自动化才能长期稳定。

## 五、Cloudflare Pages 的最大魔法：直连 git

写到这，可能你还在想：**Cloudflare 部署这步到底在哪？**

答案是：**根本不在我这边**。

money 仓库早期就在 Cloudflare Pages 里绑了：

- Source：GitHub 的 `xxx/money`
- Production branch：`main`
- Build command：（空，纯静态站点）
- Build output directory：`/`

从此以后，只要 main 分支有新 commit，Cloudflare Pages 就自己拉代码、自己 deploy、自己把 `https://money-3jg.pages.dev/` 刷新到最新。我这边的 workflow 从头到尾**没有一行调用 Cloudflare API、没有 wrangler CLI、没有部署 token**。

这就是“git-centric”部署的美妙之处：**push 这个动作既是提交、也是发布信号**。你把它和 CI 组合起来之后，整个“编版本 → 发版 → 上线”的链路只剩一个人类操作：改版本号 + commit。

> 一句话记住：Cloudflare Pages / Vercel / Netlify 这类“监视 git 自动部署”的平台，天然适合给个人项目做一键发布——你写 CI 的目标不是“怎么调它们的部署 API”，而是“怎么把文件 push 到被监视的那个分支”。

## 六、总结一下

回头看，这套发版流水线真正给我带来价值的，并不是“省了多少时间”——我手动发版其实也就十几分钟。真正值的是：

- **我可以放心更新**。改一行代码、bump 版本、push，剩下的我不用守着看。
- **我不会再漏步**。签名、下载页版本号、文件大小、更新日期，这些机械的东西 CI 比我更不健忘。
- **我能更勇敢地做小版本**。1.3.6 和 1.3.9 之间我发了四五个版本，很多只改一两行文案或配色，手动发版时代我会攒着再发，自动化之后我随时可以发。

更底层的那条经验是：**不要把“复杂”写进 CI，把“复杂”藏在业务代码里，CI 只负责搬运。**我的 workflow 没有自动 bump 版本号的逻辑、没有自己调 Cloudflare API、没有自己做文案替换的 AI 魔法，它只做四件事：读、构建、搬、推。每一环都是可以单独手动跑一遍验证的，一个人维护起来才不累。
