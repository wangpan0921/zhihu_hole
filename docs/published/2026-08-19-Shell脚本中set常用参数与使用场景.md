# Shell 脚本中 `set` 常用参数的用法和使用场景

很多 Bash 脚本开头都会出现这一行：

```bash
set -euo pipefail
```

它经常被称为 Bash 的“严格模式”。不过，背下这几个字母并不等于理解它们。尤其是 `set -e`，实际行为比“命令失败就退出”复杂得多；使用不当时，脚本可能在意料之外的位置退出，也可能在我们以为会退出时继续运行。

`set` 是 Shell 的内置命令，可以修改当前 Shell 的执行选项，也可以设置脚本的位置参数。本文以 Bash 为主，介绍工程中最常见的参数及其适用场景。

## 先看 `set` 的基本用法

短选项通常这样开启：

```bash
set -e
set -u
set -x
```

也可以合并：

```bash
set -eux
```

长选项使用 `-o`：

```bash
set -o pipefail
```

一个容易记反的地方是：减号 `-` 表示开启选项，加号 `+` 表示关闭选项。

```bash
set -x   # 开启命令跟踪
set +x   # 关闭命令跟踪

set -e   # 开启 errexit
set +e   # 关闭 errexit
```

查看当前所有选项及其状态，可以执行：

```bash
set -o
```

## `set -e`：命令失败时尽早退出

`set -e` 对应的长选项是：

```bash
set -o errexit
```

开启后，未被处理的命令返回非零状态时，Shell 通常会退出。

例如：

```bash
#!/usr/bin/env bash
set -e

mkdir /tmp/demo
cp config.yaml /tmp/demo/
echo "部署完成"
```

如果 `mkdir` 或 `cp` 失败，脚本会停止，避免在前置步骤失败后仍然输出“部署完成”。

### 适用场景

`set -e` 适合由多个连续步骤组成，而且前一步失败后继续执行没有意义的脚本，例如：

- 编译和打包脚本；
- 部署脚本；
- CI 流水线入口脚本；
- 数据迁移或初始化脚本。

### `set -e` 不是简单的“非零就退出”

Shell 为了支持条件判断，对 `set -e` 规定了不少例外。命令作为 `if`、`while`、`until` 的条件，位于 `&&` 或 `||` 列表中但不是最后一个命令，使用 `!` 取反，或者位于管道中非最后一个位置时，通常不会立即触发退出。

例如，下面的失败是程序逻辑的一部分，不会让脚本退出：

```bash
set -e

if grep -q '^enabled=true$' app.conf; then
    echo "功能已开启"
else
    echo "功能未开启"
fi
```

下面的写法也会继续执行：

```bash
set -e

mkdir /protected/path || echo "创建目录失败"
echo "脚本继续运行"
```

因此，对于预期可能失败的命令，最好显式处理结果，而不是依赖 `set -e` 猜测控制流程：

```bash
if curl -fSLo app.tar.gz "$download_url"; then
    echo "下载成功"
else
    status=$?
    echo "下载失败，退出码：$status" >&2
    exit "$status"
fi
```

另外，Bash 的函数、子 Shell 和命令替换会让 `set -e` 的行为更加复杂。重要步骤仍应使用 `if`、`|| exit` 或显式检查退出码，不要把 `set -e` 当成完整的错误处理机制。

## `set -u`：发现未定义变量

`set -u` 对应：

```bash
set -o nounset
```

开启后，读取未定义变量通常会报错并退出。

```bash
#!/usr/bin/env bash
set -u

echo "部署环境：$DEPLOY_ENV"
```

如果没有定义 `DEPLOY_ENV`，脚本不会把它悄悄当成空字符串，而是直接暴露问题。这对发现变量名拼错特别有用：

```bash
image_name="my-app"
echo "$iamge_name"  # 拼写错误，set -u 会立即发现
```

### 适用场景

`set -u` 适合依赖环境变量、配置变量或脚本参数的自动化任务。它可以避免空变量继续参与路径、命令和 API 参数拼接。

如果变量允许为空，可以给它默认值：

```bash
log_level=${LOG_LEVEL:-info}
```

如果变量必须提供，可以给出清楚的错误信息：

```bash
: "${DEPLOY_ENV:?必须设置 DEPLOY_ENV}"
: "${API_URL:?必须设置 API_URL}"
```

读取可选的位置参数时也要提供默认值：

```bash
config_file=${1:-config.yaml}
```

比起关闭 `set -u`，这些写法更能表达变量究竟是必填还是可选。

## `set -x`：打印实际执行的命令

`set -x` 对应：

```bash
set -o xtrace
```

开启后，Bash 会在执行命令前，把变量展开后的命令输出到标准错误。它特别适合排查 CI、容器和远程机器上难以复现的问题。

```bash
#!/usr/bin/env bash
set -x

name="demo"
mkdir -p "/tmp/$name"
cp app.conf "/tmp/$name/"
```

日志中会看到类似内容：

```text
+ name=demo
+ mkdir -p /tmp/demo
+ cp app.conf /tmp/demo/
```

### 适用场景

- 调试脚本实际执行了哪些命令；
- 检查变量展开结果；
- 定位 CI 流水线失败位置；
- 临时观察某一小段复杂逻辑。

可以只跟踪需要调试的部分：

```bash
prepare_environment

set -x
run_build
run_tests
set +x

package_artifacts
```

### 不要把密钥打印到日志

`set -x` 会输出展开后的参数。下面的命令可能把 token 直接写进 CI 日志：

```bash
curl -H "Authorization: Bearer $API_TOKEN" "$API_URL"
```

执行敏感命令前应暂时关闭跟踪：

```bash
set +x
curl -H "Authorization: Bearer $API_TOKEN" "$API_URL"
set -x
```

生产脚本不应默认全程开启 `set -x`。更稳妥的方式是通过调试变量控制：

```bash
if [[ ${DEBUG:-0} == 1 ]]; then
    set -x
fi
```

## `set -o pipefail`：让管道中的失败可见

默认情况下，一条管道的退出状态通常取最后一个命令的退出状态：

```bash
generate_report | gzip > report.gz
```

假设 `generate_report` 失败了，但 `gzip` 正常结束，整条管道仍可能返回成功。脚本会误以为报告已经正确生成。

开启 `pipefail` 后：

```bash
set -o pipefail
generate_report | gzip > report.gz
```

只要管道中有命令失败，整条管道就会返回非零状态；如果有多个命令失败，Bash 返回最右侧失败命令的状态。

### 适用场景

`pipefail` 适合大量使用管道的数据处理、日志处理、构建和部署脚本，通常与 `set -e` 一起使用：

```bash
set -e
set -o pipefail
```

或者简写为：

```bash
set -eo pipefail
```

需要注意，`pipefail` 不是 POSIX `sh` 标准选项。如果脚本第一行是 `#!/bin/sh`，不能假设所有系统都支持它。依赖 `pipefail` 时，应明确使用 Bash：

```bash
#!/usr/bin/env bash
```

## `set -n`：只读脚本，不执行命令

`set -n` 对应：

```bash
set -o noexec
```

它会读取命令，但不真正执行，常用于做基础语法检查。更常见的命令行用法是：

```bash
bash -n deploy.sh
```

如果没有输出且退出码为 `0`，说明 Bash 没有发现语法错误。

不过，`bash -n` 只能检查解析阶段能发现的问题，无法验证文件是否存在、变量值是否正确、网络是否连通，也不能代替真实测试。

## `set -f`：关闭路径名展开

`set -f` 对应：

```bash
set -o noglob
```

Shell 默认会把 `*`、`?` 和 `[...]` 当成通配符展开：

```bash
echo *.log
```

开启 `set -f` 后，这些字符不会再自动匹配文件名：

```bash
set -f
echo *.log   # 原样输出 *.log
set +f
```

它适合需要把包含通配符的文本原样交给其他程序处理的场景。不过，大多数时候正确引用变量更重要：

```bash
printf '%s\n' "$pattern"
```

不要为了弥补未引用的变量而长期依赖 `set -f`。

## `set -C`：防止重定向覆盖已有文件

`set -C` 对应：

```bash
set -o noclobber
```

开启后，使用 `>` 重定向时不会意外覆盖已存在的普通文件：

```bash
set -C
echo "new data" > result.txt
```

如果 `result.txt` 已存在，命令会失败。这适合生成一次性结果、备份和制品文件。

确实需要覆盖某个文件时，可以使用 `>|`：

```bash
echo "new data" >| result.txt
```

关闭该选项使用：

```bash
set +C
```

## `set -a`：自动导出后续变量

`set -a` 对应：

```bash
set -o allexport
```

开启后，新赋值或修改的变量会自动成为环境变量，可以被子进程读取：

```bash
set -a
. ./app.env
set +a

./start-app
```

这个写法常用于加载由简单 `KEY=value` 组成的环境配置文件。

但要注意，点命令会把文件当成 Shell 代码执行，并不只是解析普通的 `.env` 文本。只有在配置文件来源可信、内容符合 Shell 赋值语法时才能这样使用。另外，`set -a` 可能导出本来只想在脚本内部使用的变量，所以加载完成后应及时用 `set +a` 关闭。

## `set -E`：让 `ERR` trap 在更多上下文中继承

`set -E` 对应：

```bash
set -o errtrace
```

如果脚本使用 `trap ... ERR` 记录错误，`set -E` 会让 `ERR` trap 被 Shell 函数、命令替换和子 Shell 继承：

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

trap 'echo "错误：${BASH_SOURCE[0]}:${LINENO}，退出码 $?" >&2' ERR

build() {
    false
}

build
```

它适合需要统一错误日志的较复杂 Bash 脚本。不过，`ERR` trap 与 `set -e` 有相似的条件例外，不能替代显式错误处理。

## `set --`：设置脚本的位置参数

`set` 不只用于修改选项，还能设置 `$1`、`$2` 等位置参数：

```bash
set -- production app.yaml 3

echo "$1"  # production
echo "$2"  # app.yaml
echo "$3"  # 3
echo "$#"  # 3
```

其中 `--` 表示选项到此结束。即使后面的值以减号开头，也会被当成普通参数：

```bash
set -- "-n" "value"
printf '第一个参数：%s\n' "$1"
```

它适合把命令输出或解析结果转换成位置参数。不过不要用未引用的命令替换处理可能包含空格或通配符的数据：

```bash
# 数据包含空格时可能被错误拆分
set -- $(some_command)
```

在 Bash 中，复杂数据通常更适合使用数组。

## 常用参数对照表

| 写法 | 长选项 | 作用 | 常见场景 |
| --- | --- | --- | --- |
| `set -e` | `errexit` | 未处理的命令失败时通常退出 | 构建、部署、CI |
| `set -u` | `nounset` | 读取未定义变量时报错 | 配置和参数校验 |
| `set -x` | `xtrace` | 输出展开后执行的命令 | 调试、CI 排障 |
| `set -o pipefail` | `pipefail` | 暴露管道中任一命令的失败 | 数据处理、构建管道 |
| `set -n` | `noexec` | 读取但不执行命令 | 基础语法检查 |
| `set -f` | `noglob` | 关闭文件名通配符展开 | 原样处理模式文本 |
| `set -C` | `noclobber` | 防止 `>` 覆盖已有文件 | 制品和备份生成 |
| `set -a` | `allexport` | 自动导出变量 | 加载可信环境配置 |
| `set -E` | `errtrace` | 让 `ERR` trap 在更多上下文继承 | 统一错误日志 |
| `set --` | 无 | 重设位置参数 | 参数解析和数据拆分 |

## 一个实用的 Bash 脚本模板

对于构建、部署和 CI 脚本，可以从下面这个模板开始：

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

trap 'echo "执行失败：${BASH_SOURCE[0]}:${LINENO}，退出码 $?" >&2' ERR

: "${APP_ENV:?必须设置 APP_ENV}"

main() {
    local config_file=${1:-app.yaml}

    if [[ ${DEBUG:-0} == 1 ]]; then
        set -x
    fi

    echo "环境：$APP_ENV"
    echo "配置：$config_file"
    ./build.sh "$config_file"
}

main "$@"
```

这不是所有脚本都必须照搬的固定答案。简单的交互脚本可能需要允许某些命令失败；用于探测系统状态的脚本也可能频繁依赖非零退出码表达“没有找到”。遇到这类场景，应使用 `if` 或明确保存退出状态，而不是为了让脚本继续运行就在大段代码外包一层 `set +e`。

## 最后怎么选

通常可以按下面的思路决定：

- 希望意外失败尽早停止，使用 `set -e`，同时显式处理预期失败；
- 希望尽早发现变量名拼错和缺少配置，使用 `set -u`；
- 脚本中使用管道并且任何一步都不能失败，使用 `set -o pipefail`；
- 需要排查实际执行过程，短时间使用 `set -x`，并保护密钥；
- 需要统一捕获函数等位置的错误，可结合 `set -E` 和 `ERR` trap；
- 其他选项按具体需求开启，用完后通过对应的 `set +...` 关闭。

一句话总结：`set` 参数是用来暴露错误和约束脚本行为的工具，不是错误处理的替代品。理解每个选项的边界，再配合参数校验、条件判断和清晰的错误信息，脚本才会真正可靠。
