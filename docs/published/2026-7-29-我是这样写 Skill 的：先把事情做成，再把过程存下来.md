# 我是这样写 Skill 的：先把事情做成，再把过程存下来

我写 Skill，并不是先坐下来设计目录、定义规范、编写 SKILL.md。

我的方法其实很朴素：先用自然语言告诉 AI，我现在有一个什么问题，希望最后得到什么结果；让 AI 一步一步完成；我亲自检查效果，发现问题就继续反馈；AI 再修改、再运行，我再检查。这样反复迭代，直到结果真的可用。

等整个流程跑通以后，我才会让 AI 回过头来，把已经验证过的步骤、工具、注意事项和验收方法整理成一个 Skill，保存起来供下次复用。

整个过程可以概括成一句话：

~~~text
自然语言描述需求 -> AI 动手实现 -> 我检查结果 -> 继续反馈迭代
                    -> 效果满意 -> AI 整理流程 -> 保存为 Skill
~~~

对我来说，Skill 不是工作的起点，而是一次成功协作的存档。

## 先说概念：Skill 是什么

从形式上说，Skill 是一个可以被 AI 按需加载的能力目录。它通过名称和描述告诉 AI 什么时候使用，再通过 SKILL.md、脚本、参考资料和素材告诉 AI 应该怎样完成任务。

但 Skill 不是聊天记录，也不只是一个很长的提示词。聊天里会有试错、临时判断和只适用于当次任务的细节；Skill 保存的是从这些过程里筛选出来的稳定部分。

按照我的方法，Skill 可以理解成“已经用真实结果验证过的协作流程”。第一次遇到问题时，我和 AI 共同探索；下一次遇到同类问题时，AI 读取 Skill，直接从已经验证过的方法开始。

## 一、先别急着写 Skill，先把需求说清楚

我通常从一个确定、具体的需求开始。这里的“确定”不是要求我提前知道技术方案，而是我要能说清楚现状、问题和想要的结果。

以 generate-kid-coding-video 为例，我最开始面对的是一个已经存在的视频脚本：

~~~text
项目里有一个生成视频的脚本 scripts/kid_coding_video.py。
它生成的 narration.txt 没有清晰断句，导致视频字幕被动截断到下一屏。

我希望：
1. narration.txt 按自然语义换行断句；
2. 视频字幕严格按照 narration.txt 的断句显示；
3. quiz.txt 根据文章“一起改改看”自动生成一道完整的题和答案；
4. 最后把这套视频生成过程做成一个 Skill。
~~~

这段需求里没有指定应该修改哪个函数，也没有规定必须采用哪种字幕算法。因为这些是 AI 可以检查代码后决定的实现细节。

但它给出了四个重要信息：

- 已有基础：项目不是从零开始，已经有 kid_coding_video.py；
- 当前问题：字幕断句不清晰；
- 目标结果：旁白、字幕和 Quiz 都要正确生成；
- 最终意图：流程跑通后要沉淀成 Skill。

我发现，这种描述比一开始就要求“帮我设计一个视频生成 Skill”更有效。因为 AI 有真实脚本、真实文章和真实产物可以检查，不需要凭空猜测流程。

## 二、让 AI 一步一步完成，不要只让它给方案

需求说完以后，我会让 AI 直接查看项目并开始做，而不是只输出一份实现计划。

在这个案例中，AI 实际需要完成的事情包括：

1. 阅读 scripts/kid_coding_video.py，理解文章、旁白、字幕和视频之间的关系；
2. 找到课程 Markdown 中的“一起改改看”；
3. 修改旁白生成逻辑，让 narration.txt 按句子或分句换行；
4. 让每个非空旁白行成为一段有独立时间范围的字幕；
5. 从“先预测”和“揭晓”中提取完整 Quiz；
6. 增加准备、检查、渲染等可重复执行的入口；
7. 实际生成一节课的视频，验证结果。

这里的关键是“实际生成”。如果 AI 只修改代码，没有跑真实课程，那么很多问题根本不会出现。

例如，字幕长度测试可以证明换行函数工作正常，但它无法证明 Quiz 插入后，字幕仍然对应正确的画面。只有生成真实视频，才能看到最终效果。

## 三、我负责检查效果，AI 负责继续修正

AI 完成第一版之后，我不会因为它说“测试通过”就认为任务结束。我会打开它生成的文件，按照实际使用方式检查。

这个视频 Skill 的迭代过程很有代表性。

### 第一次检查：先看文本产物

我先检查：

- narration.txt 是否真的按自然语义换行；
- 一行字幕是否过长；
- 人工修改后的换行能否保留；
- quiz.txt 是否包含问题、至少三个选项、答案、解释和停顿时间；
- Quiz 内容是否忠于文章“一起改改看”。

如果旁白读起来不自然，我会直接修改 narration.txt，然后要求 AI 重新生成视频。这也是为什么旁白文件要成为一个可编辑的中间产物，而不是藏在脚本内部。

### 第二次检查：用真实课程生成视频

接着，我让 AI 使用这个 Skill 生成第 6 课视频。

视频生成涉及 Edge TTS 和覆盖旧文件，这时 AI 会向我确认是否允许把旁白发送到外部服务，以及是否允许覆盖已有视频。我确认以后，它才继续执行。

这一点也会被保留在成熟流程中：哪些步骤是本地只读，哪些步骤需要网络，哪些操作会覆盖文件，都应该在执行前说清楚。

### 第三次检查：发现字幕和画面对不上

视频生成后，我发现“一起改改看”附近几屏的字幕与画面不一致。

这时我的反馈并不复杂：

~~~text
“一起改改看”的几节字幕和内容对不上了，你检查下。
~~~

我不需要提前判断是旁白编号错了、Quiz 插入错了，还是画面分页错了。AI 应该根据实际文件和成片继续排查。

排查后发现，问题并不只是 narration.txt。生成器会在文章内容中插入 Quiz 题目屏和答案屏，但原文章的“揭晓”页仍然保留在后面。插入后，旁白已经进入“动手任务”，画面却还停留在“答案揭晓”，于是发生错位。

这个问题如果只改旁白，也能让某几屏暂时“听起来一致”，但课程顺序仍然是错的。最终的正确修复是：

- Quiz 答案屏负责展示揭晓、输出和解释；
- 删除后续重复的揭晓内容；
- 保留真正的动手修改任务；
- 再保留下一步的报错实验；
- 按 Quiz 插入后的最终屏序重新检查字幕。

### 第四次检查：不能只看脚本成功

AI 修正后重新生成了视频，但我需要确认它真的修好了，而不只是“又生成了一遍”。

因此，最后的检查包括：

1. 运行逐屏对照，检查画面正文与旁白语义；
2. 确认最终顺序是“预测、Quiz 题目、Quiz 答案、动手任务、下一步实验”；
3. 完整解码 MP4，确认视频流和音频流都正常；
4. 在 Quiz 附近抽帧，直接查看画面正文和底部字幕；
5. 确认检查的是最后一次修改后重新生成的视频。

到这里，这次需求才算真正完成。

## 四、我如何给 AI 反馈

这套方法并不要求一次写出完美提示词。更重要的是每轮反馈都指向一个可以检查的结果。

我常用的反馈有四种。

### 1. 指出具体位置

~~~text
第 17、18 屏附近不对。
“一起改改看”后面的字幕和画面不一致。
~~~

位置越具体，AI 越容易缩小检查范围。但修复后仍然要检查周围屏幕，因为问题可能来自前面的插入或分页。

### 2. 描述看到的现象

~~~text
画面还在讲答案揭晓，字幕已经在讲动手修改。
~~~

这种反馈比直接猜“数组索引加错了”更有用。现象是确定的，具体原因可以交给 AI 从代码和数据中判断。

### 3. 明确是否满意

~~~text
断句可以了，但 Quiz 后两屏仍然不对。
这一版顺序正确，可以重新生成完整视频。
~~~

AI 不应该自行把“局部修复完成”理解成“整体效果满意”。我会明确告诉它下一轮应该继续修改，还是可以进入生成阶段。

### 4. 对外部操作明确授权

~~~text
同意发送旁白到 Edge TTS，并覆盖第 6 课旧视频。
~~~

网络调用、覆盖已有文件和长时间渲染都不是普通的文本修改。把授权说清楚，整个协作过程会更可控。

## 五、什么时候才适合整理成 Skill

我不会在第一次提出需求时，就急着让 AI 写完整 Skill。因为这时我们通常还不知道真正的难点在哪里。

我会等到下面几件事基本确定以后再存档：

- 已经用至少一个真实案例跑通过完整流程；
- 输入、输出和中间文件已经明确；
- 关键命令能够重复执行；
- 我已经亲自检查过最终效果；
- 常见失败至少出现过一次，并且已经找到正确处理方式；
- 我能说清楚什么状态才算完成。

这时再让 AI 整理 Skill，它记录的是一条走通过的路，而不是一份想象中的方案。

我会直接这样说：

~~~text
现在这个流程已经符合预期。
请把我们从准备文章、生成 narration.txt 和 quiz.txt、检查最终屏序、
调用 TTS、渲染视频到抽帧验收的整个流程整理成一个 Skill。

把已经验证过的脚本作为唯一实现，不要复制一份；
写清楚触发场景、执行顺序、常见错误、修正分支和完成标准；
保存到 Codex 可以自动发现的 skills 目录，并运行校验器。
~~~

AI 可以根据这段已经发生过的协作历史，提取出真正值得复用的部分。

## 六、Skill 需要保存什么

整理 Skill 不是把完整聊天记录复制进去。真正值得保存的，通常是下面这些内容。

### 1. 什么时候使用

例如：生成少儿编程课程视频、准备断句旁白、生成互动题、排查字幕与画面错位、输出横屏或竖屏视频。

这些触发场景要写进 SKILL.md 的 description，因为系统会先根据名称和描述判断是否需要加载 Skill。

### 2. 已经验证过的执行入口

这个案例里，核心实现仍然是项目中的脚本：

~~~bash
python scripts/kid_coding_video.py \
  --project-root <course-project> --lesson <number> <mode>
~~~

Skill 不需要复制一份 kid_coding_video.py。它只需要告诉 AI 去哪里找到脚本，以及不同阶段应该使用什么参数。

### 3. 输入、输出和中间产物

例如：

- 输入是课程 Markdown；
- narration.txt 是可人工编辑的旁白，也是语音和字幕的共同来源；
- quiz.txt 保存完整互动题；
- MP4 是最终产物；
- narration.txt.bak 用于文章变化后找回仍然有效的人工修改。

### 4. 不能跳过的顺序

成熟流程被整理成三个阶段：

~~~text
prepare-only：先生成文本，供人检查和修改
check-narration：按最终画面顺序检查旁白
render：检查通过后再调用 TTS 和渲染视频
~~~

这样可以在成本最低的时候发现问题，避免每改一句话都重新生成九分钟视频。

### 5. 从真实失败中得到的规则

这是 Skill 最有价值的部分。例如：

- 检查对象必须是 Quiz 插入后的最终屏序，不能只看文章原始分页；
- Quiz 答案屏已经承担揭晓时，后面不能再重复文章揭晓页；
- 画面映射错了，要修改生成逻辑，不能改字幕去迁就错误画面；
- Quiz 后至少继续检查两个内容屏；
- 脚本退出码为 0 不等于内容已经正确。

这些规则不是提前想出来的，而是在真实使用中踩过问题以后沉淀下来的。

### 6. 完成标准

Skill 要明确告诉下一次执行它的 AI：什么时候可以向用户说“完成了”。

这个视频 Skill 的完成标准包括：文本结构检查通过、最终屏序正确、MP4 有正常音视频流、视频可以完整解码、关键位置抽帧后字幕与画面一致。

## 七、Skill 的基本目录结构

等流程稳定以后，再落到具体目录上就很简单了：

~~~text
generate-kid-coding-video/
├── SKILL.md              # 必需：触发条件和执行流程
├── agents/
│   └── openai.yaml       # 推荐：界面名称、简介和默认提示
├── scripts/              # 可选：需要随 Skill 分发的确定性脚本
├── references/           # 可选：较长的规则和参考资料
└── assets/               # 可选：模板、图片、字体等产物素材
~~~

不是每个 Skill 都需要所有目录。

当前的 generate-kid-coding-video 只需要：

~~~text
generate-kid-coding-video/
├── SKILL.md
└── agents/
    └── openai.yaml
~~~

因为真正的视频脚本已经属于课程项目。把它再复制到 Skill 目录，只会产生两个需要同步维护的版本。

### SKILL.md

SKILL.md 是唯一必需的文件。开头是 YAML frontmatter：

~~~yaml
---
name: generate-kid-coding-video
description: Generate narrated kid-coding videos with sentence-broken captions,
  final-screen-order alignment, and automatically extracted quizzes. Use when
  generating lesson videos or troubleshooting subtitle-to-picture mismatches.
---
~~~

name 使用小写字母、数字和连字符，目录名与它一致。

description 同时说明“能做什么”和“什么时候使用”。触发条件不能只写在正文里，因为正文是在 Skill 被触发后才读取的。

正文不需要复述整个开发故事。它只保留下一次执行真正需要的内容：

- 使用哪个脚本；
- 按什么顺序执行；
- 检查哪些文件；
- 遇到不同错误改哪一层；
- 怎样验证最终产物。

### agents/openai.yaml

这个文件用于 Skill 在界面中的展示：

~~~yaml
interface:
  display_name: "生成少儿编程讲解视频"
  short_description: "从课程文章生成逐屏对齐的断句字幕、互动问答和讲解视频"
  default_prompt: "使用 $generate-kid-coding-video 生成字幕与画面对齐的课程视频。"
~~~

它是界面元数据，不应代替 SKILL.md 中的执行流程。

### scripts、references 和 assets

只有确实需要时才创建：

- 重复执行、结果必须稳定的代码放进 scripts/；
- 只有特定场景才需要阅读的长规则放进 references/；
- 会进入最终产物的模板和素材放进 assets/。

不要为了目录完整而创建空文件，也不要额外加入 README、安装指南、更新日志等与 Skill 执行无关的文档。

## 八、让 AI 创建并校验 Skill

当流程已经跑通，可以让 AI 使用 skill-creator 创建正式目录。默认可以保存到 ~/.codex/skills，让 Codex 自动发现。

底层初始化命令类似这样：

~~~bash
python ~/.codex/skills/.system/skill-creator/scripts/init_skill.py \
  generate-kid-coding-video \
  --path ~/.codex/skills \
  --interface 'display_name=生成少儿编程讲解视频' \
  --interface 'short_description=从文章生成逐屏对齐的课程视频' \
  --interface 'default_prompt=使用 $generate-kid-coding-video 生成课程视频。'
~~~

生成后，要让 AI 阅读实际 Skill，确认 agents/openai.yaml 与 SKILL.md 一致，并运行：

~~~bash
python ~/.codex/skills/.system/skill-creator/scripts/quick_validate.py \
  ~/.codex/skills/generate-kid-coding-video
~~~

校验器只能检查名称、frontmatter 和目录结构。真正的验收仍然是再次使用这个 Skill 完成一项真实任务。

## 九、Skill 也要继续迭代

Skill 保存以后并不是结束。下一次使用时，如果又遇到新问题，我还是采用同样的循环：

~~~text
使用 Skill -> 检查结果 -> 发现新问题 -> 让 AI 修正
           -> 重新验证 -> 把新经验更新回 Skill
~~~

第 6 课字幕错位就是一次典型的 Skill 迭代。

最初的 Skill 已经会生成断句旁白和 Quiz，但它还没有足够强调 Quiz 插入后的最终画面顺序。问题修好以后，我又让 AI 优化 generate-kid-coding-video，把下面几条写成强制流程：

- 必须按最终屏序逐屏检查；
- 必须检查 Quiz 题目、答案和后续两个内容屏；
- 不能用修改旁白掩盖画面映射错误；
- 渲染后必须抽帧检查成片；
- 只有结构检查和视觉检查都通过，才能报告完成。

这正是 Skill 的意义：把这一次花时间定位的问题，变成下一次自动执行的检查步骤。

## 十、几段可以直接使用的提示词

### 开始一个新需求

~~~text
项目里已经有 ______。
现在的问题是 ______。
我希望最终得到 ______。

请先检查现有项目，再一步一步实现并验证。
不要只给方案；先完成一个可以让我实际检查的版本。
~~~

### 对第一版给反馈

~~~text
我检查了结果，______ 部分已经可以。
但在 ______ 位置，实际看到的是 ______，我希望是 ______。

请先定位原因，再修正并重新生成这一部分需要验证的产物。
~~~

### 效果满意后整理 Skill

~~~text
现在这个流程已经达到预期。

请把我们已经验证通过的完整流程整理成一个 Skill：
1. 写清楚触发场景；
2. 复用现有脚本，不重复实现；
3. 保存输入、输出、中间产物和执行顺序；
4. 加入我们实际遇到过的失败模式和修正分支；
5. 写清楚完成标准；
6. 保存到 Codex 能自动发现的目录；
7. 运行 Skill 校验器，并用一个真实任务再次验证。
~~~

### 使用中发现新问题

~~~text
这个 Skill 在 ______ 场景下出现了 ______ 问题。
请先修正实际任务并验证结果。
确认修复有效后，再把这次新经验更新回 Skill，避免以后重复出现。
~~~

## 结语

我写 Skill 的方法，没有把“写 Skill”当成一个独立的文档工作。

我先用自然语言把一个确定需求交给 AI，让它在真实项目里一步一步做出来；我检查真实结果，继续告诉它哪里不满意；AI 再修改，我再检查。等结果稳定以后，再让 AI 把这段已经走通的协作过程压缩成一个可复用的 Skill。

所以，Skill 里最重要的内容，并不是一开始能想到多少规范，而是最后留下了多少经过实际验证的经验：哪些步骤有效，哪些地方容易出错，出错时应该改哪一层，以及怎样确认结果真的正确。

先把事情做成，再把过程存下来。下一次，同类任务就不需要从头摸索了。
