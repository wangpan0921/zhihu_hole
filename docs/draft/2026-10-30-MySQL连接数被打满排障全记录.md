# 把 MySQL 最大连接数从 1000 加到 3500，然后数据库挂了：一次连接数被打满的排障全记录

## 先说结论，省你时间

如果你正被 `ERROR 1040 (HY000): Too many connections` 折磨，第一反应可能是「把 `max_connections` 调大点不就行了」。

这篇文章想告诉你的恰恰相反：**调大连接数常常不是解药，而是把问题往后拖、还顺手埋了一颗更大的雷。** 我把一次真实的排障从头到尾记录下来——从「加大连接数」开始，到最后发现真凶是 **反向 DNS 解析超时 + 客户端疯狂建连接**，中间踩的坑、用的命令、每一步的判断依据，都在这里。

读完你会掌握一套通用的排查方法：当数据库连接数出问题时，怎么一步步从「现象」挖到「真因」，而不是盲目调参。

---

## 一、问题背景

一个给内部用的 MySQL 库（存 GPU 监控指标等数据），某天开始频繁报：

```
ERROR 1040 (HY000): Too many connections
```

最初的处理很直觉：当时 `max_connections = 1000`，查到历史峰值 `Max_used_connections = 1001`——正好顶格 +1，说明确实撞到了天花板。于是把上限从 **1000 调到 3500**。

一开始看起来有效：调完之后峰值涨到 1182，确实接住了原本会被拒的那批连接。但**两周后，3500 也被打满了**，而且这次更惨——连 `root` 都登不进去，整个库处于「谁都连不上」的拒绝服务状态。

这就引出了这篇文章真正想讲的问题：**连接数为什么会无限涨？加大上限到底对不对？**

---

## 二、几个必须先搞懂的基础概念

排查之前，先把几个容易混淆的概念讲清楚，否则你会和我一样走弯路。

### 1. `max_connections` 只是一个「上限数字」，不预占内存

很多人担心「把连接数从 1000 加到 3500，内存是不是要爆」。其实不会。

`max_connections` 只是规定「最多允许多少连接进来」，它**不会预先分配 3500 个连接的内存**。内存只在连接真正进来、真正干活时才按需分配。打个比方：把停车场车位上限从 1000 改成 3500，不会凭空多出车来占地方，只有真开进来那么多车才会占满。

所以调完之后如果你 `top` 看内存没变化——**那是正常的，不代表没生效**。

### 2. 怎么确认配置真的生效了

```sql
SET GLOBAL max_connections = 3500;        -- 立即生效，不用重启，不断开现有连接
SHOW VARIABLES LIKE 'max_connections';     -- 必须用这个确认，而不是看内存
```

注意两个坑：

- `SET GLOBAL` 只改**运行时内存里的值**，配置文件 `my.cnf` 不动。一旦 MySQL 重启就会打回原值。要长期生效必须同时改 cnf。
- 有个隐藏坑：MySQL 启动时会根据连接数推算需要的文件描述符数。如果操作系统给的 `open_files_limit` / `ulimit -n` 不够大，MySQL 会**悄悄把你设的 3500 砍小**。所以 `SET` 完一定要用 `SHOW VARIABLES` 复核，看是不是真的 3500。

### 3. 三个关键指标的区别

| 指标 | 含义 | 查法 |
|------|------|------|
| `Threads_connected` | **当前实时**连接数 | `SHOW GLOBAL STATUS LIKE 'Threads_connected';` |
| `Max_used_connections` | 启动以来的**历史峰值**（只增不减） | `SHOW GLOBAL STATUS LIKE 'Max_used_connections';` |
| `max_connections` | 允许的**上限** | `SHOW VARIABLES LIKE 'max_connections';` |

`Max_used_connections` 是个「历史水位线」。如果它卡在 `上限 + 1`，几乎可以断定你撞过天花板、有连接被拒过。

## 三、第一个判断陷阱：「3500 又不够用了」是真的吗？

两周后 3500 被打满，最自然的想法是「业务涨了，3500 也不够，再加到 5000 吧」。

**但停下来算一笔账**：峰值从 1182 涨到打满 3500，两周内多出 2300+ 个连接。业务量不可能两周翻一倍以上。这个数字对不上「真实业务增长」，更像是**连接在持续堆积却不释放**——也就是连接泄漏或某个客户端在疯狂建连接。

> 这是排障里一个很重要的思维习惯：**拿到一个数字，先问它「合不合理」，而不是直接接受它。** 2300 个新连接两周内冒出来，这个增速本身就是线索。

所以结论是：**这次不能再靠调大上限解决。继续加到 5000、10000，只会把爆炸时间推迟几天，而且每加一次都在逼近真正的内存 OOM 红线。必须找出是谁占着连接不放。**

---

## 四、排查方法论：连接数问题怎么一步步挖到根

这是全文最有价值的部分。当连接数出问题时，按这个顺序查。

### 第 1 步：连进去看「谁在占连接」（如果还能连）

```sql
-- 按来源 IP 分组，看连接都来自哪些机器（最关键的一步）
SELECT SUBSTRING_INDEX(host,':',1) AS ip, COUNT(*) AS cnt
FROM information_schema.processlist
GROUP BY ip ORDER BY cnt DESC LIMIT 20;

-- 按用户+状态分组，看是不是大量 Sleep 连接堆积
SELECT user, command, COUNT(*) AS cnt
FROM information_schema.processlist
GROUP BY user, command ORDER BY cnt DESC;

-- 看 Sleep 连接挂了多久（泄漏的典型特征：大量长时间 Sleep）
SELECT id, user, host, time, state
FROM information_schema.processlist
WHERE command='Sleep' ORDER BY time DESC LIMIT 20;
```

怎么读结果：

- **某个 IP 占了绝大多数连接** → 那台机器/那个服务就是源头，顺着 IP 去查。
- **一大堆 Sleep 状态、且挂了几千秒** → 实锤连接泄漏：程序建了连接干完活不关，一直挂着。

### 第 2 步：连不进去时，从操作系统侧看（关键技巧）

这次遇到的麻烦是：**连 root 都登不进去，上面那些 SQL 根本没法执行。** 很多人到这一步就只剩「重启」一条路了。

但其实有个更安全的办法：**不连 MySQL，直接从操作系统看 TCP 连接。** 前提是你能登录数据库所在的机器。

```bash
# 找到 mysqld 进程
pidof mysqld

# 看它实际监听哪个端口（不要想当然，后面会讲为什么）
ss -tlnp | grep -i mysql

# 统计连到 MySQL 端口的客户端 IP，按连接数降序
ss -tnp 2>/dev/null | grep ':3306' | awk '{print $5}' \
  | sed 's/:[0-9]*$//' | sort | uniq -c | sort -rn | head -20
```

这一步不需要连进 MySQL，就能从 TCP 层告诉你：是某一个 IP 建了几千条连接（某个服务在狂连），还是几千个不同 IP 各连一点（真实并发）。

> **踩坑提醒**：我一开始假设端口是某个值去 grep，结果一条都没返回，差点以为「连接没堆积」。后来才发现**端口假设错了**——实际监听的是 3306。教训是：排查时不要想当然预设端口/路径，先用 `ss -tlnp | grep mysql` 查清楚真实监听端口。

### 第 3 步：看错误日志——信息量最大的一手证据

前面都是「从外部观察」，而错误日志是 MySQL 自己说「我为什么拒绝连接」。这一步常常被忽略，但它往往直接给出答案。

```bash
tail -50 /var/log/mysql/error.log
```

这次日志里刷屏的是这一句，成了破案的关键：

```
[Warning] [MY-010055] [Server] IP address '10.70.x.x' could not be resolved: Name or service not known
```

## 五、真凶浮出水面：反向 DNS 解析超时

上面那条日志是什么意思？

**MySQL 默认在每次接受新连接时，会对客户端 IP 做一次「反向 DNS 解析」**（把 IP 转成主机名，用于基于主机名的权限校验）。如果 DNS 服务器解析不了这些内网 IP，每次解析都要**等到超时**才放弃。

问题就出在这里：**解析超时的这段时间里，连接线程被占着、卡在握手阶段不释放。** 大量客户端同时连进来，每一条都卡在 DNS 超时上，连接线程迅速堆满 3500，于是所有人（包括 root）都连不进去。

证据链串起来了：

| 观察到的现象 | 说明 |
|------|------|
| 几个 IP 各占约 200 条连接 | 这些 IP 正是日志里反复「解析失败」的那几个，在疯狂重连、每条都卡在 DNS |
| 错误日志每秒刷数条 `could not be resolved` | 每个新连接都在做反向 DNS，且全部失败、全部走到超时 |

### 插一个小坑：日志时间「对不上」？是时区

排查中一度困惑：日志时间戳 `11:39`，而当前时间是 `19:53`，差了 8 小时，怀疑日志是不是旧的。

其实注意日志时间结尾那个 **`Z`**——它表示 **UTC 时间**。MySQL 错误日志默认用 UTC 记录。`11:39 UTC + 8 小时 = 19:39 北京时间`，和当前只差十几分钟，**完全是实时日志**。

> 小知识：遇到时间对不上，先看是不是 UTC 和本地时区（CST = UTC+8）的差异，别急着否定证据。

### 根治方法：关掉反向 DNS 解析

MySQL 有个参数 `skip_name_resolve`，开启后**完全不做反向 DNS，直接用 IP 鉴权**：

```ini
[mysqld]
skip_name_resolve = ON
```

- 开启后新连接不再卡 DNS 超时，握手瞬间完成。
- 这个参数是**只读的**，不能动态 `SET GLOBAL`，必须写进 cnf 后重启才生效。
- 注意副作用：开启后，权限表里用「主机名」（而非 IP/通配符）授权的账号会失效。开启前确认没有这类关键账号。

其实**生产库本来就推荐默认开 `skip_name_resolve`**，既省掉每次连接的 DNS 开销，也避免 DNS 故障拖垮数据库。这是比「修 DNS」更彻底的做法。

## 六、病根其实是两层：DNS 只是放大器

排查继续深入时，日志里又冒出一条不一样的：

```
Plugin mysqlx reported: '13: Error initializing session: Too many connections'
```

而且 DNS 解析失败的日志停了一段时间——因为连接已经满到**新连接根本进不来**，连做 DNS 解析的机会都没有了。

这让判断更完整了：

- **真正的病根**：有大量客户端在**持续疯狂建连接**（那几个 IP 各占几百条），把连接数撑满。
- **DNS 解析超时是放大器**：它让每条连接释放变慢、握手变慢，加速了连接堆积。

两者叠加，才造成了「连 root 都进不去」的雪崩。所以完整的解法是**两手都要抓**：关 DNS（减负）+ 找到并压住狂连的客户端（治本）。只关 DNS 不够，因为客户端还在源源不断地连。

## 七、紧急恢复：一个容器化部署的大坑

当时想重启 MySQL 恢复，又发现一个关键事实：`pidof mysqld` 返回 **1**。

**PID = 1 意味着 mysqld 是这个容器的主进程**——这台「机器」其实是个 K8s Pod。这带来两个重要结论：

1. 容器里通常没有 `systemctl`，`systemctl restart mysql` 用不了。
2. **千万不要在容器里 `kill 1`**——那等于杀掉整个容器主进程，容器会被判定退出重建，风险极高。

在容器场景下「重启 MySQL」的正确姿势：

- **优先**：先试本机 Unix socket 连接。socket 和 TCP 是两套路径，TCP 名额满了，socket 常常还能挤进去：
  ```bash
  mysql -uroot -p -S /var/run/mysqld/mysqld.sock
  ```
  能连进去就不用重启，直接临时抬高上限腾出名额、再 KILL 掉大户连接。
- **兜底**：通过 `kubectl delete pod <pod名>`（在有集群权限的跳板机上执行，不是在 MySQL 容器里），让控制器自动重建 = 一次干净重启。

还有个容器化的隐患要留意：**如果 cnf 文件不在持久化卷上，Pod 重建后配置可能被重置回镜像默认值**——你辛苦改的 `max_connections=3500` 可能一夜回到解放前。重启后务必复查：

```bash
grep -E 'max_connections|skip_name_resolve' /etc/mysql/mysql.conf.d/mysqld.cnf
```

## 八、治本之后：怎么监控，防止复发

救火之后更重要的是别再被同一块石头绊倒。核心思路一句话：**别靠不断调大 max_connections，要靠监控 + 告警提前发现。**

### 轻量方案：一个 cron 监控脚本

原理很简单——每分钟采集一次连接数，算出占上限的百分比，到 70% 预警、到 85% 严重告警并自动 dump 出 TOP 来源 IP（故障时你立刻知道是谁）。核心逻辑：

```bash
threads_connected=$(mysql ... -N -B -e \
  "SHOW GLOBAL STATUS LIKE 'Threads_connected';" | awk '{print $2}')
max_conn=$(mysql ... -N -B -e \
  "SHOW VARIABLES LIKE 'max_connections';" | awk '{print $2}')
pct=$(( threads_connected * 100 / max_conn ))

if [ "$pct" -ge 85 ]; then
  echo "[CRIT] 连接数达 ${pct}%，TOP 来源 IP："
  mysql ... -e "SELECT SUBSTRING_INDEX(host,':',1) ip, COUNT(*) c
    FROM information_schema.processlist GROUP BY ip ORDER BY c DESC LIMIT 15;"
fi
```

两个部署要点：

1. **密码别写进脚本**，用环境变量传（通过 `MYSQL_PWD` 给客户端，避免出现在 `ps` 进程列表）。
2. **crontab 里别用 `nohup ... &` 后台方式**，否则 cron 不回收子进程，会堆积大量僵尸进程（`<defunct>`）。直接让 cron 同步执行即可。

### 更专业的方案：mysqld_exporter + Prometheus + Grafana

如果已有 Prometheus 监控体系，用 `mysqld_exporter` 把 `mysql_global_status_threads_connected` 等指标吐出去，在 Grafana 配 85% 告警。比 cron 脚本更实时、有历史曲线、告警也更成熟。

## 九、总结：这次排障教给我的事

把整个过程浓缩成几条可复用的经验：

1. **`Too many connections` 的第一反应不该是调大上限。** 先问「连接数增长合不合理」——不合理就是泄漏或狂连，调大只是拖延。
2. **排查顺序**：按来源 IP 分组看 processlist → 连不进去就从 OS 侧 `ss` 看 TCP 连接 → 最后（也最重要）看错误日志，它常常直接写明真因。
3. **错误日志是金矿。** 这次的真凶 `skip_name_resolve` 完全是日志刷屏刷出来的。
4. **生产库建议默认开 `skip_name_resolve`**，省 DNS 开销也避免 DNS 故障拖垮数据库。
5. **容器里 PID=1 的进程不能 `kill`**，重启要走 socket 连接或 `kubectl delete pod`；还要警惕配置没持久化、重建后丢失。
6. **治本靠监控告警，不靠调参。** 提前在 70%/85% 报警，并保留现场（TOP IP），比事后救火强太多。

最后一句：**调大一个参数往往是最容易的动作，也最容易让你停止思考。真正的问题，常常藏在「为什么需要调这么大」里。**
