# Linux 定时执行脚本的常用方法：cron、systemd timer 和 at 一次讲清

很多人第一次给 Linux 配置定时任务时，会直接搜索一条“每天凌晨执行脚本”的命令，复制粘贴后就结束了。真正遇到问题时才发现：脚本手动执行没问题，放到定时任务里却找不到命令；服务器关机了一晚，任务到底有没有补执行；同一个任务运行太慢，下一次又启动了一个副本。

Linux 里并不只有一种定时方式。不同工具解决的问题不同：`cron` 适合规则明确的周期任务，`systemd timer` 适合需要日志、依赖和失败重试的服务器服务，`at` 适合只执行一次的任务，`anacron` 则适合不保证一直开机的机器。

> 一句话记住：固定周期先看 `cron`，生产服务优先考虑 `systemd timer`，只执行一次用 `at`，经常关机的电脑考虑 `anacron`。

## 一、先把脚本准备好

不管使用哪种调度器，脚本本身都应先满足几个基本条件。下面以 `/opt/jobs/backup.sh` 为例：

```bash
#!/usr/bin/env bash
set -euo pipefail

backup_dir="/data/backup"
mkdir -p "$backup_dir"
tar -czf "$backup_dir/app-$(date +%F).tar.gz" /srv/app
```

给脚本增加执行权限，并先手动执行一次：

```bash
chmod +x /opt/jobs/backup.sh
/opt/jobs/backup.sh
echo $?
```

`chmod +x` 中的 `+x` 表示增加执行权限；`echo $?` 查看上一条命令的退出码，`0` 通常表示成功。

定时任务里最好使用绝对路径，例如 `/usr/bin/tar`、`/usr/bin/date`，不要依赖交互式终端里的别名或当前目录。脚本还应自行创建需要的目录，并明确处理失败情况。

## 二、方法一：cron，最常见的周期调度器

### 1. cron 适合什么场景

`cron` 是 Linux 上最常用的周期任务工具，适合：

- 每天凌晨备份一次数据库；
- 每 5 分钟拉取一次数据；
- 每周清理日志或临时文件；
- 服务器上不需要复杂依赖的轻量脚本。

它的优点是配置简单、系统普遍自带；缺点是运行环境比较“简陋”，任务日志、失败重试和任务依赖需要自己补齐。

### 2. 编辑当前用户的任务

```bash
crontab -e
```

首次执行时，系统可能会让你选择编辑器。打开文件后增加一行：

```cron
30 2 * * * /opt/jobs/backup.sh >> /var/log/backup.log 2>&1
```

这行的含义是：每天凌晨 2 点 30 分执行脚本，把标准输出和错误输出都追加到 `/var/log/backup.log`。

查看当前用户的任务：

```bash
crontab -l
```

删除当前用户的全部任务：

```bash
crontab -r
```

`crontab -r` 没有逐条确认，误执行会删除当前用户的所有 cron 配置，使用前要确认目标用户。

### 3. root 任务和系统级配置

`crontab -e` 编辑的是当前用户的任务。需要以 root 或指定系统用户执行时，还可以使用：

```bash
sudo crontab -e       # 编辑 root 用户的 crontab
sudo crontab -u alice -e  # 编辑 alice 用户的 crontab，需要管理员权限
```

系统还支持 `/etc/crontab` 和 `/etc/cron.d/`。它们比用户 crontab 多一个“用户名”字段：

```cron
# /etc/crontab 或 /etc/cron.d/backup 中的格式
30 2 * * * root /opt/jobs/backup.sh >> /var/log/backup.log 2>&1
```

用户 crontab 是“5 个时间字段 + 命令”，系统级文件是“5 个时间字段 + 用户名 + 命令”。不要把两种格式混用，否则可能把用户名当成命令的一部分。`/etc/cron.d/` 中通常每个文件放一组相关任务，文件权限和命名也应遵循发行版的要求。

### 4. 五个时间字段怎么读

普通用户的 crontab 每行由五个时间字段和一条命令组成：

```text
分 时 日 月 星期 命令
```

| 字段 | 取值范围 | 示例 |
| --- | --- | --- |
| 分钟 | `0-59` | `30` 表示第 30 分钟 |
| 小时 | `0-23` | `2` 表示凌晨 2 点 |
| 日 | `1-31` | `1` 表示每月 1 日 |
| 月 | `1-12` | `6` 表示 6 月 |
| 星期 | `0-7` | `0` 和 `7` 通常都表示周日 |

几个常用符号：

- `*`：任意值，例如 `* * * * *` 表示每分钟执行；
- `,`：多个值，例如 `1,15` 表示每月 1 日和 15 日；
- `-`：连续范围，例如 `1-5` 表示周一到周五；
- `/`：间隔执行，例如 `*/5` 表示每 5 个单位执行一次。

常见写法如下：

```cron
# 每 5 分钟执行
*/5 * * * * /opt/jobs/check.sh

# 工作日 9:00 执行
0 9 * * 1-5 /opt/jobs/workday.sh

# 每周日凌晨 3:15 执行
15 3 * * 0 /opt/jobs/weekly.sh

# 每月 1 日和 15 日的 2:00 执行
0 2 1,15 * * /opt/jobs/half-month.sh
```

注释以 `#` 开头。`cron` 的时间精度通常是分钟，不能直接表达“每 30 秒执行一次”。

### 5. `@daily` 和 `@reboot`

对于简单周期，可以使用可读性更好的特殊写法：

```cron
@daily  /opt/jobs/daily.sh
@weekly /opt/jobs/weekly.sh
@reboot /opt/jobs/startup.sh
```

`@daily` 通常等价于每天 00:00 执行一次，但不同实现仍可能存在细节差异；如果需要严格表达凌晨 2 点，应写成 `0 2 * * *`。`@reboot` 在 cron 服务启动或系统启动后执行一次，适合启动辅助程序，但不等价于“服务健康检查”。

### 6. `cron` 里最容易踩的坑

#### 环境变量和 PATH 不同

交互式终端会加载 `.bashrc`、虚拟环境等配置，而 cron 通常不会。下面这行在终端里可能正常，在 cron 里却找不到 `python`：

```cron
0 * * * * python /opt/jobs/report.py
```

更稳妥的写法是使用解释器绝对路径，并显式设置工作目录：

```cron
0 * * * * cd /opt/jobs && /opt/venv/bin/python report.py >> /var/log/report.log 2>&1
```

也可以在 crontab 顶部声明环境变量：

```cron
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

不要假设 cron 会自动读取用户的 `.bashrc`。需要加载配置时，应在脚本中明确执行，例如 `source /opt/app/.venv/bin/activate`，更推荐直接调用虚拟环境中的绝对路径。

#### `%` 在 cron 命令里有特殊含义

在许多 cron 实现中，命令部分的 `%` 会被转换成换行，后面的内容作为标准输入传给程序。日期格式中的 `%F`、`%Y%m%d` 因此必须转义：

```cron
0 1 * * * /opt/jobs/export.sh >> /var/log/export-$(date +\%F).log 2>&1
```

如果不想记这个规则，可以把日期拼接放进脚本，crontab 只负责调用脚本。

#### 输出和权限

不重定向输出时，cron 可能尝试通过本地邮件发送执行结果，服务器未配置邮件服务时容易造成误解。通常建议显式记录日志：

```cron
*/10 * * * * /opt/jobs/check.sh >> /var/log/check.log 2>&1
```

`>>` 表示追加，`2>&1` 表示把标准错误合并到标准输出。写入 `/var/log` 往往需要 root 权限；普通用户可以写入自己的目录，例如 `/home/alice/logs/check.log`。

#### 防止任务重叠

如果脚本一次执行需要 20 分钟，却设置为每 5 分钟执行，cron 不会自动等待，可能同时启动多个副本。可以使用 `flock`：

```cron
*/5 * * * * /usr/bin/flock -n /tmp/check.lock /opt/jobs/check.sh >> /var/log/check.log 2>&1
```

`-n` 表示拿不到锁时立即退出。锁文件路径要让执行任务的用户可写；如果多个用户共享任务，应重新设计锁文件位置和权限。

## 三、方法二：systemd timer，更适合服务器服务

### 1. 为什么用 systemd timer

现代 Linux 发行版大多使用 `systemd` 管理服务。`systemd timer` 把“什么时候触发”和“触发后运行什么”分成两个单元：

- `.service`：定义要执行的脚本；
- `.timer`：定义执行时间和触发规则。

相比 cron，它更容易查看日志、设置依赖、限制权限，并且可以在机器关机错过任务后进行补执行。需要长期维护的生产任务，通常优先考虑这种方式。

### 2. 创建 service 单元

创建 `/etc/systemd/system/backup.service`：

```ini
[Unit]
Description=Backup application data

[Service]
Type=oneshot
ExecStart=/opt/jobs/backup.sh
# 可选：使用低权限用户执行，前提是该用户能访问脚本和数据
# User=backup
```

`Type=oneshot` 表示这是一个执行完就退出的一次性服务；`ExecStart` 指定启动命令。脚本应使用绝对路径，并确保可执行。

### 3. 创建 timer 单元

创建 `/etc/systemd/system/backup.timer`：

```ini
[Unit]
Description=Run application backup every day

[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true
Unit=backup.service

[Install]
WantedBy=timers.target
```

字段含义：

- `OnCalendar`：按日历时间触发，这里是每天 02:30；
- `Persistent=true`：如果机器关机时错过了触发时间，下一次启动后补执行一次；
- `Unit`：触发哪个 service，默认通常是同名的 `.service`；
- `WantedBy=timers.target`：允许通过 `systemctl enable` 加入系统的定时器集合。

启用并立即启动：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now backup.timer
```

`daemon-reload` 让 systemd 重新读取单元文件；`enable` 设置开机自动启用；`--now` 表示同时立即启动，不必再执行一次 `start`。

查看定时器和下次执行时间：

```bash
systemctl list-timers --all
systemctl status backup.timer
```

查看脚本输出和错误日志：

```bash
journalctl -u backup.service
journalctl -u backup.service -n 50 --no-pager
```

### 4. 常用的 systemd 时间写法

```ini
# 每天 02:30
OnCalendar=*-*-* 02:30:00

# 每周一至周五 09:00
OnCalendar=Mon..Fri *-*-* 09:00:00

# 开机 10 分钟后执行一次
OnBootSec=10min

# 上一次服务激活后 1 小时再次触发
OnUnitActiveSec=1h
```

`OnCalendar` 适合“几点几分”，`OnBootSec` 和 `OnUnitActiveSec` 适合“启动后多久”或“上次运行后多久”。多条触发规则可以同时存在。

为避免大量机器在同一秒同时执行，可以增加随机延迟：

```ini
RandomizedDelaySec=5min
```

### 5. systemd timer 的维护命令

```bash
sudo systemctl start backup.service       # 立即手动执行一次
sudo systemctl stop backup.timer          # 停止定时器
sudo systemctl disable backup.timer       # 取消开机启用
sudo systemctl restart backup.timer       # 修改后重启定时器
```

注意：启动 `backup.service` 是立即执行脚本，启动 `backup.timer` 才是启动定时调度。修改单元文件后，通常要先 `daemon-reload`，再重启或重新启用 timer。

如果任务只属于当前用户，也可以放在 `~/.config/systemd/user/`，使用 `systemctl --user` 管理。用户级 timer 是否能在用户未登录时运行，还取决于是否启用了 lingering：

```bash
loginctl enable-linger "$USER"
```

这一步会改变用户服务的生命周期，服务器上使用前应确认安全和运维要求。

## 四、方法三：at，只执行一次的任务

`at` 用来安排一次性任务，而不是周期任务。比如希望今天 23:30 执行一次清理：

```bash
echo "/opt/jobs/cleanup.sh >> /home/alice/cleanup.log 2>&1" | at 23:30
```

也可以指定日期：

```bash
at 23:30 2026-11-01
```

查看当前用户的待执行任务：

```bash
atq
```

删除任务：

```bash
atrm 7
```

其中 `7` 是 `atq` 输出的任务编号。查看某个任务实际保存的命令：

```bash
at -c 7
```

`at` 依赖 `atd` 服务。若系统未安装，可以按发行版安装 `at` 软件包，并确认服务处于运行状态：

```bash
sudo systemctl enable --now atd
```

`at` 同样不会自动拥有你在终端里的完整环境。建议在命令中使用绝对路径，并把输出重定向到日志文件。

## 五、方法四：anacron，适合不保证一直开机的机器

笔记本、测试机或家用电脑可能在任务时间处于关机状态。普通 cron 错过了时间通常不会补执行，而 `anacron` 按“天、周、月”的周期检查任务，开机后可以补做一次。

系统级配置一般在 `/etc/anacrontab`，格式与普通 crontab 不同：

```text
周期(天)  延迟(分钟)  标识  命令
1         5           daily-job  /opt/jobs/daily.sh
7         10          weekly-job /opt/jobs/weekly.sh
```

第一列 `1` 表示每天检查一次，第二列 `5` 表示 anacron 启动后延迟 5 分钟，第三列是任务标识，最后一列是命令。它不适合精确到某个时刻的任务；需要“每天 02:30 准时运行”时，应该使用 cron 或 systemd timer。

## 六、怎么选：一张表看懂

| 方法 | 典型用途 | 是否周期执行 | 关机错过后补执行 | 日志与状态 | 推荐程度 |
| --- | --- | --- | --- | --- | --- |
| `cron` | 简单的分钟/小时/每天任务 | 是 | 通常否 | 需要自行重定向或查系统日志 | 入门首选 |
| `systemd timer` | 服务器生产任务、需要可观测性 | 是 | 可用 `Persistent=true` | `systemctl`、`journalctl` 原生支持 | 生产优先 |
| `at` | 延迟执行、一次性清理或重启 | 否 | 不适用 | 可用 `atq` 查看 | 一次性任务首选 |
| `anacron` | 笔记本、低频维护任务 | 是 | 是 | 依赖系统配置 | 特定场景使用 |
| `while + sleep` | 临时脚本、容器内简单循环 | 是 | 否 | 由进程管理器负责 | 不建议单独用于生产 |

`while + sleep` 的写法很直观：

```bash
while true; do
    /opt/jobs/check.sh
    sleep 300
done
```

但它容易遇到进程退出后无人拉起、终端断开、日志无限增长和重复启动等问题。生产环境中应把它交给 systemd、Docker 的重启策略或其他进程管理器，而不是简单地 `nohup` 后台运行。

## 七、排查“定时任务没有执行”的顺序

可以按下面的顺序排查，通常比反复修改时间表达式更快：

1. **先手动执行脚本**：确认脚本本身能运行，退出码是否为 `0`。
2. **确认权限和用户**：任务是以哪个用户运行的？它是否能读取输入文件、写入日志和访问目标目录？
3. **把命令改成绝对路径**：包括 `python`、`node`、`tar` 和脚本依赖的配置文件。
4. **检查工作目录**：脚本里使用相对路径时，在开头显式 `cd /opt/jobs`，或全部改成绝对路径。
5. **保留标准输出和错误输出**：cron 用 `>> logfile 2>&1`，systemd 用 `journalctl -u 服务名`。
6. **检查调度器状态**：分别查看 `crontab -l`、`systemctl status cron`（部分发行版服务名为 `crond`）或 `systemctl list-timers`。
7. **检查时间和时区**：使用 `date` 查看系统时间，容器和服务器的时区可能与本地电脑不同。
8. **检查是否被锁跳过**：使用 `flock -n` 时，旧进程未退出会让后续任务主动跳过。

不要用 `watch` 代替调度器。`watch` 更适合在终端里临时重复执行命令，终端关闭后任务就结束，也没有可靠的开机启动和失败管理能力。

## 八、推荐的落地方式

如果只是个人服务器上每天执行一条简单脚本，可以从 cron 开始：

```cron
0 2 * * * /usr/bin/flock -n /tmp/backup.lock /opt/jobs/backup.sh >> /home/alice/backup.log 2>&1
```

如果任务属于长期运行的业务系统，建议使用 `systemd service + systemd timer`，把日志、运行状态、开机启动和错过补执行都纳入系统管理。无论选择哪种方式，都要做到三点：脚本可单独运行、命令使用绝对路径、失败时能留下可定位的日志。

> 定时任务最难的不是写出那五个星号，而是让任务在“换一个用户、换一个目录、机器重启、脚本失败”之后仍然表现可预期。
