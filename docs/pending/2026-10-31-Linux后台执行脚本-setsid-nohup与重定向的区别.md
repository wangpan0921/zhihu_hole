# Linux 后台执行脚本：`setsid`、`nohup`、`&` 与重定向到底有什么区别？

在服务器上跑一个监控脚本，很多人会直接复制一条“看起来很稳”的命令：

```bash
setsid nohup mysql_conn_monitor.sh >> mysql_conn_monitor.log 2>&1 < /dev/null &
```

但过一段时间后，问题就来了：关掉 SSH 后脚本还在吗？报错写进日志了吗？为什么有的命令要加 `setsid`，有的只写 `nohup`，还有的连 `nohup` 都没有？

这几条命令其实混合了四件不同的事：

- `&`：让当前 shell 不等待命令结束。
- `nohup`：让程序忽略终端关闭时常见的 `SIGHUP` 信号。
- `setsid`：让程序进入新的会话和进程组。
- `> / >>`、`2>&1`、`<`：重新安排标准输入、标准输出和标准错误。

先把这四件事分开，命令就不容易记错了。

## 一、先看五条命令分别做了什么

下面假设脚本已经有可执行权限，并且能通过 `PATH` 找到。生产环境更建议写成绝对路径，例如 `/opt/monitor/mysql_conn_monitor.sh`。

### 1. `setsid nohup ... < /dev/null &`

```bash
setsid nohup mysql_conn_monitor.sh >> mysql_conn_monitor.log 2>&1 < /dev/null &
```

这是五条命令里“脱离终端”最彻底的一条，组合了三层效果：

1. `&` 让当前 shell 立即返回，把命令放到后台。
2. `nohup` 让脚本忽略 `SIGHUP`，降低 SSH 断开或终端关闭带来的退出风险。
3. `setsid` 为脚本创建新的会话（session）和进程组（process group），不再和当前 shell 共享原来的作业控制关系。

`< /dev/null` 又把标准输入明确接到“永远读不到内容”的设备上。脚本如果误读 stdin，会立即得到 EOF，而不是卡在已经不存在的 SSH 终端上。

因此，它适合临时启动一个确实不需要交互输入的长任务。但要注意：`setsid` 和 `nohup` 解决的是不同问题，`setsid` 不是“更强版 nohup”，两者也不等于进程守护。脚本崩溃后，它们不会自动重启。

### 2. `nohup ... < /dev/null &`

```bash
nohup mysql_conn_monitor.sh >> mysql_conn_monitor.log 2>&1 < /dev/null &
```

这条命令没有创建新会话，但通常已经足够应对“退出 SSH 后继续运行”的需求：

- `&` 让 shell 不等待。
- `nohup` 忽略 `SIGHUP`。
- 显式的 `< /dev/null` 避免脚本等待终端输入。
- `>> mysql_conn_monitor.log 2>&1` 把标准输出和标准错误都追加到同一个日志文件。

脚本仍可能保留原来的会话、进程组和工作目录。对大多数普通后台脚本来说，这不是问题；如果程序会依赖作业控制、终端状态，或者需要更彻底地与终端隔离，再考虑 `setsid`。

### 3. `nohup ... &`

```bash
nohup mysql_conn_monitor.sh >> mysql_conn_monitor.log 2>&1 &
```

它和上一条的主要差别只有标准输入：没有显式写 `< /dev/null`。

在 GNU/Linux 上，如果 `nohup` 发现标准输入来自终端，通常会把它改到一个不可读的输入源，让程序读到 EOF；具体行为以系统上的 `nohup` 实现为准。因此，很多时候这条命令也能正常“挂后台”。

不过，脚本的输入来源一眼看不出来，排查问题时容易产生误解。只要脚本确定不需要输入，建议把 `< /dev/null` 明确写出来。显式声明比依赖 `nohup` 的附带处理更容易维护，也更方便迁移到其他 Unix 环境。

### 4. 直接执行并把输出、错误都写入日志

```bash
mysql_conn_monitor.sh >> mysql_conn_monitor.log 2>&1
```

这里没有 `&`，所以当前 shell 会一直等待脚本结束。这是前台执行，不是后台执行。

它的优点是简单：脚本退出码会直接返回给当前 shell，按 `Ctrl+C` 也能方便地停止。缺点是 SSH 断开、终端关闭时，脚本通常仍会收到 `SIGHUP`，可能随之退出；标准输入也仍然连接着当前终端。

### 5. 只把标准输出追加到日志

```bash
mysql_conn_monitor.sh >> mysql_conn_monitor.log
```

这条同样是前台执行，而且只处理了标准输出（文件描述符 `1`）：

- 正常输出：追加到 `mysql_conn_monitor.log`。
- 错误输出（文件描述符 `2`）：仍然显示在终端。
- 没有 `&`：当前 shell 继续等待。

所以它适合调试时边看报错边保存正常输出，不适合无人值守运行。SSH 断开后，错误信息也不会神奇地出现在日志文件里。

## 二、`2>&1` 为什么要放在最后

Shell 的重定向会从左到右处理：

```bash
mysql_conn_monitor.sh >> mysql_conn_monitor.log 2>&1
```

处理过程是：

1. 先把标准输出 `1` 指向日志文件。
2. 再让标准错误 `2` 指向“标准输出当前指向的位置”，也就是同一个日志文件。

因此，常见写法是 `>> log 2>&1`。下面这条顺序不同，效果也不同：

```bash
mysql_conn_monitor.sh 2>&1 >> mysql_conn_monitor.log
```

它会先把标准错误复制到当时的标准输出（通常仍是终端），再把标准输出改到日志文件。结果就是：正常输出进日志，错误输出还留在终端。

`>>` 表示追加，适合长期运行的监控脚本；单个 `>` 表示覆盖，每次启动都会清空原日志。无论选择哪种，都应配合日志轮转，否则日志文件会一直变大。

## 三、五条命令放在一起对比

| 命令 | 是否后台 | 是否忽略 `SIGHUP` | 是否新建会话 | 标准输入 | 标准错误 |
| --- | --- | --- | --- | --- | --- |
| `setsid nohup ... >> log 2>&1 < /dev/null &` | 是 | 是 | 是 | `/dev/null` | 日志 |
| `nohup ... >> log 2>&1 < /dev/null &` | 是 | 是 | 否 | `/dev/null` | 日志 |
| `nohup ... >> log 2>&1 &` | 是 | 是 | 否 | 通常由 `nohup` 处理，建议显式写出 | 日志 |
| `... >> log 2>&1` | 否 | 否 | 否 | 当前终端 | 日志 |
| `... >> log` | 否 | 否 | 否 | 当前终端 | 当前终端 |

一句话记忆：

> `&` 管“现在要不要等”，`nohup` 管“终端没了会不会收到 SIGHUP”，`setsid` 管“要不要换一个会话”，重定向管“输入输出去哪儿”。

## 四、实际应该怎么选

### 只想临时放到后台跑

```bash
nohup /opt/monitor/mysql_conn_monitor.sh \
  >> /var/log/mysql_conn_monitor.log 2>&1 < /dev/null &
```

启动后可以用 `ps`、`pgrep` 或 `jobs -l` 检查进程，再用 `tail -f` 查看日志。若需要记录 PID，可以在命令末尾保存 `$!`，但要注意当前 shell 中的 `$!` 只代表刚刚启动的后台进程。

### 希望与当前终端的作业控制关系更彻底地隔离

```bash
setsid nohup /opt/monitor/mysql_conn_monitor.sh \
  >> /var/log/mysql_conn_monitor.log 2>&1 < /dev/null &
```

这适合明确需要新会话的场景，但不要把它当作完整的服务管理方案。

### 希望长期运行、失败自动拉起

优先考虑 `systemd`、容器编排平台或其他进程管理器。它们可以统一处理启动顺序、自动重启、日志轮转、资源限制和停止服务。`nohup` 只是“别因为终端关闭就退出”，并不负责监控进程健康状况。

## 五、几个容易忽略的坑

1. **脚本不一定能找到。** `mysql_conn_monitor.sh` 必须在 `PATH` 中，或者使用 `./mysql_conn_monitor.sh`、绝对路径；脚本还应有正确的 shebang 和执行权限。
2. **重定向不等于日志管理。** `>>` 只负责打开文件并追加，不负责按天切割、压缩和删除旧日志。
3. **后台不等于无人值守。** 脚本可能依赖环境变量、当前目录、配置文件或网络凭据。启动前应使用绝对路径，并在脚本中明确设置必要环境。
4. **`nohup` 不会自动重启。** 进程被 `kill -9`、内存不足或自身异常退出时，`nohup` 都不会把它拉起来。
5. **停止时要找对进程。** 生产环境不要用宽泛的 `pkill -f mysql`，应保存 PID 或使用 `systemctl stop`，避免误杀其他进程。

## 总结

这五条命令没有谁“绝对正确”：前两条适合临时脱离 SSH 运行，第三条是常见简写，第四条适合前台执行和调试，第五条只保存正常输出。真正理解 `&`、`nohup`、`setsid` 和三类标准流之后，你就能按运行场景组合命令，而不是靠复制一条看不懂的启动命令。
