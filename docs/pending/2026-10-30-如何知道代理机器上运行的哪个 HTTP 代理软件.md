# 如何知道代理机器上运行的哪个 HTTP 代理软件

## 背景

一个项目经过 N 个人转手后，原负责人已经离职，许多历史信息也无从考证。这个项目运行在火山服务环境中，无法直接访问外网，但又需要通过外网发送飞书消息。因此，项目配置了一个 HTTP 代理，通过代理访问飞书服务。

代码里只留下了一个 IP 和端口：`http://10.106.1.168:8888`。这个代理究竟由什么软件提供？它运行在哪里？下面记录一下我的排查过程。

## 第一步：用 ss 定位监听端口的进程

先在代理机器上查看 8888 端口由哪个进程监听：

```text
# 查看监听进程
sudo ss -ltnp 'sport = :8888'

# 如果进程名不明显，可以根据 PID 继续查看进程详情：
ps -fp 1234
sudo readlink -f /proc/1234/exe
sudo tr '\0' ' ' < /proc/1234/cmdline
```
![proxy1](./proxy1.png)

如果看到类似下面的启动命令：

```text
/usr/bin/docker-proxy -proto tcp -host-ip 0.0.0.0 -host-port 8888 -container-ip 172.19.0.2 -container-port 8888
```

这里的 `docker-proxy` 并不是实际的 HTTP 代理软件，而是 Docker 提供的端口转发进程。这条命令表示：

```text
代理机 0.0.0.0:8888
        ↓ Docker 端口映射
容器 172.19.0.2:8888
```

也就是说，当外部访问 `10.106.1.168:8888` 时，流量会被转发到某个 Docker 容器的 8888 端口。真正的 HTTP 代理软件应该运行在这个容器里。


## 第二步：用 docker ps 查看容器和端口映射

```text
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
podman ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
```

![proxy2](./proxy2.png)

通过这一步，可以看到服务对应的容器名称、镜像名称、容器 ID 和端口映射关系。

```text
# 如果没有代理机器的登录权限，也可以先从客户端发起请求，确认代理是否可用：
curl -v -x http://10.106.1.168:8888 https://open.feishu.cn/
```

## 第三步：查看容器内的实际进程

确认容器后，继续查看容器内运行的进程：

```text
-bash-4.4$ sudo docker exec 863e9225f3a9 ps -ef
PID   USER     TIME  COMMAND
    1 root     45d19 tinyproxy -d
  214 root      0:00 ps -ef
```

这里可以看到，容器中的实际进程是 `tinyproxy`。至此，已经确认这个代理服务使用的是 Tinyproxy。

## 最快的确认方式

如果只想快速确认 8888 端口对应的容器、镜像和启动命令，可以直接执行：

```text
sudo docker ps --filter publish=8888 --format '容器={{.Names}} 镜像={{.Image}} 命令={{.Command}} 端口={{.Ports}}'
```

![proxy4](./proxy4.png)

从输出可以判断：这是一个通过 Docker 部署的 Tinyproxy 正向 HTTP 代理。

当前请求链路如下：

```text
客户端
  -> 10.106.1.168:8888
  -> Docker 端口映射
  -> tinyproxy 容器:8888
  -> open.feishu.cn:443
```

关键信息：

- 容器名：tinyproxy
- 镜像：xxx.cloud.xxx.cn/yzl-common/vimagick/tinyproxy:25-09-09
- 启动命令：tinyproxy -d
- `-d`：以前台方式运行，便于交给 Docker 管理
- 端口：宿主机 8888 映射到容器 8888

## 第四步：用 docker inspect 查看部署配置

先查看容器的完整部署配置：

```text
sudo docker inspect tinyproxy
```

如果只关心挂载、环境变量、重启策略和网络配置，可以提取这些字段：

```text
sudo docker inspect tinyproxy \
  --format 'Mounts={{json .Mounts}}
Env={{json .Config.Env}}
Restart={{json .HostConfig.RestartPolicy}}
Network={{json .NetworkSettings.Networks}}'
```

![proxy5](./proxy5.png)

## 第五步：查看 Tinyproxy 配置

```text
sudo docker exec tinyproxy cat /etc/tinyproxy/tinyproxy.conf
```

![proxy6](./proxy6.png)

配置文件中的几个关键字段如下：

- Port：容器监听端口
- Allow：允许使用代理的客户端 IP 或网段
- ConnectPort 443：允许通过代理访问 HTTPS
- Timeout：连接超时
- LogLevel：日志级别


## 第六步：判断部署方式

接下来判断这个容器是通过 `docker run` 还是 Docker Compose 部署的：

```text
sudo docker inspect tinyproxy \
  --format '{{json .Config.Labels}}'
```

![proxy7](./proxy7.png)

如果输出中包含以下标签：

```text
com.docker.compose.project
com.docker.compose.service
com.docker.compose.project.config_files
```

就说明这个容器由 Docker Compose 部署，`com.docker.compose.project.config_files` 通常可以帮助我们找到对应的 `compose.yaml` 文件。


## 第七步：查看 docker-compose.yaml

```text
sudo cat /root/yzl/tiniproxy/docker-compose.yaml
```

## 小白科普

Tinyproxy 是一个开源、轻量级的 HTTP/HTTPS 正向代理软件，主要运行在 Linux/Unix 系统上。它的特点包括：

- 支持 HTTP 代理
- 通过 HTTP CONNECT 方法转发 HTTPS 流量
- 资源占用较小
- 支持按客户端 IP 设置 Allow/Deny
- 支持访问日志、超时和端口限制
- 通常使用 GPL v2 或更高版本许可证

正向代理（Forward Proxy）位于客户端和目标服务器之间。客户端主动将请求交给代理，由代理代替客户端访问目标服务器，再将响应返回给客户端。

正向代理通常用于解决以下问题：

- 客户端无法直接访问外网
- 统一出口和访问控制
- 记录、审计网络请求
- 缓存或限制访问
- 隐藏客户端源地址

Tinyproxy、Squid 都属于正向 HTTP 代理。访问 HTTPS 时，客户端通常使用 `CONNECT` 方法，让代理建立一条加密隧道。代理一般只能看到目标域名和连接信息，不能直接看到 HTTPS 内容。

常见代理类型如下：

| 类型 | 说明 | 常见用途 |
| --- | --- | --- |
| 正向代理 | 代理替客户端访问外部服务 | 内网访问外网、统一出口 |
| 反向代理 | 代理服务器接收外部请求，再转发给后端服务 | Nginx、网关、负载均衡 |
| HTTP/HTTPS 代理 | 使用 HTTP 协议代理请求，HTTPS 通常用 CONNECT | Web/API 访问 |
| SOCKS4/SOCKS5 代理 | 更底层的通用 TCP/UDP 代理 | SSH、数据库、浏览器等多种协议 |
| 透明代理 | 客户端通常不需要配置代理，网络设备自动劫持流量 | 网关审计、统一出口 |
| 匿名代理 | 尽量隐藏客户端地址或代理身份 | 隐私访问 |
| VPN | 在客户端与网关之间建立虚拟网络隧道 | 整体网络接入、跨网访问 |
| CDN/边缘代理 | 代理并缓存公网服务内容 | 加速、抗攻击、就近访问 |
| 服务网格代理 | 服务旁边的代理进程，负责服务间通信 | Istio/Envoy、微服务治理 |

也可以按工作方向进行区分：

正向代理：客户端 -> 代理 -> 目标服务

反向代理：客户端 -> 代理 -> 后端服务

两者的主要区别是：

- 正向代理代表客户端，通常由客户端配置代理地址。
- 反向代理代表服务端，客户端通常只访问代理域名，不知道后端真实地址。

回到本文的案例：这个项目中的 Tinyproxy 属于“正向代理 + HTTP 代理”。
