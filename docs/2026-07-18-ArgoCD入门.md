# Argo CD 入门：用一个最小示例看懂 GitOps

如果你第一次接触 Argo CD，可以先把它理解成一句话：

> Argo CD 是一个帮你把 Git 仓库里的 Kubernetes 配置，自动同步到集群里的工具。

你改 Git 里的 YAML，它就负责把集群里的应用也改成同样的状态。

这套思路叫 **GitOps**。对小白来说，不用先背概念，先记住一个直觉就够了：

- Git 里放“期望状态”；
- 集群里放“实际状态”；
- Argo CD 负责把两边对齐。

## 一、它解决什么问题

在没有 Argo CD 的时候，常见部署方式是：

1. 人手工 `kubectl apply`。
2. CI/CD 脚本里写一串部署命令。
3. 多个环境各改各的，最后没人说得清线上到底跑的是哪个版本。

这样做的问题是：

- 配置散在各处，不好追踪。
- 改动历史不清楚。
- 集群和 Git 很容易不同步。
- 回滚时要翻日志、找脚本、猜版本。

Argo CD 的思路很直接：

> 只要 Git 里的声明变了，集群就跟着变。

这样部署就从“人手工操作”变成了“以 Git 为准”。

## 二、先认识几个最常见的词

### 1. Application

Argo CD 里最核心的对象叫 `Application`。

它不是你的业务应用代码，而是一个“部署说明书”，告诉 Argo CD：

- 去哪个 Git 仓库找配置；
- 看哪个目录；
- 部署到哪个 Kubernetes 集群和命名空间。

### 2. Sync

`Sync` 就是同步。意思是把 Git 里的配置真正应用到集群。

如果 Git 改了，但还没同步，Argo CD 会看到状态是 `OutOfSync`。

### 3. Desired State / Live State

可以理解成两种状态：

- Desired State：Git 里希望集群变成什么样；
- Live State：集群现在实际是什么样。

Argo CD 就是比较这两者是否一致。

## 三、一个最小可操作示例

Argo CD 官方文档里有一个很经典的示例：`guestbook`。

我们就用它来理解最小流程。

### 第一步：安装 Argo CD

如果你已经有集群，这一步只需要在集群里装 Argo CD。

官方文档给出的典型命令是：

```bash
kubectl create namespace argocd
kubectl apply -n argocd --server-side --force-conflicts -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
```

如果是学习环境，官方也提供按版本固定安装的方式，生产环境更适合固定版本，不要长期用 `stable` 漂移。

### 第二步：准备一个示例仓库

Argo CD 官方提供了一个示例仓库：

```text
https://github.com/argoproj/argocd-example-apps.git
```

里面就有 `guestbook` 示例目录。

### 第三步：写一个 Application

下面是一个最小的 `Application` 示例：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: default
```

这几行分别什么意思：

- `repoURL`：Git 仓库地址。
- `targetRevision`：分支、tag 或 commit，`HEAD` 表示当前默认分支最新内容。
- `path`：仓库里的目录，这里是 `guestbook`。
- `destination.server`：目标 Kubernetes 集群。
- `destination.namespace`：部署到哪个命名空间。

你可以把它保存成 `application.yaml`。

### 第四步：创建应用

如果你已经配置好 `kubectl` 能连上集群，就执行：

```bash
kubectl apply -n argocd -f application.yaml
```

然后去 Argo CD 的 UI 或者 CLI 看状态。

### 第五步：同步部署

刚创建完时，应用通常还没真正部署到集群，需要同步：

```bash
argocd app sync guestbook
```

同步之后，Argo CD 会把 Git 仓库里的 Kubernetes YAML 应用到集群里。

如果你用 UI，也可以在页面里点 `Sync`。

## 四、这个示例里到底发生了什么

还是用最通俗的话说：

1. 你把 `application.yaml` 提交给 Argo CD。
2. Argo CD 发现这个应用指向 `argocd-example-apps` 仓库里的 `guestbook` 目录。
3. 它读取那里的一组 Kubernetes YAML。
4. 它把这些 YAML 应用到集群里。
5. 以后你只要改 Git 里的 YAML，Argo CD 就可以继续同步。

所以 Argo CD 干的不是“写业务代码”，而是“盯住 Git 和集群是否一致”。

## 五、为什么它适合新手理解

Argo CD 的好处不是“概念高级”，而是“心智模型清楚”。

你只需要记住三件事：

- Git 是唯一可信来源；
- Argo CD 是同步器；
- Kubernetes 是最终执行环境。

这样以后你看 UI 上的状态，就不会迷糊：

- `Synced`：Git 和集群一致。
- `OutOfSync`：Git 改了，但集群还没跟上。
- `Healthy`：资源本身工作正常。
- `Progressing` / `Degraded`：资源还在变更，或者已经有异常。

## 六、一个最常见的日常用法

假设你把镜像版本从 `v1` 改成 `v2`，同时提交到 Git。

Argo CD 看到 Git 变更后，会发现集群和 Git 不一致，于是显示 `OutOfSync`。

你点同步，或者开启自动同步后，它就把新版本部署上去。

这比“谁手工改了线上”更可控，因为：

- 改动历史在 Git 里。
- 回滚直接回退 Git 提交。
- 多人协作时，大家看到的是同一份声明。

## 七、入门时最容易踩的坑

### 1. 以为 Argo CD 直接替代 Kubernetes

不是。Kubernetes 还是执行者，Argo CD 只是负责把声明应用过去。

### 2. 以为改完 Git 就一定立刻生效

不一定。还要看是否已经同步，是否启用了自动同步，是否有权限或资源问题。

### 3. 把 Application 当成业务代码

`Application` 只是部署配置，不是你的服务本体。

### 4. 忘了 namespace

Argo CD 自己通常装在 `argocd` namespace 里，业务应用一般部署到别的 namespace。这个别混。

### 5. 只看同步，不看健康状态

`Synced` 不代表服务一定正常，还要看 `Healthy`。

## 八、如果你只想记住一个最小模板

先记这个：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: default
```

它表达的意思就是：

> 去这个 Git 仓库的这个目录，把里面的 Kubernetes 配置同步到这个集群的这个命名空间。

## 九、小结

Argo CD 对小白来说，不必先追着术语跑。先把它当成一个 Git 到 Kubernetes 的同步器：

- Git 存你想要的状态；
- Argo CD 盯着 Git；
- 集群最终按 Git 走。

你理解了 `Application`、`Sync`、`Synced`、`OutOfSync` 这几个词，再看 UI 和 YAML，就会顺很多。

如果你接下来真的要上手，建议先拿官方的 `guestbook` 示例跑一遍。跑通一次，比看十遍概念更有用。
